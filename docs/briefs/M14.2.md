# M14.2 `query_index` Core: `IndexQuery` and `IndexQueryAuthorizer`

Base: `dev`. Core only, one new source file plus three test files. It
runs in parallel with M14.1 (which refactors `EmailIndex.cs`): **do not
edit `EmailIndex.cs`, `EmailIndex.Ai.cs` or `MailboxIndexes.cs`**. Everything
needed already exists: `EmailIndex.DbPath` (public), `MailboxIndexes.Mailboxes`,
`MailboxIndexes.For`, `MailboxIndexes.Normalize`, `MailboxIndexes.AllMailboxes`.

## Goal

Implement the Core side of `query_index` (SPEC §11.12, schema §9.1,
storage/logging §5.1, perf §17): run **one read-only `SELECT`** over three
per-connection **temp views** (`mail`, `mail_fts`, `mail_attachments`) of a
mailbox's index, through a dedicated non-pooled `Mode=ReadOnly`
connection with `query_only`, SQLite limits, an authorizer allow-list
(`IndexQueryAuthorizer.Decide`, a pure function), and a progress handler
that enforces a 10 s deadline for the whole call. Shape the result
(columns, rows, row/cell/size caps, `truncated*`, `elapsed_ms`) and map
every failure to the exact §11.12 `McpException` texts. M14.3 wires it
into `McpTools`; this task adds no tool, no logging and no App code.

## Hard rules that apply here

- **Nothing is ever written to the index file.** The connection is
  `Mode=ReadOnly`; temp views live in the connection's temp schema; then
  `query_only`, the authorizer and `sqlite3_stmt_readonly` each block
  writes on their own. A test hashes the `.db` before and after.
- **Only what `search_emails`/`get_message` expose.** No `meta`,
  `sync_state`, `ai_decisions`, `sqlite_*` tables, pragmas, or the
  `emails` columns `store_id`, `internet_message_id`, `in_reply_to`,
  `clippy_marker`, `last_modified` (and `entry_id` only as `mail.id`).
  Attachment content isn't in the index, so it can't leak.
- **No logging in `IndexQuery.cs`.** No `ILogger`, no `Console`, no
  `Debug.Write`. The SQL text, cell values and SQLite messages are never
  logged (§5.1, §11.12). M14.3 logs counts only and adds the scan.
- No `load_extension`: never call `SqliteConnection.EnableExtensions` or
  `LoadExtension`; additionally turn it off with `sqlite3_db_config`.
- No `.Result`/`.Wait()`. The API is synchronous like `EmailIndex`
  (Microsoft.Data.Sqlite has no real async I/O, §9.2).

```csharp

public sealed record IndexQueryResult(

    [property: JsonPropertyName("truncated")] bool Truncated,
    [property: JsonPropertyName("truncated_reason"), JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]

    [property: JsonPropertyName("elapsed_ms")] long ElapsedMs);

{
    public const int MaxSqlChars = 20_000;
    public const int DefaultMaxRows = 200;
    public const int MaxRowsLimit = 1_000;
    public const int MaxColumns = 100;
    public const int MaxCellChars = 2_000;
    public const int MaxTotalChars = 1_000_000;
    public const int ProgressInterval = 1_000;          // VM steps between deadline checks
    public const int MaxValueBytes = 50_000_000;        // SQLITE_LIMIT_LENGTH (see Spec changes)
    public static readonly TimeSpan Timeout = TimeSpan.FromSeconds(10);

    /// <summary>Runs one read-only SELECT over the temp views of one mailbox ("" / address) or every
    /// enabled mailbox ("all"). maxRows is clamped to 1..1000.</summary>
    /// <exception cref="McpException">Every user-facing failure, with an IndexQueryTexts message
    /// or the §9.3 mailbox error (from MailboxIndexes.For).</exception>
    /// <exception cref="OperationCanceledException">ct was cancelled (before or during the query).</exception>
    /// <exception cref="ArgumentNullException">indexes is null.</exception>
    public static IndexQueryResult Run(MailboxIndexes indexes, string? sql, string? mailbox,
        int maxRows = DefaultMaxRows, CancellationToken ct = default);

    /// <summary>Test seam: same as Run with a shorter deadline.</summary>
    internal static IndexQueryResult Run(MailboxIndexes indexes, string? sql, string? mailbox,
        int maxRows, TimeSpan timeout, CancellationToken ct);

    /// <summary>The CREATE TEMP VIEW script for one mailbox key ("" = own); the key is a doubled-quote SQL literal.</summary>
    internal static string ViewDdl(string mailboxKey);

    /// <summary>Skips whitespace, ';', "--" line comments and "/* */" comments (an unterminated
    /// "/*" runs to the end). Returns the first word (ASCII letters/digits/_ only) upper-cased
    /// (invariant), "" when nothing is left or the next char isn't a word char, and the index
    /// where that first token starts (sql.Length when nothing is left).</summary>
    internal static (string Keyword, int Start) LeadingKeyword(string sql);

    /// <summary>True when the text is only whitespace, ';' and comments (LeadingKeyword(t).Start == t.Length).</summary>
    internal static bool IsEmptyTail(string? tail);
}

/// <summary>SPEC §11.12 authorizer as a pure function. Allow → (true, null); deny → (false, what).</summary>
public static class IndexQueryAuthorizer
{
    public readonly record struct Decision(bool Allow, string? What);

    /// <param name="action">SQLite action code (raw.SQLITE_*).</param>
    /// <param name="arg1">3rd C argument (table / pragma / …).</param>
    /// <param name="arg2">4th C argument (column / function name / pragma value / …).</param>
    /// <param name="dbName">"main", "temp", … or null.</param>
    /// <param name="viewName">Inner-most trigger or view responsible, or null for top-level SQL.</param>
    public static Decision Decide(int action, string? arg1, string? arg2, string? dbName, string? viewName);
}

public static class IndexQueryTexts
{
    public const string SqlRequired = "sql is required: one SELECT over the views mail, mail_fts and mail_attachments.";
    public const string SqlTooLong = "sql is longer than 20,000 characters. Shorten the query.";
    public const string MultipleStatements = "query_index runs exactly one SELECT statement. Remove everything after the first statement.";
    public const string NoParameters = "query_index takes no parameters; write the values into the SQL.";
    public const string TooManyColumns = "query_index returns at most 100 columns.";
    public const string Timeout = "The query ran longer than 10 seconds and was stopped. Add a date range, a folder or a LIMIT, or use email_stats for counts.";
    public static string SqlError(string sqliteMessage);   // "SQL error: <msg>. query_index reads the views mail, mail_fts and mail_attachments (see the tool description)."
    public static string Denied(string what);              // "query_index only reads the views mail, mail_fts and mail_attachments with one SELECT. Not allowed here: <what>."
    public static string Unavailable(string mailboxKey);   // "The index for <label> isn't available right now. Check index_status."
```

`SqlError`: trim the SQLite message and drop one trailing `.` before
inserting it, so the text never has `..`. An empty message becomes
`unknown error`. `Unavailable`: `<label>` is `your own mailbox` for `""`,
else the mailbox key. The `Timeout` text keeps "10 seconds" even when the
test seam passes a shorter deadline.

## Behavior

### A. `Run` order

1. `ArgumentNullException.ThrowIfNull(indexes)`;
   `ct.ThrowIfCancellationRequested()`; start a `Stopwatch` (the deadline
   and `elapsed_ms` cover the whole call).
2. `sql` null/whitespace → `McpException(SqlRequired)`. `sql.Length >
   MaxSqlChars` → `SqlTooLong`. Don't trim the SQL that is prepared
   beyond step 4.
3. **Keyword pre-check** on `(kw, start) = LeadingKeyword(sql)`:
   - `start == sql.Length` (only comments/`;`) → `SqlRequired`.
   - `SELECT`, `WITH`, `VALUES` → continue.
   - `INSERT`, `REPLACE`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `ALTER`,
     `REINDEX`, `ANALYZE`, `VACUUM` → `Denied("writing")`.
   - `PRAGMA` → `Denied("PRAGMA")`; `ATTACH` → `Denied("ATTACH")`;
     `DETACH` → `Denied("DETACH")`; `EXPLAIN` → `Denied("EXPLAIN")`.
   - `BEGIN`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT`, `RELEASE` →
     `Denied("transactions")`.
   - Anything else (including `kw == ""`) →
     `Denied("statements that don't start with SELECT, WITH or VALUES")`.

   Why first: `DELETE FROM mail` fails in SQLite's prepare with "cannot
   modify mail because it is a view" before the authorizer is asked;
   the pre-check gives the §11.12 "Not allowed here" text instead.
4. `maxRows = Math.Clamp(maxRows, 1, MaxRowsLimit)`.
5. Mailboxes: `key = MailboxIndexes.Normalize(mailbox)`. `key == "all"`
   → `targets = indexes.Mailboxes` (own first, then shared in the order
   they were added) and `withMailboxColumn = true`; else `targets =
   [key]` after `indexes.For(mailbox)` (which throws the §9.3
   `McpException` for unknown/disabled mailboxes). For each target take
   `indexes.For(target).DbPath` (a mailbox disabled meanwhile throws the
   §9.3 error; that's fine).
6. For each target in order, while rows remain to be collected: if the
   deadline has passed → `Timeout`; run section B+C on
   `sql.Substring(start)`. When `maxRows` is reached and more targets
   remain, stop, `truncated = true`, `truncated_reason = "max_rows"`
   (later mailboxes weren't queried, so rows may have been left out).
   Any error in any mailbox fails the whole call (no partial results).
7. Columns: the statement's column names from the first target (all
   targets run the same SQL against the same views, so they match).
   With `all`, prepend `"mailbox"` to the columns and the mailbox key
   (`""` for own) to every row. The user's own columns may repeat names;
   names are returned as SQLite gives them.
8. Return `IndexQueryResult(columns, rows, rows.Count, truncated,
   reason, truncatedCells, stopwatch.ElapsedMilliseconds)`.

### B. Connection setup (per target, exactly in this order)

1. `File.Exists(dbPath)` false → `Unavailable(key)`.
2. `new SqliteConnection(new SqliteConnectionStringBuilder { DataSource = dbPath, Mode = SqliteOpenMode.ReadOnly, Pooling = false }.ToString())`,
   `Open()`. Then one command: `PRAGMA busy_timeout=5000;`.
3. Schema check, still without the authorizer:
   `SELECT count(*) FROM main.sqlite_master WHERE type IN ('table') AND name IN ('emails','attachments','emails_fts')`
   must be 3. Otherwise → `Unavailable(key)`.
4. Execute `ViewDdl(key)` (one command, three statements; below).
5. `PRAGMA query_only = ON;` (after the views: `query_only` also blocks
   the temp schema).
6. On `var db = connection.Handle`:
   - `raw.sqlite3_limit(db, raw.SQLITE_LIMIT_ATTACHED, 0)`
   - `raw.sqlite3_limit(db, raw.SQLITE_LIMIT_SQL_LENGTH, MaxSqlChars)`
   - `raw.sqlite3_limit(db, raw.SQLITE_LIMIT_LENGTH, MaxValueBytes)`
   - `raw.sqlite3_db_config(db, raw.SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION, 0, out _)`
7. Install the authorizer: `raw.sqlite3_set_authorizer(db, callback, null)`.
   The callback calls `IndexQueryAuthorizer.Decide` and returns
   `raw.SQLITE_OK` or `raw.SQLITE_DENY`; on deny it stores the first
   `What` of this statement in a per-call state object (later denials
   don't overwrite it). The callback catches every exception and returns
   `SQLITE_DENY` (exceptions must not cross into native code).
8. Install the progress handler:
   `raw.sqlite3_progress_handler(db, ProgressInterval, cb, null)` where
   `cb` returns 1 when `ct.IsCancellationRequested` or
   `stopwatch.Elapsed >= timeout`, else 0.
9. Keep both delegates in locals and `GC.KeepAlive` them after the
   statement is finalized. Dispose order: statement, then connection.
   With `Pooling=false` the handle is really closed, so neither the
   authorizer nor the pragmas reach any other connection.

Any `SqliteException` in steps 2–4 → `Unavailable(key)` (file being
rebuilt, locked past the busy timeout, not a database). Never the SQLite
message: the file path is in it.

### C. Temp-view DDL (`ViewDdl`)

`<mb>` is the normalized key with every `'` doubled, inside single
quotes (own mailbox: `''`). Exactly:

```sql
CREATE TEMP VIEW mail AS
SELECT e.entry_id AS id,
       e.id AS doc,
       '<mb>' AS mailbox,
       e.folder AS folder,
       strftime('%Y-%m-%dT%H:%M:%S', e.event_time, 'unixepoch', 'localtime') AS date,
       e.event_time AS unix_time,
       e.sender_name AS sender_name,
       e.sender_email AS sender_email,
       e.to_addrs AS to_addrs,
       e.cc_addrs AS cc_addrs,
       e.subject AS subject,
       e.conversation_topic AS topic,
       e.body AS body,
       COALESCE(e.unread, 0) AS unread,
       COALESCE(e.has_attachments, 0) AS has_attachments,
       e.attachment_names AS attachment_names
FROM main.emails AS e;

CREATE TEMP VIEW mail_fts AS
SELECT f.emails_fts AS mail_fts,
       f.rank AS rank,
       f.rowid AS doc,
       f.subject AS subject,
       f.body AS body,
       f.sender_name AS sender_name,
       f.sender_email AS sender_email,
       f.to_addrs AS to_addrs,
       f.cc_addrs AS cc_addrs,
       f.attachment_names AS attachment_names
FROM main.emails_fts AS f;

CREATE TEMP VIEW mail_attachments AS
SELECT a.email_id AS doc,
       a.position AS position,
       a.filename AS filename,
       a.size AS size,
       COALESCE(a.is_inline, 0) AS is_inline
FROM main.attachments AS a;
```

The FTS column order matches `emails_fts` (§9.1), so
`snippet(mail_fts, 1, …)` means `body` as in the tool description.
Through these flattenable views, `mail_fts MATCH …`, `snippet(mail_fts, …)`,
`highlight(mail_fts, …)`, `bm25(mail_fts)` and `ORDER BY rank` resolve
to the FTS5 hidden columns after query flattening. T2.4 proves it.

**Fallback (only if T2.4 can't pass through the view):** drop the
`mail_fts` view from `ViewDdl` and keep everything else. The model then
uses the real table: `emails_fts MATCH …`, `snippet(emails_fts, …)`,
`emails_fts.rowid` as the join key to `mail.doc`. Rewrite T2.4 for that
form and say so in the hand-back first line, because SPEC §11.12, the
error texts and M14.3's tool description must change. Don't take the
fallback for one failing aux function; report which one fails instead.

### D. Statement (per target)

1. Reset the recorded denial. `rc = raw.sqlite3_prepare_v2(db, text, out stmt, out tail)`.
2. `rc != SQLITE_OK` → recorded denial ? `Denied(what)` :
   `SqlError(raw.sqlite3_errmsg(db).utf8_to_string())`.
3. `stmt` null/invalid → `SqlRequired` (can't normally happen after the
   pre-check).
4. `!IsEmptyTail(tail)` → `MultipleStatements`. This is a lexical check,
   not a second prepare: preparing `; ;SELECT 2` returns no statement
   for the empty `;` and would hide the second statement.
5. `raw.sqlite3_stmt_readonly(stmt) == 0` → `Denied("writing")`.
6. `raw.sqlite3_bind_parameter_count(stmt) > 0` → `NoParameters`
   (`?`, `?1`, `:x`, `@x`, `$x`; a `?` inside a string literal is not a
   parameter).
7. `raw.sqlite3_column_count(stmt) > MaxColumns` → `TooManyColumns`.
   Column names: `raw.sqlite3_column_name(stmt, i).utf8_to_string()`.
8. Step loop:
   - `rc == SQLITE_ROW`: if the result already has `maxRows` rows →
     `truncated = true`, `reason = "max_rows"`, stop (so `truncated` is
     true only when another row really exists). Otherwise build the row
     (E). If `totalChars + rowChars > MaxTotalChars` → `truncated =
     true`, `reason = "size"`, stop without adding it. Else add.
   - `rc == SQLITE_DONE` → next target.
   - `rc == SQLITE_INTERRUPT` (or any error while the progress handler
     fired): `ct.IsCancellationRequested` →
     `throw new OperationCanceledException(ct)`; else → `Timeout`.
   - Other error: recorded denial ? `Denied(what)` : `SqlError(errmsg)`.
     (FTS5 prepares its own statements during `step`; a denial there
     shows up here.)
9. The deadline also counts while stepping rows that the handler doesn't
   see (cheap rows): check `stopwatch.Elapsed >= timeout` every 100 rows
   and after each target → `Timeout`.

### E. Cell shaping

- `SQLITE_INTEGER` → `long`. `SQLITE_FLOAT` → `double`; non-finite
  (`±Infinity`, e.g. `SELECT 1e999`) → `null` (JSON has no infinity).
- `SQLITE_NULL` → `null`.
- `SQLITE_TEXT` → `string`. Longer than `MaxCellChars` → the first 2,000
  chars (1,999 when char 1,999 (0-based) is a high surrogate) + `"…"`,
  and `truncated_cells++`.
- `SQLITE_BLOB` → `"[blob, <n> bytes]"` with `n = sqlite3_column_bytes`
  (invariant culture), never the bytes.
- `rowChars` = sum of the lengths of the string cells as returned (cut
  text including `…`, blob placeholders). Numbers, nulls, the `mailbox`
  column and column names don't count. A row is added only when the
  total stays ≤ 1,000,000.

### F. `IndexQueryAuthorizer.Decide`

Name comparisons are ordinal-ignore-case. Rules in order:

| action | rule |
|---|---|
| `SQLITE_SELECT`, `SQLITE_RECURSIVE` | allow |
| `SQLITE_READ` | the READ rules below |
| `SQLITE_FUNCTION` | `arg2` is the name. Deny `load_extension`, `fts3_tokenizer`, `readfile`, `writefile`, `edit`, and every name starting with `sqlite_` except `sqlite_version`; `What = "function " + name.ToLowerInvariant()`. `arg2` null → deny `"function (unknown)"`. Else allow. |
| `SQLITE_PRAGMA` | allow only `arg1 == "data_version"` with `arg2 == null` and `viewName == null` (FTS5 runs `PRAGMA 'main'.data_version` internally, `fts5_index.c` `fts5IndexDataVersion`; users can't reach it: `PRAGMA` is refused by the keyword pre-check and `pragma_*` table-valued functions by READ). Else deny `"PRAGMA"`. |
| `SQLITE_ATTACH` / `SQLITE_DETACH` | deny `"ATTACH"` / `"DETACH"` |
| `SQLITE_TRANSACTION`, `SQLITE_SAVEPOINT` | deny `"transactions"` |
| `SQLITE_INSERT`, `SQLITE_UPDATE`, `SQLITE_DELETE`, all `SQLITE_CREATE_*`/`SQLITE_DROP_*` (1–17), `SQLITE_ALTER_TABLE`, `SQLITE_REINDEX`, `SQLITE_ANALYZE`, `SQLITE_CREATE_VTABLE`, `SQLITE_DROP_VTABLE` | deny `"writing"` |
| anything else (incl. 0 / `SQLITE_COPY`) | deny `"action <n>"` (invariant) |

**READ rules** (`arg1` = table, `arg2` = column, may be `""` for a
table read with no column, e.g. `count(*)`):

1. `arg1` is `mail`, `mail_fts` or `mail_attachments` → allow (SQLite
   may report reads of a view's or CTE's result columns under its name;
   the real tables underneath are always checked separately by rules
   3–5, so allowing the name itself grants nothing).
2. `arg1` is `json_each` or `json_tree` → allow.
3. `arg1` is `emails_fts`, `emails_fts_data`, `emails_fts_idx`,
   `emails_fts_config` or `emails_fts_docsize` → allow, any column
   (FTS5's own statements, and the index data is derived from text the
   views expose).
4. `viewName` is `mail`, `mail_fts` or `mail_attachments` (access
   through a view):
   - `emails` with column in `ViewEmailColumns` = { `""`, `id`,
     `entry_id`, `folder`, `event_time`, `sender_name`, `sender_email`,
     `to_addrs`, `cc_addrs`, `subject`, `conversation_topic`, `body`,
     `unread`, `has_attachments`, `attachment_names` } → allow;
   - `attachments` with column in { `""`, `email_id`, `position`,
     `filename`, `size`, `is_inline` } → allow.
5. Top level / any other context: `emails` with column in
   `DirectEmailColumns` = { `id`, `subject`, `body`, `sender_name`,
   `sender_email`, `to_addrs`, `cc_addrs`, `attachment_names` } → allow
   (FTS5's external-content statements read these).
6. Otherwise deny. `What`: for `emails`/`attachments` with a non-empty
   column → `"column <table>.<column>"` (table and column lower-cased);
   otherwise `"table <arg1>"` (as given; `"table (unknown)"` when null).

Why rule 4 checks columns even inside a view (stricter than §11.12's
"allowed when the view argument is mail, …"): the view argument is the
*name* of the inner-most view or subquery, and a user CTE can take that
name — `WITH mail AS (SELECT store_id FROM emails) SELECT * FROM mail`
would otherwise read hidden columns under the "mail" context. With rule 4
a fake `mail` can only reach what the real views expose.

## Spec changes (proposed; not applied — I was told not to edit SPEC.md)

These are low-risk and reversible; please apply them to SPEC §11.12 with
this brief:

1. **Authorizer READ through a view is column-checked** (security
   tightening). §11.12 says READ is allowed whenever the view argument is
   `mail`/`mail_fts`/`mail_attachments`. That argument is a *name*, and a
   user CTE or subquery alias can take it
   (`WITH mail AS (SELECT store_id FROM emails) …`). Replace with rules
   F.1–F.6: through a view only the columns the views expose
   (`emails`: id, entry_id, folder, event_time, sender_name,
   sender_email, to_addrs, cc_addrs, subject, conversation_topic, body,
   unread, has_attachments, attachment_names; `attachments`: all five),
   plus reads named `mail`/`mail_fts`/`mail_attachments` themselves.
2. **`PRAGMA data_version` is allowed for FTS5's internal statement**
   (arg2 null, no view context). This is the "FTS5 needs one more read"
   case §11.12 foresees. User-typed `PRAGMA` stays refused.
3. **The tail check is lexical** (only whitespace, `;` and comments),
   not "prepare the tail": `sqlite3_prepare_v2` returns no statement for
   an empty `;`, so `SELECT 1; ;DROP …` would pass a single tail prepare.
4. **Leading-keyword pre-check** before prepare, mapping to `<what>`
   (`writing`, `PRAGMA`, `ATTACH`, `DETACH`, `EXPLAIN`, `transactions`,
   or `statements that don't start with SELECT, WITH or VALUES`). Needed
   because SQLite rejects `DELETE FROM mail` ("cannot modify mail
   because it is a view") before asking the authorizer.
5. **`SQLITE_LIMIT_LENGTH` 50,000,000** against `randomblob`/`zeroblob`/
   `printf` memory bombs inside the 10 s window.
6. **Texts not in §11.12:** `sql is required: one SELECT over the views mail, mail_fts and mail_attachments.`
   and `sql is longer than 20,000 characters. Shorten the query.`;
   `<mailbox>` in the unavailable text is `your own mailbox` for `""`;
   a trailing `.` of SQLite's message is dropped in `SQL error: …`.
7. **Small result rules:** `truncated`/`max_rows` only when another row
   exists, or (for `all`) when mailboxes were left unqueried; the size
   cap is row-granular (≤ 1,000,000 chars of string cells); non-finite
   reals are `null`; unavailable also covers a file without the
   `emails`/`attachments`/`emails_fts` tables (checked before the views
   are created).
