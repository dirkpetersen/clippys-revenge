# M16.11 Sent Items first in sync and an earlier first style skill

User request 2026-11-15: "Scan sent items before inbox which allows us to
create the skills sooner when we populate the database initially."
Ships in v0.1.0 with the rest of M16, but touches none of the other M16
code.

## Goal

Make the first index build useful for the writing-style skill sooner
(SPEC §10 "Folder order" and "Sent Items ready", §19.6 "Sent Items first",
§19.7 Worker). Today `SyncEngine` processes the folders in the configured
order (default `Inbox`, `Sent Items`), and each folder's backfill runs to
the end before the next folder starts, so a 12-month Inbox backfill
delays Sent Items by up to an hour. The style corpus comes from the index
(`EmailIndex.SentForStyle`), and the first automatic generation runs in
the drafting worker's `BeforePassAsync`. That pass starts on
`CycleCompleted` (after **all** mailboxes are done) or on the 15-minute
tick. The tick is the real problem: during a long first backfill it can
build the skill from a half-indexed Sent Items, or record
`writing style not updated: only 0 sent emails (need 20)` and then wait
24 h. This task:
1. processes Sent Items (and its subfolders) first in every mailbox, then
   Inbox, then the rest;
2. keeps automatic style runs waiting until the own Sent Items backfill is
   complete;
3. wakes the drafting worker the moment it completes, so the first skill
   is built before the Inbox backfill and before the shared mailboxes,
   with all the existing gates and the "never twice" guarantees.

## Hard rules that apply here

- Sync only reads (Table API, `ReadAsync`). Nothing new on the COM side,
  no App COM changes. Never send, never delete, never move.
- The style skill still uses only the own mailbox's index, never
  attachment content. Model calls are unchanged (same prompt, same
  consent, same `AutoRegenerateStyle`).
- No new settings, no new user-visible texts. The existing Activity lines
  (`Sent: backfill started, …`, `Sent: backfill complete`,
  `writing style updated from <n> sent emails (<duration>)`) just appear
  earlier.

## Behavior

### A. `SyncPlanner.ProcessingOrder`

Rank each path (ordinal comparisons on the canonical form):
- 0: exactly `FolderPaths.SentItems` (`Sent Items`)
- 1: other paths where `FolderPaths.IsUnderSentItems` is true (`Sent Items\Old`)
- 2: exactly `FolderPaths.Inbox`
- 3: everything else, including `Inbox\…`, and `Sent Items Archive`
  (its first segment isn't `Sent Items`)

Return a new list, stably sorted by rank (`OrderBy` is stable). Don't
dedupe: the engine already applies `Distinct(OrdinalIgnoreCase)` before
calling it.

### B. `SyncEngine.SyncMailboxAsync`

1. Everything before the folder loop is unchanged (retention, decisions
   purge, `OpenMailboxAsync`, meta). A `NotMounted` mailbox returns as
   today, and `sentGroup` isn't called.
2. `configured = plan.Folders.Distinct(StringComparer.OrdinalIgnoreCase).ToList()`,
   `order = SyncPlanner.ProcessingOrder(configured)`. Loop over `order`.
   The per-folder body (GetFolderAsync, state, changes, backfill,
   reconcile) is unchanged.
3. Sent group = the entries of `order` where `IsUnderSentItems`. When it
   is empty, call `sentGroup(new(plan.Mailbox, true, false))` before the
   first folder. Otherwise call it once, right after the last Sent-group
   folder is processed (after its reconcile, or right after it was found
   missing), before the next folder's `GetFolderAsync`:
   - `Complete` = every Sent-group folder was missing (`GetFolderAsync`
     returned null) or its `FolderRun.Complete` is true;
   - `FinishedNow` = `Complete` and some Sent-group run had
     `StartedIncomplete`.
   If the cycle throws or is cancelled before that point, the callback
   isn't called.
4. `results` (→ `MailboxSyncResult.Folders`) and `runs`, as used for the
   `Sync` event text, are put back in **configured** order. Collect them
   per path and emit them in `configured` order. So
   `Inbox +3, Sent +2 (0.0 s)` for plan `Inbox, Sent Items` stays as
   today. `RefreshThreadMetaAsync` may get `runs` in either order.
   `BackfillFinished` is computed as today.
5. Nothing else changes: batch size, newest first within a folder,
   watermarks, `Backfilling` labels, backfill events, purge, meta.

### C. `SyncService`

1. `SyncOneAsync` passes `OnSentGroup` to `_engine.SyncMailboxAsync`.
2. `OnSentGroup(SentGroupResult r)`: ignore it unless
   `r.Mailbox == MailboxIndexes.OwnMailbox`. Under `_lock` set
   `_ownSentComplete = r.Complete`. If `r.FinishedNow`, raise
   `OwnSentBackfillCompleted` outside the lock. Call each handler
   separately (as `RaiseCycleCompleted` does). A handler exception logs
   Warning `A OwnSentBackfillCompleted handler failed ({Type}).` (type name
   only) and the next handler still runs.
3. `RebuildAsync`: when the targets include the own mailbox, set
   `_ownSentComplete = false` together with its `Reset` (inside the gate).
4. Pause, Resume, `NotifySettingsChanged` and retention changes don't
   touch the flag. A RetentionMonths increase makes the next own cycle
   report `Complete = false` only after the re-run Sent group if it still
   isn't complete. That's acceptable, because Sent goes first.
5. The event is raised even if the cycle is aborted later. It isn't
   raised again by later cycles unless a Sent-group backfill starts
   incomplete again (Rebuild, RetentionMonths increase, a newly added
   Sent subfolder).

### D. `StyleSkill.RunIfDueCoreAsync`

The order becomes: `ct` check → `RefreshMeetingSection()` (unchanged,
still runs while waiting) → the settings/consent check → **new**: if
`_sentIndexed` is not null and returns false, return
`new StyleRunResult.NotDue()` → the `_nextAutoAttemptUtc` check → gate →
`IsDue` → … (all unchanged).
- While waiting there's no event, no log, and neither
  `_nextAutoAttemptUtc` nor `_nextRefreshCheckUtc` is touched, so the
  first pass after the flag turns true can run at once.
- If the delegate throws, the result counts as **ready** (`true`), so a
  broken delegate can never block the skill forever.
- `RegenerateAsync` ignores `_sentIndexed`.

### E. `Program.cs`

- `styleSkill = new StyleSkill(…, logger: …, sentIndexed: () => syncRef.OwnSentBackfillComplete);`
  (`syncRef` already exists above it).
- After `sync.CycleCompleted += _ => draftsRef.Wake();` add
  `sync.OwnSentBackfillCompleted += () => draftsRef.Wake();`.
- That woken pass goes through the worker's normal gates (`StartCheck`:
  Enabled + consent, sync not paused, Outlook available, no NotSignedIn
  hold) and then `BeforePassAsync` → `RunIfDueAsync`. On a fresh index the
  Inbox has no rows yet, so the rest of the pass finds no candidates. The
  later `CycleCompleted` pass finds the skill (`NotDue`). After a failed
  or too-small run, the 24 h retry applies.

## Spec changes

Made by the architect on 2026-11-15 (already in SPEC.md):
- §10: new bullets **Folder order: Sent Items first (M16.11)** and **Sent
  Items ready (M16.11)**. The cycle bullet now says "in the order above".
  Decision (low-risk, reversible): the order applies in **every** cycle,
  not only during a backfill, because the incremental passes are the same
  per folder and only their order within a cycle of a few seconds moves.
  The `Sync` event text and `MailboxSyncResult.Folders` keep the
  configured order, so no visible text changes.
- §19.6: new bullet **Sent Items first (M16.11)**. Automatic runs wait
  for `OwnSentBackfillComplete`, and `OwnSentBackfillCompleted` wakes the
  worker. Decision: the trigger is the *complete* Sent group, not a count
  threshold, so the first skill sees the full 12-month corpus (a skill
  built from a partial corpus would stay for at least 7 days).
- §19.7 Worker: a pass also starts on `SyncService.OwnSentBackfillCompleted`.
- §3 layout: `SyncModels.cs` lists `SentGroupResult` and
  `SyncPlanner.ProcessingOrder`.
