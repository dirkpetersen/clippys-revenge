# M19.6 Pipeline: attachment text in every drafting path

Base: `dev` at or after `190ff57` (M18.1–M18.6 and M19.1–M19.5 merged).
M19.6 wires M19.4's `DraftAttachments.CollectAsync` and M19.5's prompt
block and notes into `DraftWorker`. It is **Core + fakes only**: no App
file changes. M19.7 implements the COM source and wires it in `Program`.
Parallel: a reviewer reads the M18 code (read-only), and a flaky-test
fixer edits `SingleInstanceTests`, `ConnectionTesterTests`,
`IndexQueryBombTests`, `ComWorkerTests`, `TrayBadgeRendererTests` and
the `OwnSent_RebuildResetsOwnFlagOnly` test. Don't touch those files.

## Goal

When `ReadAttachments` is on and an attachment source is wired, every
drafting prompt collects attachment text right before its model call:
automatic (§19.7 step 5), manual (§19.7), revisit (§23.6 step 5, for the
reply target) and rescan (§23.8, through the same code). The collection
runs at the path's priority, inside the 20 s per-prompt budget that
`CollectAsync` already enforces. Its items go into
`DraftPromptInput.Attachments` and its notes go into the saved draft
right after the reason line. The `Draft` event gains
` (attachments: <r> read, <n> not read)`, and one Debug count line is
logged per prompt. This task also adds the settings `ReadAttachments`
(default `true`) and `AttachmentsNoticeShown`, the new consent text and
the one-time notice (an `Ai` event plus a balloon, using
`AiNotice`/`MarkNoticeShown`). It defines the per-draft
"used attachment text" flag that M20.1 checks before writing an
`ai_draft_texts` row: the user decided to skip those rows.

Extracted text, file names, URLs and paths are never logged, never
stored and never in Activity. Only counts are.

SPEC refs: §26.8 (where it runs, priority, scope, Activity and logs),
§26.10 (settings, consent, notice), §26.5 (time budget), §26.6/§26.7
(prompt and notes, M19.5), §26.1/§26.2/§26.3 (anchor, thread, sender
rule), §19.2 (settings table), §19.7 (steps 5–8, events), §19.10
(consent), §19.11 (privacy), §19.13 (call kinds and token lines are
unchanged), §23.6/§23.9 (revisit, replace event), §23.8 (rescan), §25.3
(notice pattern), §25.4 (reason line and `top`), §27.2 (the flag M20.1
reads), §26.12 (pipeline, settings and privacy tests).

## Hard rules that apply here

- **Attachment content never enters the index.** Nothing in this task
  writes attachment text, names, URLs, paths, counts or the
  used-attachment flag to SQLite, settings, logs or Activity. No schema
  change. The only new persisted values are the two booleans in
  `settings.json`.
- **Never send, never delete or move.** No new `.Send(`, `.Move(`,
  `.Display(` or `Delete(`. Drafts still go only through
  `IReplyDraftWriter`.
- Mail and attachment text are data (§19.5): they reach the model only
  through M19.5's escaped block. Notes are Clippy's text, built by
  `AttachmentNotes.Html`.
- `DraftAttachments*.cs` keep no reference to `EmailIndex` (§26.8,
  M19.4). The thread query lives in the new `DraftWorker.Attachments.cs`.

## Behavior

### A. `CollectAttachmentsAsync`

1. **Gate.** Return `AttachmentSet.Empty` at once, with no index call,
   no source call, no notice and no log, when any of these holds:
   `!ai.ReadAttachments`, `_s.Attachments is null` or `!ai.HasConsent`.
2. `AttachmentsNotice(ai)` (Behavior E).
3. `thread = index.ThreadAttachments(anchor.Topic, anchor.Time, anchor.EntryId)`
   (default 50 messages). When `excludeEntryId` is not null, drop rows
   whose `EntryId` equals it (ordinal). The revisit passes its old
   draft's id here, so Clippy's own draft is never a source.
4. `own = identity with { OwnSmtp = userSmtp }` when `userSmtp` is not
   empty, else `identity`. This way the §26.3 sender rule uses the same
   resolved address as the rest of the pass, including the index
   fallback of `UserSmtp`.
5. `request = new AttachmentRequest(key, anchor.EntryId, anchor.Subject, anchor.Body, anchor.SenderName, anchor.SenderEmail, anchor.Time, anchor.Attachments ?? [], thread, own, signatureText, priority, _s.Zone)`.
6. `set = await _s.Attachments.CollectAsync(request, ct)`.
7. Errors:
   - `OperationCanceledException` while `ct.IsCancellationRequested`:
     rethrow.
   - Any other exception, from steps 3–6 (index, plan or a bug):
     Warning `AI drafts: reading attachments failed ({Type}).` with the
     exception type name only. Return `AttachmentSet.Empty`. The draft
     goes on without attachments and there is no Debug line.
8. Debug line, once per successful collection (also with 0 items):
   `_log?.LogDebug("AI drafts: attachments {Read} read, {Truncated} truncated, {Skipped} skipped, {Links} links, {Chars} chars in {Ms} ms", c.Read, c.Truncated, c.Skipped, c.Links, c.Chars, c.ElapsedMs)`.
   Here `<r>` is `Read` only, as in §26.8. Logging is best effort:
   wrap it in `try`/`catch (Exception)`.
9. Return `set`. Nothing in this method keeps a reference to the set or
   its texts after it returns, so the set lives only as long as the
   caller's locals.

The 20 s budget, the 10 s per-file limit, one file in memory at a time,
`OutlookUnavailableException` handling and every skip reason are
`CollectAsync`'s (M19.4). The worker adds no second timer.

### B. `BuildRequestAsync` (automatic and manual)

Same steps as today's `BuildRequest`, in this order:

1. `thread = index.Thread(topic, eventTime, DraftPrompt.MaxThreadMessages, entryId)`,
   then `input = PromptInput(...)`, then `related = FindRelated(...)`,
   then `input = input with { Related = related }`. This is unchanged.
2. `set = await CollectAttachmentsAsync(ai, index, key, new AttachmentAnchor(entryId, topic, eventTime, email.Subject, email.Body, anchorSenderName, email.SenderEmail, anchorAttachments), input.SignatureText, identity, userSmtp, priority, null, ct)`.
3. `input = input with { Attachments = set.Items.Count > 0 ? set.Items : null }`.
4. System prompt: today's call with one more argument at the end,
   `attachments: DraftPrompt.HasAttachments(input)`. User prompt:
   `DraftPrompt.UserPrompt(input)`. Everything else in `ModelRequest`
   stays the same.
5. Return `new DraftPromptBuild(request, set)`.

With the gate closed, `set` is `Empty`, `Attachments` stays null and
`attachments:` is false. Both prompts are then byte-identical to M18's.

### C. Automatic path (`ProcessCandidateAsync`, and the rescan through it)

Steps 1–4 are unchanged, so the daily limit and the backoff are checked
before any attachment work. New order for step 5:

```
var detail = index.Get(c.EntryId);            // null → gone row, as today
var email  = new PromptEmail(...);            // as today
var callCt = p.CallToken ?? ct;
if (callCt.IsCancellationRequested) return DraftPassEnd.Cancelled;
if (!p.Rescan) { p.Scope ??= Begin(Drafting); p.Total++; Report(...); }   // moved up: the scope is held while collecting (26.8)
DraftPromptBuild built;
try
{
    built = await BuildRequestAsync(ai, cur, index, key, email, c.ConversationTopic ?? facts!.ConversationTopic,
        c.EventTime, c.EntryId, detail.InternetMessageId ?? factsImid, identity, userSmtp, manual: false,
        detail.SenderName, detail.Attachments, p.Priority, callCt);
}
catch (OperationCanceledException) when (callCt.IsCancellationRequested)
{
    return DraftPassEnd.Cancelled;            // no row, no call counted (like Failed(Cancelled))
}
var result = await _s.Model.RunAsync(built.Request with { Kind = … as today … }, callCt);
```

- Priority: `p.Priority`. That is `Background` in a pass and
  `Interactive` in a rescan (§26.8). Cancellation: `callCt`, so
  **Cancel rescan** also stops a collection that is running.
- Step 8: `top = ReasonTop(ai, reply.NoteForUser) + AttachmentNotes.Html(built.Attachments.Notes)`
  is passed to `MakePlan` in place of today's `ReasonTop(...)`. The
  notes appear whether `ReasonLine` is on or not.
- `Draft` event:
  `DraftTexts.DraftCreated(made.Subject) + DraftAttachmentTexts.EventSuffix(built.Attachments.Counts)`.
  For example, with subject `Re:: Budget` and counts read 2, truncated
  1, skipped 1, the text is
  `AI reply draft created: Re:: Budget (attachments: 3 read, 1 not read)`.
- `no_reply`, `low_confidence`, failures and re-check skips save no
  draft, so they get no notes and no event. Their rows are as today.
- The pass summary `Ai` event, the pass log line and the rescan log
  line are **unchanged**. They have no attachment counts, and the token
  sums are as M19.1 defined them. `ModelCallKind` is unchanged: reading
  attachments is not a separate call (§26 adds no model call).

### D. Manual path (`ManualCoreAsync`)

`BuildRequestAsync(..., manual: true, e.SenderName, e.Attachments, WorkPriority.Interactive, ct)`
with `e` = the live (COM-read) email, so the body and attachment list
are the COM-read ones (§26.1). An `OperationCanceledException` for `ct`
propagates as today. No row is written, because collection happens
before the model call. The save uses `top` with notes as in C, and the
`Draft` event gets the suffix as in C. The click-feedback balloon
(`DraftTexts.ManualDone`) is unchanged.

### E. One-time notice (`AttachmentsNotice`)

This is the §25.3 pattern, the same as `RelatedNotice`:

- Return when `!ai.ReadAttachments || ai.AttachmentsNoticeShown || !ai.HasConsent || _s.Attachments is null`.
- Return when `Interlocked.Exchange(ref _attachmentsNoticeDone, 1) != 0`
  (at most once per process).
- `_s.MarkNoticeShown?.Invoke(AiNotice.Attachments)`. An exception
  gives the Warning
  `AI drafts: couldn't save that the attachments notice was shown ({Type}).`
  and the notice still shows.
- `_s.Hub.Event(ActivityKind.Ai, DraftAttachmentTexts.Notice)` and
  `_s.Balloons.Post(DraftAttachmentTexts.Notice, BalloonKind.Info)`.
  Each is in its own `try`/`catch` (best effort).

It fires right before the first collection in the process, from any
path, while the setting is on. Users who give consent after this change
never see it, because `RecordConsent` sets the flag.

### F. Revisit (`RevisitAsync` step 5 and `ReplaceAsync`)

1. Build `thread`, `email`, `input` and `related` as today. Then, in
   the same order as in C:
   - the `callCt` check;
   - the scope with `p.Total++` and `Report` (when `!p.Rescan`);
   - `set = await CollectAttachmentsAsync(ai, s.Index, s.Key, new AttachmentAnchor(targetId, topic, detail.EventTime, detail.Subject, detail.Body, detail.SenderName, detail.SenderEmail, detail.Attachments), input.SignatureText, s.Identity, s.UserSmtp, s.Priority, t.Draft.DraftEntryId, callCt)`.
     An `OperationCanceledException` while `callCt` is cancelled gives
     `return DraftPassEnd.Cancelled`, with no revisit row and no
     attempt.
   - Then `input with { Attachments = … }` as in B.3, and
     `RevisitSystemPrompt(..., ai.ReasonLine, attachments: DraftPrompt.HasAttachments(input))`.
   - Then `RevisitUserPrompt(new RevisitPromptInput(input, …))`.
2. The anchor is the **reply target** (`targetId`/`detail`), and its
   thread rows reach up to the target's time (§26.1). Priority is
   `s.Priority`: `Background` in a pass and `Interactive` in a rescan.
3. `ReplaceAsync(..., AttachmentSet attachments, CancellationToken ct)`
   takes the set as a new parameter (place it before `ct`).
   `MakePlan(..., ReasonTop(ai, reply.NoteForUser) + AttachmentNotes.Html(attachments.Notes))`.
   The event is
   `RevisitTexts.ForReplace(move?.Status, made.Subject, DraftAttachmentTexts.EventSuffix(attachments.Counts))`,
   for example
   `AI reply draft updated (the thread moved on): Re:: Budget (attachments: 1 read, 0 not read). The old draft is in Deleted Items.`
4. `keep`, `remove` and low-confidence revisits save no draft, so they
   get no notes and no suffix. The `Removed` event is unchanged.

### G. The flag for M20.1 (§27.2)

The user decided (2026-11-15/16) that a draft whose prompt contained
attachment text gets **no** `ai_draft_texts` row. M19.6 stores
nothing. It only makes the flag available at every save:

- automatic and rescan: `built.Attachments.Counts.UsedText`, in scope
  at the `_s.Writer.ReplyAsync` call in step 8;
- manual: the same, in `ManualCoreAsync`;
- revisit replace: `attachments.Counts.UsedText` in `ReplaceAsync`.

`UsedText` is true when at least one item was `read` or `truncated`.
Items that were all skipped don't count, because no extracted text
reached the model. M20.1 writes its row only when `!UsedText`. Don't
persist the flag anywhere in M19.6.

### H. Settings and JSON

- `ReadAttachments` and `AttachmentsNoticeShown` round-trip through
  `Settings.ToJson`/`FromJson` and `Clone`. When they are missing from
  the JSON, the values are `true`/`false`.
- `SettingsEditor.Rebase`: add
  `if (l.AttachmentsNoticeShown) d.AttachmentsNoticeShown = true;` next
  to the related-mail line. Otherwise an Apply in an open Settings
  window would clear a notice that was marked meanwhile.
- The worker reads `ReadAttachments` from the `cur`/`s.Settings`
  snapshot that the candidate already uses, so the setting is live per
  candidate (§19.2: all fields are live).

### I. Privacy (what must never appear)

Logs, Activity events and balloons hold only the constant texts above,
counts and exception type names. No file name, URL, local path,
extracted text or skip reason. Nothing is written to any index file.
The `DraftAttachmentTexts.EventSuffix` output contains only digits and
constant words.

## Spec changes

These are low-risk, reversible decisions for the caller to record in
`SPEC.md`. They are not edited here.

1. **§26.8 "Where it runs"**:
   - `DraftWorkerServices.Attachments` (`DraftAttachments?`, last,
     optional). When it is null, attachments are never read and prompts
     are byte-identical to M18's. The gate is `ReadAttachments`, a
     wired source and consent.
   - Collection runs after the daily-limit and backoff checks, inside
     the `Drafting` scope (automatic step 5 now opens the scope before
     building the prompt). It runs with the path's cancellation token,
     so **Cancel rescan** stops it.
   - Cancellation during collection ends the step like
     `Failed(Cancelled)`: no row and no revisit attempt.
   - An unexpected exception (for example from the index thread query)
     logs `AI drafts: reading attachments failed (<Type>).` and the
     draft goes on without attachments.
   - The anchor's sender rule uses the pass's resolved user SMTP (the
     identity, else the index `mailbox_smtp`).
   - A revisit excludes its own old draft's entry id from the thread
     rows.
2. **§26.8 Debug line**: it is logged once per collection that ran,
   including 0 items. Its `<r>` is `read` only, unlike the event's.
   There is no line when the gate is closed or when collection failed.
3. **§26.8 event / §23.9**: the suffix is
   `DraftAttachmentTexts.EventSuffix(counts)`, `""` unless something
   was considered. In the revisit replace event it is inserted after
   the subject and before the period:
   `AI reply draft updated (the thread moved on): <subject> (attachments: <r> read, <n> not read). The old draft is in Deleted Items.`
   (`RevisitTexts.*` gain `suffix = ""`). `Removed` events and the pass
   and rescan summaries are unchanged.
4. **§26.10 notice**: it fires right before the first collection in the
   process, from any path (the §25.3 pattern), and only while a source
   is wired. `RecordConsent` sets `AttachmentsNoticeShown` together with
   `RelatedMailNoticeShown`. `MarkNoticeShown(AiNotice.Attachments)`
   sets it. `SettingsEditor.Rebase` adopts it.
   `AiNotice { RelatedMail, Attachments }`. The texts are
   `DraftAttachmentTexts.Notice` and
   `AiTabTexts.ReadAttachmentsText`.
5. **§27.2 "Drafts built from attachment text"**: decided by the user
   (skip). This replaces "pending user decision … Default until then".
   No `ai_draft_texts` row is written for a draft whose prompt had any
   `read` or `truncated` item: `AttachmentCounts.UsedText`, available at
   every save (automatic, manual, rescan, revisit replace). Skipped-only
   prompts don't count. The flag itself is never stored.
6. **§19.10**: the base consent text quoted there is still the M11
   wording. The current text (`AiConsent.Text`, M19) should be quoted
   instead, or the paragraph should point to §26.10.
