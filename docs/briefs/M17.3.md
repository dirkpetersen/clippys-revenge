## Goal

Make the one-time download links usable end to end: the new MCP tool
`attachment_link(id, filename?, position?)` saves the chosen attachment
through COM into a random `.bin` file in the user-only folder
`%LOCALAPPDATA%\ClippysRevenge\links\`, registers it in the
`AttachmentLinks` store and returns `{url, filename, size, expires_at,
curl, note}`; `GET /files/{token}` (M17.2) then serves it once. The App
gets `PrivateFolder.Ensure` (protected DACL, one full-control rule for
the current user, links/junctions refused; reused by M19.7 for
`ai-files\`), `OutlookMail.SaveAttachmentForLink` (size check before and
after `SaveAsFile`), and wiring: one store instance for the process,
start-up cleanup before the host starts, the store cleared after every
host restart (port change) and disposed at exit. Settings → Connection
gets the masked `export CLIPPY_TOKEN=…` line and a **Copy WSL token
line** button. The orchestration that doesn't need COM lives in Core
(`AttachmentLinkTool`) so it is tested on Linux. SPEC refs: §24.1 (tool,
result, annotations), §24.2 (save at link creation, folder, ACL, temp
name, cleanup), §24.3 (limits, clear on port change/restart/exit), §24.5
(token line), §24.6 (hard rules, scan), §24.7, §11.3 (selection and
errors), §13 (same host and bearer), §15 (safety scan).

## Hard rules that apply here

- **Never send / never delete email**: no `.Send(`, `.Save(`, `.Display(`,
  `.Move(` or `Delete(` on Outlook objects. The only deletes are
  `File.Delete` of Clippy's own temp file in `OutlookMail.Attachments.cs`
  and the store's `ILinkFileSystem.DeleteFile`.
- **Every file path from a tool goes through `PathPolicy`**: the tool
  takes no path. The temp path comes only from
  `AttachmentLinks.PrepareTempPath()` (which runs
  `PathPolicy.Check(Folder, [Folder], Write)` and the link check); the
  App re-checks the name with `LinkPaths.IsTempFileName` before
  `SaveAsFile`. No tool input reaches the path.
- **Attachment content never enters the index**: no link file references
  `EmailIndex`, `MailboxIndexes`, `UpsertBatch` or `SetThreadMeta`.
  Clippy never reads the bytes (`SaveAsFile` writes, `FileInfo.Length`
  measures).
- **Never log tokens, paths or file names**: no log line, activity event
  or exception message written by new code contains the link token, the
  bearer token, the temp path, the folder path, the email id or the
  attachment name. Only literals, counts, sizes, `LinkRefusal` values and
  exception type names. (Tool *error results* may name the attachment,
  as `get_attachment` does; they never contain the temp path.)
- **Private folder**: protected DACL, current user only, inherited by
  files; a folder that is a junction/symlink is refused, never followed,
  never ACL'd, never cleaned. No `icacls`, no `Process.Start`.
- **Localhost + token**: no change to `BearerAuth`, `TokenHolder`, the
  binding or `McpHttpHost`. The bearer token is never put in a tool
  result; the `curl` line reads `$CLIPPY_TOKEN`.

## Behavior

### A. `LinkTexts` additions (Core)

`ToolDescription`, exactly:

`Makes a one-time download link for one attachment of an email, for use from WSL or another shell. Use the id from search_emails; pass filename or position when the email has more than one attachment. Run the returned curl command in the shell: it saves the file in the current folder. The link works once and expires in 10 minutes. The file content is not returned to you. The shell needs CLIPPY_TOKEN set (see note in the result). To save the file on the Windows side instead, use get_attachment.`

`WslTokenLine(token)`: `ArgumentException.ThrowIfNullOrEmpty(token)`;
every char must be ASCII `A-Z a-z 0-9 - . _ ~ + / =`, else
`ArgumentException("Token must contain only letters, digits and -._~+/=.", nameof(token))`
(the message never contains the token). Returns
`"export CLIPPY_TOKEN=" + token` (no quotes; Clippy's tokens are 64 hex
chars). `MaskedWslTokenLine` = `export CLIPPY_TOKEN=••••••••`.

### B. `AttachmentLinkTool.CreateAsync` (Core), in this order

1. `id` null/blank → `McpException("id is required. Use the id from search_emails.")`
   (same text as `get_attachment`). Nothing else happens.
2. `_links.CheckCanCreate()` (count, bytes, rate; throws
   `AttachmentLinkException`). The saver is not called.
3. `var tempPath = _links.PrepareTempPath();` (ensures the private
   folder, refuses a link, `PathPolicy` check; throws `FolderUnusable`).
4. `saved = await _saver.SaveForLinkAsync(id.Trim(), filename, position, tempPath, AttachmentLinks.MaxLinkBytes, ct)`.
   On **any** exception (including `OperationCanceledException`):
   `_links.Discard(tempPath)`, then rethrow unchanged (`throw;`).
5. `var link = _links.Add(tempPath, saved.FileName, saved.Size);` — on
   refusal `Add` deletes the file and throws; let it propagate. Use
   `tempPath` (not `saved.Path`).
6. `return AttachmentLinkResult.Create(link, _port(), _tz);` — if this
   throws, `_links.TryConsume(link.Token)` and `_links.Complete(link)`
   (no orphan link), then rethrow. `_tz` = `timeZone ?? TimeZoneInfo.Local`.
7. Logging (Debug only, optional logger): on success
   `"attachment_link: link created ({Bytes} bytes, {Open} open)."` with
   `saved.Size`, `_links.OpenCount`; on an `AttachmentLinkException`
   `"attachment_link refused ({Reason})."` with `ex.Reason`. Nothing else.
   Never the id, name, url, token or path.
8. No `ActivityHub` events here: the host's tool filter already records
   `attachment_link` / `attachment_link failed` (consistent with
   §24.4's "only the tool name").

### C. COM save (App)

`OutlookMail.SaveAttachmentForLink(app, id, filename, position, tempPath, maxBytes, abandoned)`:

1. `if (!LinkPaths.IsTempFileName(Path.GetFileName(tempPath)) || !Path.IsPathFullyQualified(tempPath)) throw new ArgumentException("tempPath must be a link temp file.", nameof(tempPath));`
2. `abandoned.ThrowIfCancellationRequested()` (the caller already gave up).
3. `item = GetItem(app, id)`; `live = ReadAttachments(item)`;
   `target = AttachmentSelection.SelectOne(live, filename, position)`
   (same errors and attachment list as §11.3).
4. `if (target.Size is { } est && est > maxBytes) throw new AttachmentLinkException(LinkRefusal.TooBig, LinkTexts.TooBig(est));`
   — before `SaveAsFile`. A `null` size goes on to the save.
5. `atts = item.Attachments; att = atts[target.Position]; att.SaveAsFile(tempPath);`
   `var length = new FileInfo(tempPath).Length;`
6. `if (length > maxBytes)` → delete the file (below), throw
   `AttachmentLinkException(LinkRefusal.TooBig, LinkTexts.TooBig(length))`.
7. `if (abandoned.IsCancellationRequested)` → delete the file, throw
   `new OperationCanceledException(abandoned)`.
8. Return `new SavedAttachment(tempPath, target.FileName, length)`.
9. `catch (Exception ex) when (ex is COMException or IOException or UnauthorizedAccessException && !ComErrors.IsOutlookGone(ex))`
   → delete the file, throw
   `new McpException($"Could not save \"{target.FileName}\" for the download link ({reason}). Try again, or use get_attachment.")`
   where `reason` = `ex.Message.TrimEnd('.')` for a `COMException`, else
   `ex.GetType().Name` (IO messages contain the temp path; never put it
   in a result). Outlook-gone errors propagate unchanged (the worker maps
   them to the existing "Outlook not running" text). If the exception
   happens before `target` is known (steps 1–3), it's the existing
   `GetItem`/`SelectOne` exception and propagates unchanged.
10. `finally`: `Release(att); Release(atts); Release(item);` (existing
    `Release` helper).
11. "Delete the file" = a private static helper in this file:
    `try { File.Delete(path); } catch (Exception e) when (e is IOException or UnauthorizedAccessException) { }`.
    Receiver must be `File` (safety scan). No logging (OutlookMail has no
    logger; the Core store retries via `Discard`).
12. Nothing reads the file content; no index call.

`OutlookAttachmentLinkSaver.SaveForLinkAsync`:

```csharp
using var abandon = new CancellationTokenSource();
try
{
    await stores.EnsureResolvedAsync(WorkPriority.Interactive, ct).ConfigureAwait(false);
    return await worker.RunAsync(
        app => mail.SaveAttachmentForLink(app, id, filename, position, tempPath, maxBytes, abandon.Token),
        WorkPriority.Interactive, ct, OutlookStores.AttachmentTimeout).ConfigureAwait(false);
}
catch
{
    abandon.Cancel();   // before Core's Discard runs: a COM save still running deletes its own file (step 7)
    throw;
}
```

Why: `ComWorker.RunAsync` gives up on timeout/cancel while the COM call
may still finish later. Order "flag set → Core `Discard`" vs "save →
flag check" guarantees one of the two deletes the late file. Reading
`Token.IsCancellationRequested` after the `using` disposed the source is
safe.

### D. Wiring (`Program.cs`)

1. After the update-at-start block (after `var hub = new ActivityHub();`,
   before anything that serves requests), create **one** store for the
   process, named `attachmentLinks`:
   ```csharp
   var attachmentLinks = new AttachmentLinks(new AttachmentLinksOptions
   {
       Folder = LinkPaths.Default(Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData)).Folder,
       EnsurePrivateFolder = PrivateFolder.Ensure,
       Logger = loggerFactory.CreateLogger<AttachmentLinks>(),
   });
   attachmentLinks.CleanUpAtStart();   // before the host starts: no link exists yet, so nothing valid is deleted
   ```
   `CleanUpAtStart` never throws and logs only type names (M17.1).
   It must run before `StartHostAsync(...)` (scan checks the order).
2. `McpHostOptions`: `Links = attachmentLinks`.
3. `ConfigureServices`: in the branch where `indexes`, `mail`, `sync`
   are non-null, add
   ```csharp
   s.AddSingleton<IAttachmentLinkSaver, OutlookAttachmentLinkSaver>()
       .AddSingleton(sp => new Optional<AttachmentLinkTool>(new AttachmentLinkTool(attachmentLinks,
           sp.GetRequiredService<IAttachmentLinkSaver>(), () => hostRef?.Port ?? settings.Port,
           TimeZoneInfo.Local, loggerFactory.CreateLogger<AttachmentLinkTool>())));
   ```
   In the `else` branch: `s.AddSingleton(new Optional<AttachmentLinkTool>(null));`
   (both branches are required: `AttachmentTools` won't resolve
   otherwise, and then `get_attachment` would break too). With the index
   down, `attachment_link` answers `Optional.IndexUnavailableMessage`
   like `get_attachment` (the id resolve chain needs the index).
4. Restart = port change: the applier's `RestartServer` becomes
   `p => RestartHostAsync(host, attachmentLinks, p)`:
   ```csharp
   private static async Task<bool> RestartHostAsync(McpHttpHost host, AttachmentLinks links, int port)
   {
       try { return await host.RestartAsync(port).ConfigureAwait(false); }
       finally { links.Clear(); }   // SPEC 24.3: the URLs name the old port
   }
   ```
   Clear **after** the old host stopped, so no link made on the old port
   survives (a link made in the few ms after the new host started is
   also cleared; curl gets 404 and the model asks again, which is the
   safe side). The applier's fallback restart to the old port clears
   again; that's fine.
5. Exit: right after the `WaitBounded(... host.DisposeAsync() ...)` line,
   add `attachmentLinks.Dispose();` (stops the 60 s timer, deletes every
   file; never throws). Before drafts/sync stop. The update-handover
   path at start-up returns before the store exists, so nothing to do
   there.
6. No logging of the folder path anywhere in `Program`.

### F. `PrivateFolder.Ensure` (App)

1. Validate: `ArgumentException.ThrowIfNullOrWhiteSpace(folder)`; not
   `Path.IsPathFullyQualified` → `ArgumentException("folder must be a fully qualified path.", nameof(folder))`.
   `full = Path.TrimEndingDirectorySeparator(Path.GetFullPath(folder))`.
2. `user = WindowsIdentity.GetCurrent().User` (null →
   `UnauthorizedAccessException("The current user has no SID.")`).
3. Build `DirectorySecurity sec`: `sec.SetAccessRuleProtection(isProtected: true, preserveInheritance: false)`;
   `sec.AddAccessRule(new FileSystemAccessRule(user, FileSystemRights.FullControl, InheritanceFlags.ContainerInherit | InheritanceFlags.ObjectInherit, PropagationFlags.None, AccessControlType.Allow))`.
   Don't change the owner.
4. `File.Exists(full)` → `IOException("The private folder path is a file.")`.
5. If the folder exists: refuse a link (below). If missing:
   `Directory.CreateDirectory(parent)` for the parent (normal ACL is fine
   for `ClippysRevenge\`), then create the folder **with** the DACL in
   one step: `new DirectoryInfo(full).Create(sec)` (`FileSystemAclExtensions`).
   If that throws `IOException` because the folder appeared meanwhile,
   continue (step 6 re-checks and step 7 re-applies).
6. Refuse a link: `info.Refresh()`; `info.LinkTarget is not null` or
   `info.Attributes.HasFlag(FileAttributes.ReparsePoint)` →
   `IOException("The private folder is a junction or symbolic link.")`.
   Never call `SetAccessControl` on a link.
7. `info.SetAccessControl(sec)` (re-applied every call, so a folder that
   existed with inherited entries is fixed).
8. Verify: `acl = info.GetAccessControl(AccessControlSections.Access)`;
   require `acl.AreAccessRulesProtected`, and every rule in
   `acl.GetAccessRules(includeExplicit: true, includeInherited: true, typeof(SecurityIdentifier))`
   is `Allow`, `!IsInherited`, `IdentityReference == user`; the union of
   their rights contains `FullControl` and the union of their
   `InheritanceFlags` is `ContainerInherit | ObjectInherit`; at least one
   rule. Otherwise `UnauthorizedAccessException("The private folder's access list could not be set.")`.
9. Refuse a link once more (step 6) after verification.
10. No logging, no `Process.Start`, no `icacls`, no deletes. Messages
    never contain the path.

M19.7 will call `PrivateFolder.Ensure` for `ai-files\`; keep the API
generic (no link-specific text, no Core types).
