# M15.1 Remove sending: `send_meeting_invite` → `create_meeting_draft`, no `.Send(` anywhere

Base: `dev` at `812e024` (M13/M14 reviews done, version 0.0.7). M15.1 runs
first and alone; M15.2–M15.5 build on it. This task **removes** the send
path and leaves seams for them. It does **not** add the category (M15.2),
tracking (M15.2), `reply_to_id`/the note (M15.3), the tray list (M15.4) or
the badge (M15.5).

## Goal

Clippy stops being able to send anything. `send_meeting_invite` becomes
`create_meeting_draft`: it resolves the recipients, creates the meeting
and only ever **saves** it unsent, then tells the model that the user adds
the Teams or Zoom link and sends it in Outlook. The confirmation dialog
and everything behind it go: `InviteGate`, the confirmation queue and its
view model, `InviteConfirmForm` and its presenter,
`ActivityState.AwaitingConfirmation`, its amber tray icon and the
`InviteConfirmTimeoutSeconds` setting. `MeetingInviteMode` keeps only
`DraftOnly` (new default) and `Disabled`; a stored `Send` (or any unknown
value) loads as `DraftOnly`. The source scan changes from "exactly one
`.Send(`" to "**no `.Send(` anywhere in `src/`**". CLAUDE.md, the agent
files and README get the approved hard-rule wording.

SPEC refs: §22 intro (new hard rule), §22.1 (all of it, except
`reply_to_id`/note, which are M15.3, and `category`, which M15.2 fills),
§22.7 (Settings, `MeetingInvites`, safety-scan bullets), §1.4, §5.2
(`MeetingInviteMode`, `InviteConfirmTimeoutSeconds` rows), §6.1
(`AwaitingConfirmation` row removed), §6.6 / §11.9 / §12 `InviteGate`
(marked removed), §8 `CreateMeeting` "From M15" paragraph, §20.9 (idle
test without `AwaitingConfirmation`), §18 decision of 2026-11-14.

## Hard rules that apply here

- **Never send anything** (new wording, user-approved 2026-11-14). After
  this task `src/` contains **zero** `.Send(` calls, and no string literal
  `"Send"` that could be used for late binding. `CreateMeeting` calls
  `.Save()` only.
- **Never delete or move mail.** Unchanged. The one `item.Close(olDiscard)`
  on unresolved recipients stays (it discards an unsaved new item; it is not
  a delete).
- **Never launch Outlook.** No new COM entry points.
- **No `.Display(`** yet: `NoDisplayCalls` stays as it is (M15.4 changes it).
- Live tests never send. The live test is only adapted so it compiles and
  still checks "saved, not sent" (M15.6 extends it).

### §B Settings migration (`MeetingInviteModeJsonConverter`)

- `Read`:
  - `JsonTokenType.String`: trim; `"Disabled"` compared
    `OrdinalIgnoreCase` → `Disabled`; **every other string** → `DraftOnly`
    (`"DraftOnly"`, `"draftonly"`, `"Send"`, `"send"`, `""`, `"Bogus"`).
  - `JsonTokenType.Null` → `DraftOnly` (value-type converters receive
    null; §5.2 "null values take their defaults").
  - `JsonTokenType.Number`: pre-M15 ordinals: `2` (old `Disabled`) →
    `Disabled`; anything else (`0` old `Send`, `1` old `DraftOnly`,
    `7`, `-1`, `1.5`) → `DraftOnly`. Use `TryGetInt32`; a non-integer is
    "anything else". Clippy never writes numbers; this is only for
    hand-edited files.
  - Any other token → `throw new JsonException("MeetingInviteMode must be a string.")`
    (unchanged behaviour for garbage: the store renames the file to
    `.bad`).
- `Write`: `Disabled` → `"Disabled"`; every other value (including an
  undefined cast) → `"DraftOnly"`.
- The safe direction is deliberate: an unknown value never turns drafts
  **off** silently and never turns anything **on** that could send
  (nothing can).
- `InviteConfirmTimeoutSeconds`: the property is gone, so an old value is
  an unknown property and is ignored (STJ default; no
  `UnmappedMemberHandling`). Any value is tolerated, including `5`, `-1`,
  `"x"` or an object. `ToJson` never writes it.
- `SettingsStore.Load` doesn't rewrite the file because of a migration
  (no new warning, no `.bad`); the next `Save` writes the clean form.
- `Validate`: `if (!Enum.IsDefined(MeetingInviteMode)) Add("MeetingInviteMode", "Must be DraftOnly or Disabled.");`
  The `InviteConfirmTimeoutSeconds` bound check goes. `CopyFrom` drops the
  timeout line.

### §C `MeetingInvites.CreateDraftAsync`

Exact texts (copy verbatim):

- `InviteTexts.DisabledMessage`:
  `Meeting drafts are disabled in Clippy's Revenge. Ask the user to enable them in the tray settings (Meeting invites: Draft only), then try again.`
- `InviteTexts.Saved(mailbox)`:
  `The meeting was saved in <cal> without sending. It has no Teams or Zoom link: the user adds one in Outlook and sends the invite. It is listed in the Clippy tray under Draft invites.`
  with `<cal>` = `InviteTexts.Calendar(mailbox)`: `your calendar` when
  `mailbox` is `""`, else `the calendar of <mailbox>` (the normalized,
  lower-case SMTP).
- `InviteTexts.When(s, e)`: `$"{s:ddd} {s:M/d} {s:HH:mm}–{e:HH:mm}"`
  formatted with `CultureInfo.InvariantCulture`, U+2013 en dash, e.g.
  `Tue 11/17 13:00–14:30`; an end at midnight is `00:00`.
- `InviteTexts.SavedEvent(n, s, e)`:
  `meeting draft saved for <n> attendees: <When>`; for `n == 1`
  `meeting draft saved for 1 attendee: <When>` (see Spec changes).
- `InviteTexts.NotCreatedEvent(reason)`: `meeting draft not created: <reason>`.
- `InviteTexts.ToolDescription`:
  `Saves a meeting unsent in the calendar. Nothing is sent: Clippy can't add a Teams or Zoom link, so the user opens the meeting in Outlook, adds the link and sends the invite there. Times are local. To book option N of a find_free_times result, or of the times offered in a draft, pass that option's start and end; the option lines show a date without a year, so use the next occurrence of that date. Every recipient must resolve in Outlook or nothing is created. With mailbox, the meeting is saved in that shared mailbox's calendar (delegate or editor rights needed).`
  (M15.3 appends the `reply_to_id` sentence.)

Flow:

1. `var mode = settings().MeetingInviteMode;` If `mode != DraftOnly`
   (i.e. `Disabled`, or an undefined value: fail closed): record one
   event `NotCreatedEvent(DisabledReason)` with `mailbox: null` and throw
   `new McpException(InviteTexts.DisabledMessage)`. This happens before
   argument validation (invalid arguments still get the Disabled message).
2. `MeetingRequest.Create(recipients, subject, start, end, body, location, mailbox, timeZone, _time.GetUtcNow())`.
   `ctx.Mailbox = req.Mailbox.Length > 0 ? req.Mailbox : null`.
3. `var r = await calendar.ResolveAsync(req, ct)`. If `r.Unresolved.Count > 0`
   → `throw new McpException(InviteTexts.Unresolved(r.Unresolved))`
   (nothing created).
4. `var m = await calendar.CreateAsync(req, CancellationToken.None)`: once
   resolution is done, creation runs to completion even if the caller
   cancels (same as today; a half-created item is worse than a finished
   draft). No mode re-read.
5. Record one event `SavedEvent(r.Attendees.Count, req.Start, req.End)`
   with `mailbox: ctx.Mailbox`; mark recorded. No balloon, no
   notification (the class no longer takes a `BalloonCenter`).
6. Return:
   ```csharp
   new MeetingDraftResult
   {
       Message = InviteTexts.Saved(req.Mailbox),
       Subject = req.Subject,
       Start = Fmt(req.Start), End = Fmt(req.End),            // yyyy-MM-ddTHH:mm:sszzz, as today
       Mailbox = req.Mailbox,                                  // "" for the own calendar
       Organizer = Recipients.Format([new Recipient(r.OrganizerName, r.OrganizerEmail)]),
       Recipients = Recipients.Format(r.Attendees.Select(a => new Recipient(a.Name, a.Email))),
       Category = null,                                        // M15.2
       EntryId = m.EntryId, StoreId = m.StoreId,
   };
   ```

Exactly **one** `ActivityKind.Invite` event per call (bold in Activity,
unchanged `ActivityView` rule). Failure handling wraps steps 2–5 like
today's `Ctx`:
- `OperationCanceledException` before the event was recorded →
  `NotCreatedEvent(CancelledReason)`, rethrow.
- Any other exception before the event was recorded →
  `NotCreatedEvent(TrayText.Truncate(ex.Message, 200))`, rethrow the
  same exception.
- After step 5 nothing records a second event (M15.2/M15.3 failures go
  into the result, not into an exception).
- Event summaries never contain the body or location.

### §D `OutlookCalendar.CreateMeeting(app, req)`

Same item building as today (shared vs own calendar, `olMeeting`,
subject, start, end, location, body, `olRequired` recipients,
`ResolveAll()`; on failure collect names, `item.Close(olDiscard)`, throw
`McpException(InviteTexts.Unresolved(bad))`). Then:

```csharp
item.Save();          // the only call; there is no switch and no decision any more
```

All of that stays inside the existing `try { … } catch (Exception ex) when (shared && IsAccessFailure(ex)) { throw new McpException(InviteTexts.NoCalendarRights(req.Mailbox)); }`.

**After** that inner try (still inside the outer `try/finally` that
releases COM objects), read the ids in their own guard so a read failure
after a successful save is never reported as "no calendar rights":

```csharp
string entryId = "", storeId = "";
Outlook.MAPIFolder? parent = null;
try
{
    entryId = item.EntryID ?? "";
    if (folder is not null) storeId = folder.StoreID ?? "";
    else { parent = item.Parent as Outlook.MAPIFolder; storeId = parent?.StoreID ?? ""; }
}
catch (COMException ex) when (!ComErrors.IsOutlookGone(ex)) { }   // saved; ids unknown
finally { if (parent is not null) Marshal.ReleaseComObject(parent); }
return new CreatedMeeting(entryId, storeId);
```

(Use whatever local names fit; the shape matters: ids read after
`.Save()`, failures other than "Outlook is gone" swallowed, `Parent`
released.) If `item.Parent` is not a `MAPIFolder`, release it anyway
(`Marshal.IsComObject` guard) and leave `storeId` empty.

Update the method's doc comment: no mention of sending, InviteGate or
confirmation. M15.2 will set `item.Categories` right before
`item.Save()`; leave that line free (no comment placeholder needed).

`ResolveInvite`: return `new ResolvedInvite(orgName, orgEmail, attendees, unresolved)`;
