# M7.2 `get_attachment`, `save_attachments` (PathPolicy, UniquePath, inline handling)

## Goal

Add the two attachment export tools (SPEC §11.3, §11.4, the §11 "File
paths" rule, §8 `SaveAttachment` / `IsInline`, §12 `FileNames.UniquePath` and
`PathPolicy.Check`, §1 "attachment content is never stored", §5.1 default
`AttachmentDir`, §5.2 `AllowedFolders`). `get_attachment` saves one attachment
of one email, read live through COM. `save_attachments` runs the
`search_emails` filters against the index, picks the attachments to save
from the indexed metadata, and saves each one live through COM into one
folder. Duplicate names get `name (2).ext`. Every `save_dir` goes through
`PathPolicy` (Write mode, relative to `AttachmentDir`). A refusal records a
`Blocked` event and returns an error naming the allowed folders. All
selection, planning, path and result logic lives in Core behind
`IAttachmentSaver`, so it is tested on Linux with a fake saver. The App only
adds the COM saver and the thin tool class. Attachment bytes go only to the
chosen file on disk. They never go into the index, a log, an event or a tool
result.

## Behavior

### A. `AttachmentSelection`

**A1. `SelectOne(attachments, filename, position)`.** `filename` is
trimmed, and blank means not given. Names compare with
`StringComparison.OrdinalIgnoreCase` on the whole `FileName`. `<list>` is
`Describe(attachments)` and `<n>` is `attachments.Count`. Exact messages:

1. Empty list → `This email has no attachments.`
2. `position` given and no attachment has that `Position` (this includes
   `position <= 0`) →
   `There is no attachment at position <p>. This email has <n> attachment(s): <list>.`
3. `position` and `filename` both given, and the name at that position
   differs →
   `The attachment at position <p> is "<actual>", not "<filename>". Pass only one of filename and position, or matching values.`
4. Only `position` → that attachment (inline or not).
5. Only `filename`: no match →
   `This email has no attachment named "<filename>". Its attachments: <list>.`
   More than one match →
   `<k> attachments are named "<filename>" (positions <p1>, <p2>, …). Pass position to choose one.`
   One match → that attachment (inline or not).
6. Neither given: if exactly one attachment is not inline, return it.
   Otherwise, if the list has exactly one attachment (it is inline),
   return it. Otherwise →
   `This email has <n> attachments. Pass filename or position to choose one: <list>.`

All of these are `McpException`. `attachments` null → `ArgumentNullException`.

**A2. `SelectForBulk(attachments, attachmentName, attachmentExt, includeInline)`.**
An attachment is kept when **all** of these hold for that same attachment:

- `includeInline` is true, or `IsInline` is false.
- `attachmentName` (trimmed) is blank, or `FileName` contains it, with
  **ASCII-only** case folding (`A`–`Z` ≈ `a`–`z`, every other character
  exact). This is the same match as the index's SQLite `LIKE`. `%`, `_` and
  `\` are plain characters.
- `attachmentExt` (trimmed, one leading `.` removed) is blank, or
  `FileName` ends with `"." + ext`, with ASCII-only case folding.

The result is ordered by `Position`.

**A3. `MatchLive(live, wanted)`.** Return the live entry with the same
`Position` when its `FileName` equals `wanted.FileName`
(`OrdinalIgnoreCase`). Otherwise return the single live entry with that
`FileName`, if there is exactly one. Otherwise return null. This protects
against the index being stale: it never saves an attachment other than the
one the plan picked.

**A4. `Describe`.** Entries are in position order, formatted
`<position> "<FileName>"`, with ` (inline)` appended for inline ones and
joined with `, `. After `MaxListed` entries, append `, … (<rest> more)`.
An empty list gives `(none)`.

### B. `AttachmentExport`

**B1. `ResolveSaveDir(saveDir, toolName)`.** Read `settings()` once per call
(settings are live, SPEC §5.2).

- `path` = the trimmed `saveDir`, or `s.AttachmentDir` when `saveDir` is
  null or blank. Even the default goes through `PathPolicy`.
- `PathPolicy.Check(path, s.EffectiveAllowedFolders(), PathMode.Write, relativeTo)`.
  `relativeTo` is `s.AttachmentDir` when that is fully qualified, otherwise
  null (a relative `save_dir` is then refused).
- `PathNotAllowedException ex` → first
  `hub.Event(ActivityKind.Blocked, $"{toolName} refused save_dir \"{shown}\": {PathPolicy.Describe(ex.Reason)}")`,
  where `shown` is `path` cut to `MaxShownPathLength` characters. Then
  throw `new McpException(ex.Message)`. Its text already names the allowed
  folders.
- `IOException` or `UnauthorizedAccessException ex` → no event; throw
  `McpException($"Could not use save_dir \"{shown}\": {ex.Message}")`.
- Return the full path that `Check` returned. The folder exists at that
  point, because Write mode creates it.

**B2. `GetAsync(id, filename, position, saveDir, ct)`.**

1. If `id` is null or blank → `McpException("id is required. Use the id from search_emails.")`.
   This is checked before the path check.
2. `dir = ResolveSaveDir(saveDir, "get_attachment")`. This happens before
   any COM work.
3. `saved = await saver.SaveOneAsync(id.Trim(), filename, position, dir, ct)`.
   Exceptions propagate.
4. Return `new GetAttachmentResult(saved.Path, saved.FileName, saved.Size)`.

**B3. `SaveAsync(args, ct)`.** `args` null → `ArgumentNullException`.

1. `dir = ResolveSaveDir(args.SaveDir, "save_attachments")`, first.
2. `filter = args.Search.ToFilter(tz)`. A date error becomes an
   `McpException`.
3. `hits = indexes.Search(filter, args.Search.Mailbox)`. Its `McpException`
   (unknown mailbox) propagates. `all` is allowed.
4. Plan: for each hit, in result order,
   `wanted = SelectForBulk(hit.Email.Attachments, args.Search.AttachmentName, args.Search.AttachmentExt, args.IncludeInline)`.
   Keep only hits whose `wanted` is not empty.
5. Execute the plan in order, one `saver.SaveManyAsync(hit.Email.Id, wanted, dir, ct)`
   per email, **sequentially** (never in parallel):
   - Each returned outcome goes to `saved` or `failed`, using that hit's
     `Id` and `Mailbox` and the requested `Position` and `FileName`.
   - `OutlookUnavailableException ex`: this email's wanted entries and
     **every remaining planned entry** go to `failed` with `ex.Message`.
     Stop. Don't call the saver again.
   - `OperationCanceledException` propagates.
   - Any other exception `ex`: this email's wanted entries go to `failed`
     with `ex.Message`. Continue with the next email.
6. `count = saved.Count`. `note`:
   - no hits → `No emails matched the filters.`
   - hits, but an empty plan →
     `<n> email(s) matched, but none had attachments to save. Inline attachments are skipped unless include_inline is true.`
   - otherwise null.

The result never contains attachment content. Only names, paths, sizes and
error texts go in it.

### C. App: `OutlookMail` attachment members (worker thread only)

**C1. `SaveAttachment(app, id, filename, position, dir)`:**
`item = GetItem(app, id)`, then `live = ReadAttachments(item)` (or M5.3's
reader), then `target = AttachmentSelection.SelectOne(live, filename, position)`,
then `SaveOne(item, target, dir)`. Release `item` in `finally`.

**C2. `SaveAttachments(app, id, wanted, dir)`:** open the item once and
read `live` once. For each wanted entry: `m = MatchLive(live, w)`. When it
is null, the outcome's error is
`Attachment "<w.FileName>" (position <w.Position>) is no longer on this email. It may have changed since it was indexed; run search_emails again.`
Otherwise `SaveOne(item, m, dir)`. A save failure becomes that entry's
error outcome, and the loop continues. Release `item` in `finally`.

**C3. `SaveOne(item, target, dir)`:**

- `path = FileNames.UniquePath(dir, target.FileName)` is computed **here,
  on the worker thread, immediately before `SaveAsFile`**. All saves are
  serialized on the one worker thread, so two tool calls can't pick the
  same free name. Never overwrite an existing file.
- `att = item.Attachments[target.Position]`, then `att.SaveAsFile(path)`.
  `size = new FileInfo(path).Length`. Return
  `new SavedAttachment(path, target.FileName, size)`.
- On `COMException`, `IOException` or `UnauthorizedAccessException`
  (except the "gone" HRESULTs, which must propagate so the worker can
  report `OutlookUnavailable` (M5.1). Use M5.1's `ComErrors` helper to tell
  them apart): best-effort delete `path` if it now exists (we created it),
  then fail with `Could not save "<FileName>": <ex.Message>`. That is an
  `McpException` in C1 and an error outcome in C2.
- Release `att` and the `Attachments` collection in `finally`, and release
  every `Attachment` read while listing inside the loop (CLAUDE.md
  conventions).

**C4. Live list (`ReadAttachments`, only if M5.3 doesn't expose one):**
COM indexes 1..`Count`. For each attachment, `new AttachmentInfo(att.Index, att.FileName ?? "", att.Size, mail.IsInline(att, …))`,
with the same inline rule as `ReadForIndex` (§8). Positions must match
what `ReadForIndex` stores, otherwise `MatchLive` fails on everything.

**C5. `ItemNotFoundException`** (when not already an `McpException`) →
`McpException($"Email \"{id}\" was not found in Outlook. It may have been deleted; run search_emails again to get a current id.")`.
`OutlookAttachmentSaver` does this mapping.

## Spec changes (proposed)

Don't edit SPEC.md in this task. The orchestrator applies these. Append to
§11.3, after "`save_dir` must pass `PathPolicy`.":

> Details (M7.2): `save_dir` defaults to `AttachmentDir`. Selection: `position` is the 1-based attachment index; `filename` matches the whole file name case-insensitively. If both are given they must agree. With neither, the single non-inline attachment is used (or the only attachment); otherwise the error lists the attachments (`1 "report.pdf", 2 "image001.png" (inline)`) and asks for `filename` or `position`. Inline attachments can be fetched by name or position. The file is saved with `FileNames.UniquePath` (never overwrites); `filename` in the result is the attachment's original name and `size` the bytes written.

Append to §11.4, after "Returns `{saved[], failed[], count}`.":

> Details (M7.2): `limit` (clamped 1–200) and `offset` count **emails**, as in `search_emails`. An attachment is saved when it matches `attachment_name` and `attachment_ext` itself (same matching as search) and is not inline, unless `include_inline=true`. Emails are saved one after another, newest first, into one folder. `saved[]` entries are `{id, mailbox, position, filename, path, size}`, `failed[]` entries `{id, mailbox, position, filename, error}`, and `count` is the number saved. A per-email or per-attachment failure goes to `failed[]` and the rest continue; when Outlook becomes unavailable, all remaining attachments are reported as failed with that message. An attachment that no longer matches its indexed name and position is not saved. The result also has `note`, set when nothing matched or nothing was eligible.

Append to §3, under `src/ClippysRevenge.Core/`:

> `AttachmentSelection.cs` (get_attachment / save_attachments selection rules), `AttachmentExport.cs` (save-dir policy, bulk save loop over `IAttachmentSaver`), `SearchArgs.cs` (tool args → `SearchFilter`). Under App: `AttachmentTools.cs` (the two attachment tools), `OutlookMail.Attachments.cs` (partial: `SaveAttachment`).
