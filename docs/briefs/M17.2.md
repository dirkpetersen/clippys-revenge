# M17.2 Endpoint: `GET /files/{token}` in `McpHttpHost`

Base: `dev` at or after `734464d` (M17.1 merged: `AttachmentLinks.cs`,
`AttachmentLinks.Helpers.cs`, the `/files/` mask in `LogRedactor`).
Pure Core plus tests. No App change: M17.3 builds the store, passes it
to the host, clears it on port change/restart/exit and adds the tool.
Parallel work: M19.1–M19.3 and M20.3 don't touch the files below.

## Goal

Serve one-time attachment downloads on the existing Kestrel host:
`GET /files/{token}` behind the unchanged `BearerAuth` (loopback only,
constant-time bearer compare, `Origin` → 401), so a download needs both
the bearer token and the link token. The link is used up atomically
(`AttachmentLinks.TryConsume`) only after auth passed, the whole file is
streamed with the pinned headers (no `Range`, no HEAD), and the temp file
is deleted afterwards whatever happened. ASP.NET Core's own log
categories are capped at Warning so the token in the request path never
reaches a log at any level; Clippy's own lines name only outcomes and
sizes. SPEC refs: §24.4 (whole section), §24.3 (single use, 401 doesn't
use the link up), §24.5 (both tokens), §24.6 (no index references, no
token/path/name in logs), §24.7 (endpoint tests), §13 (bearer rules,
"Download links" bullet), §5.1 (log redaction).

## Hard rules that apply here

- **Localhost-only and token-gated**: the route is mapped on the same
  `WebApplication` after `app.UseBearerAuth()`; nothing in this task
  changes `BearerAuth`, `TokenHolder`, the binding or `ValidateBindings`.
  No second listener, no CORS, no `WWW-Authenticate`.
- **Never log the token**: no log line, activity event or exception
  message written by this code contains the link token, the bearer
  token, the temp path or the attachment's file name. Only literals,
  byte counts and exception type names.
- **Attachment content never enters the index**: `FilesEndpoint.cs` has
  no reference to `EmailIndex`, `MailboxIndexes`, `UpsertBatch` or
  `SetThreadMeta` (M17.3's scan will check this file by name).
- **Never delete email**: the only delete is the store's own
  `Complete(link)` → `ILinkFileSystem.DeleteFile` of Clippy's temp file.

```csharp
// FilesEndpoint.cs
namespace ClippysRevenge.Core;

/// <summary>GET /files/{token} (SPEC 24.4). Mapped by McpHttpHost after UseBearerAuth, so only authorized requests
/// reach it. Logs and events never hold the token, the temp path or the file name.</summary>
public static class FilesEndpoint
{
    public const string Route = AttachmentLinks.FilesPath + "/{token}";   // "/files/{token}"
    public const string DownloadEvent = "attachment download";
    public const string DownloadFailedEvent = "attachment download failed";
    public const string AllowedMethod = "GET";
    public const int CopyBufferSize = 81_920;

    /// <summary>endpoints.Map(Route, ctx => HandleAsync(ctx, links, hub, time, logger)) — the RequestDelegate
    /// overload (all methods; the handler answers 405 itself). Called once, from McpHttpHost.Build.</summary>
    /// <exception cref="ArgumentNullException">endpoints, hub or time is null.</exception>
    public static IEndpointConventionBuilder Map(IEndpointRouteBuilder endpoints, AttachmentLinks? links,
        ActivityHub hub, TimeProvider time, ILogger? logger);

    /// <summary>Behavior B. Never throws (every failure becomes 404, 405 or an aborted connection).</summary>
    internal static Task HandleAsync(HttpContext context, AttachmentLinks? links, ActivityHub hub,
        TimeProvider time, ILogger? logger);
}
```

In `McpHttpHost.Build`, the logger is
`app.Services.GetRequiredService<ILoggerFactory>().CreateLogger(typeof(FilesEndpoint))`
(category `ClippysRevenge.Core.FilesEndpoint`, so it is *not* capped by
the `Microsoft.AspNetCore` filter and its Debug lines appear when the
user's log level allows).

## Behavior

### A. Host changes (`McpHttpHost.Build`)

1. Directly after `_options.ConfigureLogging?.Invoke(builder.Logging);`
   add
   `builder.Logging.AddFilter("Microsoft.AspNetCore", LogLevel.Warning);`
   (a general rule for every provider, so ASP.NET Core and Kestrel
   categories log nothing below Warning whatever minimum level the app or
   a test sets; it is added after `ConfigureLogging` so it applies to the
   providers registered there). No provider-specific rule is added.
2. Pipeline order stays: `app.UseBearerAuth(); app.MapMcp(McpPath);` then
   `FilesEndpoint.Map(app, _options.Links, hub, time, filesLogger);`.
   `WebApplication` runs routing first and endpoints last, so `BearerAuth`
   rejects (401) before the handler can run and a 401 never reaches
   `TryConsume`.
3. The route is always mapped (also when `Links` is null). `/files/...` is
   mapped exactly once in the codebase.
4. The host never calls `Links.Clear()`/`Dispose()`; clearing on port
   change, restart and exit is M17.3's wiring.

### B. The handler (`FilesEndpoint.HandleAsync`)

1. **Method.** `!HttpMethods.IsGet(request.Method)` (POST, PUT, DELETE,
   PATCH, HEAD, OPTIONS, anything) → status 405, `ContentLength = 0`,
   header `Allow: GET`, return. The store is not touched, so the link
   stays usable.
2. **Token.** `var token = context.Request.RouteValues["token"] as string;`
   `var link = links?.TryConsume(token);` (it already rejects anything
   that isn't 43 chars of `[A-Za-z0-9_-]`, unknown, used or expired, and
   deletes an expired link's file). `link is null` → 404,
   `ContentLength = 0`, return. Query string and request headers other
   than auth are ignored. No event, no log line.
3. **Open.** `new FileStream(link.TempPath, FileMode.Open, FileAccess.Read,
   FileShare.Read, CopyBufferSize, FileOptions.SequentialScan | FileOptions.Asynchronous)`.
   `IOException` (incl. `FileNotFoundException`,
   `DirectoryNotFoundException`) or `UnauthorizedAccessException` → log
   Debug `Attachment download: the link's file is missing or unreadable ({Type}).`
   (type name), 404 with `ContentLength = 0`, then `links.Complete(link)`
   (deletes whatever is left; retry rule), return. The link stays used
   up. No event.
4. **Send.** `var start = time.GetTimestamp();` then, inside
   `using (hub.Begin(ActivityState.Serving, DownloadEvent))`:
   - `StatusCode = 200`; for each pair of
     `FileDownloadHeaders.Build(link.FileName, stream.Length)` set
     `context.Response.Headers[key] = value` (Content-Type,
     Content-Disposition, Content-Length, X-Content-Type-Options,
     Cache-Control; exactly those, in that order). No `Accept-Ranges`,
     `ETag`, `Last-Modified` or `Content-Range`. `Range`/`If-Range`
     request headers are never read: always the whole file with 200. No
     `Results.File`, `SendFileAsync`, `UseStaticFiles` or anything else
     that does range or conditional processing.
   - set a local `started = true`, then
     `await stream.CopyToAsync(context.Response.Body, CopyBufferSize, context.RequestAborted);`
     and `await context.Response.CompleteAsync();`
   - On success: `hub.Event(ActivityKind.Tool, DownloadEvent, time.GetElapsedTime(start))`
     and log Debug `Attachment download completed ({Bytes} bytes).` with
     `stream.Length`.
5. **Failure** (`catch (Exception ex)` around 4; nothing is rethrown):
   - `hub.Event(ActivityKind.Tool, DownloadFailedEvent, time.GetElapsedTime(start))`;
     log Debug `Attachment download failed ({Type}).` (type name only;
     never `ex.Message`, never the exception object, since Kestrel
     messages can echo the request).
   - `started` true → `context.Abort()` (the client sees a broken
     transfer; `curl -f` fails instead of saving a short file).
     `started` false (failure while setting headers) → if
     `!context.Response.HasStarted`: `Response.Clear()`, 404,
     `ContentLength = 0`; else `context.Abort()`.
6. **Finally** (always, after 3 succeeded): dispose the stream, then
   `links.Complete(link)` (deletes the temp file; a failed delete is the
   store's retry). So the file is gone after a completed, aborted or
   failed download.
7. Hub and logger calls are each wrapped so a throwing hub/logger (e.g. a
   disposed `ActivityHub`) can't break the download or skip step 6.
8. 401 (BearerAuth), 404 and 405 record no activity event.
9. Nothing in this file reads or writes settings, the index, COM or the
   bearer token.

### C. Routing edge cases (by construction, no extra code)

- `/files`, `/files/`, `/files/a/b` → no route match → the framework's
  404 with an empty body (after auth).
- Path segments are URL-decoded by routing before `TryConsume`; anything
  that isn't exactly the 43-char token is 404.

## Spec changes

Low-risk, reversible decisions made here; not applied by this brief
(another architect is editing `SPEC.md`). Add to §24.4:

1. The 405 response also carries `Allow: GET` (empty body, as before).
2. The handler is `FilesEndpoint` (Core, `FilesEndpoint.cs`), mapped
   with `Map` (all methods) after `UseBearerAuth`; the store reaches the
   host as `McpHostOptions.Links` (null → always 404). The host never
   clears the store; clearing on port change/restart/exit is wiring
   (M17.3).
3. The temp file is opened *after* the link is consumed; when it is
   missing or unreadable the answer is 404, the link stays used up, and
   no event is recorded.
4. While streaming, the host holds a `Serving` scope labelled
   `attachment download` (the tray shows activity like a tool call).
5. A failure after the headers are sent aborts the connection (so
   `curl -f` reports an error instead of keeping a short file) and
   records `attachment download failed`; a failure before that answers
   404.
6. The log cap is `builder.Logging.AddFilter("Microsoft.AspNetCore", LogLevel.Warning)`
   after the app's logging configuration. Clippy's own lines (Debug,
   category `ClippysRevenge.Core.FilesEndpoint`):
   `Attachment download completed (<n> bytes).`,
   `Attachment download failed (<Type>).`,
   `Attachment download: the link's file is missing or unreadable (<Type>).`
7. §3 layout: `FilesEndpoint.cs` (Core, §24.4).
