# M1.5 `PathPolicy` + tests

## Goal

Implement `PathPolicy.Check` in Core (SPEC §1 rule 8, §11 "File paths",
§12 `PathPolicy`, §15 `PathPolicy` row). It is the single gate every
tool file path goes through: it normalizes the path, refuses device/UNC
forms, alternate data streams and paths outside the allowed folders
(separator-boundary, case-insensitive), refuses junctions and symlinks
below the matched root, and applies `Read` (existing file) or `Write`
(folder, created if missing) semantics. Pure .NET, no Windows APIs, so the
class and almost all tests run on Linux. Only the junction test and the
drive-relative test are Windows-only.

## Cross-task dependencies

None. `PathPolicy` takes the allowed roots as a plain list. Where the list
comes from (`Settings.AllowedFolders` + `AttachmentDir`, M1.7) and turning
the exception into an `McpException` plus a `Blocked` event (M7.2, M7.3)
are not part of this task. Don't reference `Settings`, `FileNames` or
`ActivityHub`.

## Public API

```csharp
namespace ClippysRevenge.Core;

public enum PathMode { Read, Write }

public enum PathRejectReason
{
    Empty,
    InvalidCharacters,
    DeviceOrUnc,
    AlternateDataStream,
    NotFullyQualified,
    ReservedDeviceName,
    NoAllowedFolders,
    OutsideAllowedFolders,
    LinkBelowRoot,
    Inaccessible,
}

public sealed class PathNotAllowedException : Exception
{
    public PathNotAllowedException(string? path, PathRejectReason reason, IReadOnlyList<string> allowedRoots);
    public string? RequestedPath { get; }           // the raw input, as given
    public PathRejectReason Reason { get; }
    public IReadOnlyList<string> AllowedRoots { get; } // normalized roots (see Behavior 8)
}

public static class PathPolicy
{
    /// Returns the normalized full path.
    /// Throws PathNotAllowedException (policy refusal),
    ///        FileNotFoundException (Read: missing, or is a folder),
    ///        IOException (Write: path exists as a file; or CreateDirectory fails),
    ///        ArgumentNullException (allowedRoots is null),
    ///        ArgumentException (relativeTo is given but not fully qualified).
    public static string Check(string? path, IReadOnlyList<string> allowedRoots,
                               PathMode mode, string? relativeTo = null);

    /// Human-readable text for a reason (used in the exception message).
    public static string Describe(PathRejectReason reason);
}
```

`relativeTo` exists so M7.2 can pass `AttachmentDir` for relative
`save_dir` values (§11 "Relative `save_dir` values resolve under
`AttachmentDir`") without duplicating the resolution logic.

## Behavior

Checks run in this order. The first failing check decides `Reason`, so the
tests can assert exact reasons.

1. `path` null, empty or whitespace → `Empty`.
2. Any char `< 0x20` (including NUL) → `InvalidCharacters`.
3. The first two chars are each `\` or `/` (covers `\\server\share`,
   `\\?\`, `\\.\`, `//server/share`, `\/`) → `DeviceOrUnc`. This is a
   string check and applies on every OS.
4. A `:` anywhere except index 1, or a `:` at index 1 when char 0 is not
   an ASCII letter → `AlternateDataStream` (covers `file.txt:stream`,
   `file.txt::$DATA`, `\??\C:\x` after normalization). Applies on every OS.
5. Resolve:
   - `Path.IsPathFullyQualified(path)` → `full = Path.GetFullPath(path)`.
   - Else if `Path.IsPathRooted(path)` (`\foo`, `C:foo` on Windows) →
     `NotFullyQualified`. Never resolve these against a current directory.
   - Else (relative): if `relativeTo` is null → `NotFullyQualified`;
     otherwise `relativeTo` must be fully qualified (else
     `ArgumentException`) and `full = Path.GetFullPath(path, relativeTo)`.
     The result still has to pass every check below; `..\..\x` relative to
     `AttachmentDir` is refused by step 9 when it lands outside.
   - Never call `Path.GetFullPath(string)` on a non-fully-qualified path
     (it would use the process current directory).
6. Re-run checks 3 and 4 on `full`. Then trim trailing separators from
   `full` unless it is a filesystem root (`C:\`, `/`).
7. Any path component of `full` whose name, up to the first `.` and with
   trailing spaces trimmed, equals (case-insensitive) `CON`, `PRN`, `AUX`,
   `NUL`, `COM0`–`COM9` or `LPT0`–`LPT9` → `ReservedDeviceName`. Applies on
   every OS (the app only runs on Windows; doing it everywhere keeps it
   testable on Linux).
8. Normalize the roots: skip null/whitespace entries, and skip entries that
   are not fully qualified or start with two separators (rule 3). Apply
   `Path.GetFullPath`, then trim trailing separators unless the entry is a
   filesystem root. Remove duplicates (case-insensitive). If none are left
   → `NoAllowedFolders`. `AllowedRoots` on the exception is this
   normalized list, also for reasons found before step 8. Compute it
   up front, but only *throw* `NoAllowedFolders` at this step.
9. Matching uses `StringComparison.OrdinalIgnoreCase`. A root matches when
   `full` equals it, or when `full` starts with `root + separator`. For a
   filesystem root that already ends in a separator, use the root as it
   is. `C:\Docs2` and `C:\Docs2\x` do **not** match `C:\Docs`. If more than
   one root matches, use the **longest**. No match →
   `OutsideAllowedFolders`.
10. Link walk: for each component **below** the matched root, from the
    shallowest down to `full` itself (the root itself is not checked; the
    user chose it and it may be a junction, e.g. Documents redirected to
    OneDrive):
    - `FileSystemInfo info = Directory.Exists(p) ? new DirectoryInfo(p) : new FileInfo(p);`
    - If `info.LinkTarget is not null` → `LinkBelowRoot`. This catches
      symlinks (file and directory), junctions/mount points and **dangling**
      links. Check it before `Exists`.
    - Else if `!info.Exists` → stop (deeper components can't exist).
    - `IOException` / `UnauthorizedAccessException` while inspecting →
      `Inaccessible` (fail closed).
    - Use `LinkTarget`, not `FileAttributes.ReparsePoint`. OneDrive
      Files-On-Demand placeholders and dedup files are reparse points but
      not links, and refusing them would break attaching files from a
      OneDrive-backed Documents folder (see Spec changes).
11. Mode:
    - `Read`: if `Directory.Exists(full)` →
      `FileNotFoundException($"'{full}' is a folder, not a file.")`; if
      `!File.Exists(full)` →
      `FileNotFoundException($"File not found: '{full}'.")`. Set `FileName`
      to `full` in both cases. Otherwise return `full`.
    - `Write`: if `File.Exists(full)` →
      `IOException($"'{full}' is a file, not a folder.")`. Otherwise
      `Directory.CreateDirectory(full)` and return `full`. Don't catch
      exceptions from `CreateDirectory`. Don't re-walk afterwards, because
      only folders that didn't exist were created.

`PathNotAllowedException.Message` is exactly:

```
Path '{RequestedPath}' is not allowed: {Describe(Reason)}. Allowed folders: {string.Join("; ", AllowedRoots)}.
```

When `AllowedRoots` is empty, the part after `Allowed folders: ` is
`(none)`. `Describe` returns exactly:

| Reason | Text |
|---|---|
| `Empty` | `the path is empty` |
| `InvalidCharacters` | `the path contains control characters` |
| `DeviceOrUnc` | `device and network (UNC) paths are not supported` |
| `AlternateDataStream` | `alternate data streams are not supported` |
| `NotFullyQualified` | `the path must be absolute, like C:\Users\you\Documents\file.pdf` |
| `ReservedDeviceName` | `the path uses a reserved device name` |
| `NoAllowedFolders` | `no allowed folders are configured` |
| `OutsideAllowedFolders` | `it is outside the allowed folders` |
| `LinkBelowRoot` | `it goes through a junction or symbolic link` |
| `Inaccessible` | `part of the path could not be inspected` |

Other rules:
- No logging inside `PathPolicy`, no static state, thread-safe.
- Don't follow links to resolve them, and don't call `ResolveLinkTarget`.
  Any link below the root is refused.
- The returned path keeps the casing of the input (after `GetFullPath`),
  not the casing of the root.
- Known limitation (document it in an XML comment, don't solve it): there
  is a time-of-check/time-of-use gap between the walk and the caller's
  file operation.

## Spec changes (proposed)

Replace the `PathPolicy` bullet in SPEC §12 with:

```
- `PathPolicy.Check(path, allowedRoots, mode, relativeTo?)` → full path, or
  throws `PathNotAllowedException` (with a `Reason`; the message names the
  allowed folders):
  - Relative paths resolve against `relativeTo` (the tools pass
    `AttachmentDir`); without it they are refused. Drive-relative (`C:x`)
    and root-relative (`\x`) paths are always refused. The current
    directory is never used.
  - `Path.GetFullPath` first, then the path must be equal to or under one
    root, compared case-insensitively on a **separator boundary**
    (`C:\Docs2` is not under `C:\Docs`). When roots overlap, the longest
    match is used.
  - Reject device and UNC forms (`\\?\`, `\\.\`, `\\server\share`),
    alternate data streams (`:` after the drive), control characters, and
    reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM0-9`, `LPT0-9`)
    in any component.
  - Reject when any existing component of the path below the root is a
    junction or symbolic link (including dangling links), so a link can't
    escape the root. The root itself may be a link. Other reparse points
    (OneDrive Files-On-Demand placeholders, dedup) are not links and are
    allowed. If a component can't be inspected, the path is refused.
  - `mode` is `Read` (draft attachments, must exist and be a file;
    otherwise `FileNotFoundException`) or `Write` (save directories,
    created if missing; `IOException` if the path is an existing file).
    Only policy refusals are `PathNotAllowedException`, so only they record
    a `Blocked` event.
```
