# M11.2 Index schema 2 and the draft marker

## Goal

Give the index what AI drafting (M11.6, M11.7) needs, and mark every
draft Clippy creates (SPEC §9.1, §9.2, §8, §10, §19.4, §19.9):

- **Schema 2** (§9.1): the migration 1→2 adds `in_reply_to`,
  `conversation_topic`, `clippy_marker` and the `ai_decisions` table. It
  runs in one transaction, is idempotent, and is tested from a frozen
  schema-1 fixture. A new database is created at version 2 directly.
- **New `EmailIndex` members** (§9.2): thread columns on `IndexedEmail` /
  `EmailDetail`, `SetThreadMeta`, `Thread`, `RepliedTo`, `SentForStyle`,
  `GetDecision`, `UpsertDecision`, `ModelCallsSince`, plus
  `DraftCandidates` and `PurgeDecisions` (see Spec changes). Decisions
  older than 30 days are purged.
- **`ReadForIndex`** (§8) reads `PR_IN_REPLY_TO_ID`,
  `PR_CONVERSATION_TOPIC` and `ClippyDraft` with one
  `PropertyAccessor.GetProperties` call.
- **Thread-metadata refresh** (§10): one Table-only pass per migrated
  index that fills the three columns for rows indexed before version 2,
  then sets `meta.thread_meta_complete = 1`.
- **Draft marker** (§8, §19.4): `create_draft` and `reply_draft` set
  `ClippyDraft = tool` before the first save or move. `ReplyPlan` carries
  the marker and the work priority, so M11.7 can create `ai` drafts at
  `Background` priority through `OutlookReplyDraftWriter` (§19.9).
- The live draft tests assert the marker.

## Hard rules that apply here

- **Never send.** Nothing here adds `.Send()`, `.Display()`, a `Move`
  or a delete of a mail item. The only COM writes added are
  `PropertyAccessor.SetProperty(DraftMarker.PropertyName, …)` on the new
  draft, before its existing `.Save()` (or the reply path's existing
  `Move`).
- **Index rows only.** The refresh pass and `SetThreadMeta` only
  `UPDATE` the three new columns of existing rows. They never insert or
  delete an `emails` row, and they never touch `last_modified`, `unread`,
  `event_time`, `entry_id` or any FTS column. That way the sync skip rule
  and the reconcile safeguards from c5521f1 (`ReconcilePlanner`'s
  suppression and `MailboxReconciler`'s abandon rule) see the same state
  as before. Their existing tests must pass unchanged.
- **The migration is safe on the user's real index.** It runs inside
  the constructor's existing `BEGIN IMMEDIATE` transaction, so it's all or
  nothing. Every statement is guarded (`IF NOT EXISTS`, or a column check),
  and existing rows, rowids and FTS content are untouched. A
  version-1 app still refuses a version-2 file (the existing "newer
  schema" rule).
- **Long-term EntryIDs** (a264667): the Table pass uses
  `MailTable.Columns(field)` (which includes `PR_LONGTERM_ENTRYID_FROM_TABLE`)
  plus the three new columns, and maps ids with `MailTable.ParseEntryId`
  through `MailTable.ToRow`. Don't add a second id parser.
- **No mail text in `ai_decisions`** (§9.1, §19.11): the API takes ids,
  outcomes and numbers (and the topic column the §9.1 schema defines; see
  Spec changes 7). No logs here contain subjects, topics or bodies.
- **Attach-only COM** is unchanged. **No attachment content**: `Thread`
  returns attachment *names* from `attachment_names` only.

## Behavior

### A. Migration (§9.1)

Replace `string[] Migrations` with
`Action<SqliteConnection, SqliteTransaction>[] Migrations = [Step1, Step2]`.
`Step1` executes the unchanged `Step1Ddl`. The constructor keeps its
shape: one `BeginTransaction()` (Microsoft.Data.Sqlite's default is
`BEGIN IMMEDIATE`, so concurrent constructors serialize), then
`ReadVersion`, the steps `current+1..SchemaVersion` (calling
`afterMigrationStep?.Invoke(n)` after each), then the `schema_version`
upsert. When `current == 0`, it also writes `thread_meta_complete = 1` in
the same transaction, because a new file has no pre-v2 rows. Then
`Commit`. Any exception disposes the transaction uncommitted, which rolls
everything back, and the constructor rethrows.

`Step2` runs exactly this, in order:

```sql
-- for each (name, type) in [(in_reply_to, TEXT), (conversation_topic, TEXT), (clippy_marker, TEXT)]:
--   only when SELECT COUNT(*) FROM pragma_table_info('emails') WHERE name = @name returns 0:
ALTER TABLE emails ADD COLUMN in_reply_to TEXT;
ALTER TABLE emails ADD COLUMN conversation_topic TEXT;
ALTER TABLE emails ADD COLUMN clippy_marker TEXT;

CREATE INDEX IF NOT EXISTS ix_emails_irt ON emails(in_reply_to);
CREATE INDEX IF NOT EXISTS ix_emails_topic ON emails(conversation_topic COLLATE NOCASE, event_time);

CREATE TABLE IF NOT EXISTS ai_decisions (
  source_entry_id TEXT PRIMARY KEY,
  source_imid TEXT,
  conversation_topic TEXT,
  decided INTEGER NOT NULL,
  outcome TEXT NOT NULL,
  rule TEXT,
  model_calls INTEGER NOT NULL DEFAULT 0,
  attempts INTEGER NOT NULL DEFAULT 0,
  confidence REAL,
  draft_entry_id TEXT,
  draft_created INTEGER);
CREATE INDEX IF NOT EXISTS ix_ai_decided ON ai_decisions(decided);
CREATE INDEX IF NOT EXISTS ix_ai_imid ON ai_decisions(source_imid);
```

Column names and types are constants in code, never input. The step
doesn't touch `emails` rows, the FTS table, the triggers or `meta`
(except via the constructor's `schema_version` upsert). A migrated file
has no `thread_meta_complete` key, so the §10 refresh runs once.

The "newer schema" error is unchanged. Its message now says
`supports up to 2`.

### B. Thread columns in `UpsertBatch` / `Get`

- The `INSERT` column list gains `in_reply_to, conversation_topic, clippy_marker`.
  Values: `MailThreadMeta.FromValues(e.InReplyTo, e.ConversationTopic, e.ClippyMarker)`.
  So `"AI"` is stored as `ai`, `"x"` as null, and `" <a@b> "` as `<a@b>`.
- `ON CONFLICT … DO UPDATE` adds
  `in_reply_to = COALESCE(excluded.in_reply_to, emails.in_reply_to)` and
  the same for the other two. A read that failed to get the properties
  (null) never wipes values a Table pass or an earlier read stored.
- `Validate` doesn't change. Thread values are never a reason to reject
  a batch.
- `Get` selects the three columns into `EmailDetail`.
- `Search`, `SearchPage`, `Status`, `ListEntries` and `GetSyncInfo` don't
  change. The new columns aren't in FTS, and `emails_au` doesn't fire for
  them.

### C. Queries

- "Sent Items or under it" is
  `(e.folder = 'Sent Items' COLLATE NOCASE OR e.folder LIKE 'Sent Items\%')`.
  Without an `ESCAPE` clause, `\` is literal in SQLite `LIKE`.
- `Thread` uses `ix_emails_topic`:
  `WHERE e.conversation_topic = @t COLLATE NOCASE AND e.event_time <= @before [AND e.entry_id <> @x] ORDER BY e.event_time DESC, e.id DESC LIMIT @max`.
  The body is `substr(e.body, 1, 20000)`.
- `RepliedTo`: one `SELECT EXISTS(…)` with the halves joined by `OR`. The
  `in_reply_to` half uses `ix_emails_irt`. `after` is exclusive.
- `SentForStyle`: see the API comment. The AI-originated exclusion is
  `NOT EXISTS (SELECT 1 FROM ai_decisions d WHERE d.outcome = 'drafted' AND d.source_imid IS NOT NULL AND d.source_imid = e.in_reply_to AND e.event_time > COALESCE(d.draft_created, 0))`.
  A `drafted` row without `draft_created` excludes every matching reply,
  which is the conservative choice. `clippy_marker IS NULL` covers both `ai`
  and `tool`, because only those two values or null are ever stored.
- `DraftCandidates`:
  `LEFT JOIN ai_decisions d ON d.source_entry_id = e.entry_id WHERE e.folder = 'Inbox' COLLATE NOCASE AND e.event_time >= @since AND (d.source_entry_id IS NULL OR (d.outcome = 'failed' AND d.attempts < 3)) ORDER BY e.event_time DESC, e.id DESC LIMIT @max`.
- All times are bound as unix seconds and read back as UTC
  (`FromUnixTimeSeconds`). Every value is a bound parameter.

### D. Decisions

`UpsertDecision` validates before it opens a connection. Every message
starts with `AI decision: `, and `ParamName` is `decision`:

| Invalid when | Message |
|---|---|
| `SourceEntryId` null/blank | `AI decision: SourceEntryId is empty.` |
| `Outcome` undefined | `AI decision: unknown outcome.` |
| `Outcome == Skipped` and `Rule` null/blank | `AI decision: a skipped outcome needs a rule id.` |
| `Outcome != Skipped` and `Rule` not null | `AI decision: only a skipped outcome has a rule id.` |
| `Rule` longer than 32 chars or not `^[a-z_]+\z` | `AI decision: rule ids are lower-case letters and '_'.` |
| `ModelCalls < 0` or `Attempts < 0` | `AI decision: counts can't be negative.` |
| `Confidence` not null and (NaN, infinite, or outside 0–1) | `AI decision: confidence must be between 0 and 1.` |

The rule check is what keeps free text (such as a model's `reason`) out of
the table. `Outcome` is stored through `AiOutcomes.ToDb`. `GetDecision`
reads it back through `FromDb`, so an unknown stored value reads as
`Skipped`. `model_calls` and `attempts` are what the caller passes. The
caller does the read-modify-write; the drafting worker has a concurrency
of 1.

`ModelCallsSince` sums the cumulative `model_calls` of rows whose last
attempt is at or after `sinceUtc`. If an email was tried before midnight
and again after, all its calls count today. That overcounts and errs on
the safe side for the daily limit (Spec changes 8).

`PurgeDecisions(now)` runs
`DELETE FROM ai_decisions WHERE decided < @t` with
`t = (now − 30 d).ToUnixTimeSeconds()`. `PurgeOlderThan` runs the same
statement in its transaction, with `DateTimeOffset.UtcNow`.

### E. `ReadForIndex` (§8)

Inside the existing `try`, after `pa` is obtained, make one call:
`var values = ComSafe.Try(() => pa.GetProperties(MailTable.ThreadPropertyNames.Cast<object>().ToArray()) as object[]);`
then
`var meta = values is { Length: 3 } ? MailThreadMeta.FromValues(values[0], values[1], values[2]) : MailThreadMeta.Empty;`.
Set `InReplyTo`, `ConversationTopic` and `ClippyMarker` from `meta`.
`GetProperties` reports a missing property as an error value in its slot,
and `FromValues` turns that into null. A COM failure of the whole call
gives `Empty`. Don't open any other object for this.

### F. Thread-metadata refresh (§10)

`OutlookMail.EnumerateThreadMeta` is `EnumerateRange` with
`MailTable.ThreadColumns(rf.TimeField)`: the same `DaslFilter.Range`
filter, the same sort and the same `MailTableQueries.Range` paging.
`WithTable` takes the column list. The three existing callers pass
`MailTable.Columns(rf.TimeField)`, so their behavior is unchanged.

**Marker column fallback.** If `cols.Add(DraftMarker.PropertyName)` throws
a `COMException` that isn't "Outlook gone", don't add it. Map each raw row
by appending one `null`, so `ToRow` still sees 10 values and the marker is
null. The other nine columns are always added. With `COALESCE`, a null
marker never clears a stored one.

`OutlookMailSource.ListThreadMetaAsync` makes one `Run(…)` (Background)
per call. It runs `EnumerateThreadMeta(app, ToResolved(folder), from, toExclusive)`
and maps each row to
`ThreadMetaRow(r.EntryId, r.EventTime, t.InReplyTo, t.ConversationTopic, t.ClippyMarker)`
with `t = r.Thread ?? MailThreadMeta.Empty`.

**`SyncEngine.SyncMailboxAsync`:**

1. Right after `ApplyRetention(plan, index)`, call
   `index.PurgeDecisions(now)`. It needs no COM, so it runs even when the
   mailbox isn't mounted. It has no activity scope and no event.
2. Keep each processed folder's `SourceFolder` in its `FolderRun`.
3. After the folder loop and before the purge block: if
   `index.GetMeta(EmailIndex.ThreadMetaCompleteKey) != "1"`, then for
   each run in `runs` order with `run.Complete == true`:
   - `using var scope = _hub.Begin(ActivityState.Syncing, (prefix.Length == 0 ? "" : prefix + " ") + "Updating thread data " + path);`
   - Start with `to = now.AddSeconds(1)`. Loop for at most 10,000 pages:
     `page = await _source.ListThreadMetaAsync(f, cutoff, to, ct)`, then
     `matched += index.SetThreadMeta(page.Rows.Select(r => (r.EntryId, r.InReplyTo, r.ConversationTopic, r.ClippyMarker)))`.
     Stop when `!page.HasMore` or the page is empty. Otherwise
     `next = page.Rows[^1].EventTime`. If `next >= to`, stop and treat
     the folder as **not done**, because the source misbehaved. Otherwise
     `to = next`. Call `ct.ThrowIfCancellationRequested()` after each page.
   - The folder is done when the loop ends normally.
   - `OperationCanceledException` and `MailSourceUnavailableException`
     propagate, which leaves the key unset. Any other exception is logged
     `_log?.LogWarning(ex, "Thread data refresh of folder {Folder} failed.", path)`.
     The folder is then not done, and the next folder carries on. No
     activity event, no `Error` state.
   - After the loop, if there is at least one run, every run has
     `Complete == true`, and every run's pass is done, call
     `index.SetMeta(ThreadMetaCompleteKey, "1")` and
     `_log?.LogInformation("Thread data refresh complete for mailbox {Mailbox}: {Rows} rows.", …)`
     (own mailbox as `(own)`). Missing folders (`f is null`) aren't runs,
     so they don't block the key.
4. The refresh doesn't count toward `Upserted`/`UnreadUpdated`, so it
   never triggers the `Sync` event on its own. It records no event and
   calls no `Report`.

On a migrated index, in practice, every folder's backfill is already
complete. Even for one that isn't, the backfill pass finishes within the
same cycle (it runs to `cutoff`), so `run.Complete` is true. Rows the
Table lists that aren't indexed are ignored by `SetThreadMeta`.

## Spec changes (proposed)

The caller applies these to `SPEC.md`. All are low-risk, reversible
clarifications. None relaxes a hard rule.

1. **§9.1, new files.** "A database created at version 2 gets
   `meta.thread_meta_complete = 1` at creation (it has no pre-v2 rows), so
   the §10 refresh only runs on migrated files. The migration is
   idempotent: column adds are guarded by `pragma_table_info`, and the
   other statements use `IF NOT EXISTS`."
2. **§9.2, thread columns are never cleared.** "`UpsertBatch` and
   `SetThreadMeta` store `in_reply_to` and `conversation_topic` trimmed
   (empty → null) and the marker through `DraftMarker.Normalize`. A null
   value never overwrites a stored one (`COALESCE`). `SetThreadMeta`
   matches ids exactly, then upper-cased, and never inserts or deletes."
3. **§9.2, "Sent Items rows"** in `RepliedTo` and `SentForStyle` means
   folder `Sent Items` or a subfolder of it (as `FolderPaths.IsUnderSentItems`).
4. **§9.2, signatures and extra members:**
   - `Thread(topic, before, max ≤ 100, excludeEntryId?)`.
   - `SentForStyle(from, to, max = 5000)`, inclusive bounds, newest first.
   - `Thread`/`SentForStyle` bodies are cut to 20,000 characters, and
     attachment names come from `attachment_names`.
   - New: `DraftCandidates(since, max ≤ 500)` (§19.7 candidate query) and
     `PurgeDecisions(now)`.
   - `UpsertDecision` validates rule ids (`^[a-z_]{1,32}$`, only for
     `skipped`), counts and confidence. An unknown stored outcome reads as
     `skipped`.
5. **§10, refresh details.**
   - Label: `Updating thread data <folder>`, with the shared-mailbox
     prefix.
   - It runs after the folder loop, for folders whose backfill is complete
     at that point.
   - Missing folders don't block the key.
   - A per-folder failure is logged (Warning) without an event, and the
     key stays unset.
   - `ai_decisions` older than 30 days are also purged at the start of
     every mailbox cycle (`PurgeDecisions`), because `PurgeOlderThan` only
     runs when old mail exists.
6. **§8, Table and marker details.**
   - `IMailSource.ListThreadMetaAsync` (pages of ≤ 500, newest first).
   - `MailTable.ThreadColumns` = the existing columns (incl.
     `PR_LONGTERM_ENTRYID_FROM_TABLE`) + the three thread columns.
   - If Outlook refuses the `ClippyDraft` Table column, the pass runs
     without it.
   - `ReplyPlan` gains `Marker` and `Priority`. `DraftPlan` gains `Marker`.
   - The warning text is `Could not set the ClippyDraft marker on a draft.`
   - Known limit: Outlook Tables may return long string columns
     shortened, so a very long topic from the refresh may not match. Rows
     re-read through `ReadForIndex` get the full value.
7. **§9.1 vs §19.11 (decide when writing M11.7):** `ai_decisions.conversation_topic`
   is a copy of the email's topic, which is in effect its subject. But
   §9.1 says the table "never holds … subjects" and §19.11 says "ids,
   outcomes and numbers only". This brief keeps the column as §9.1
   defines it and stores whatever the caller passes. Nothing in the spec
   reads it: §19.4 matches on `source_imid`. **Recommendation:** M11.7
   writes `null` there, and §9.1 marks the column "unused, always null".
   That keeps the privacy wording true without another migration. This
   isn't blocking for M11.2.
8. **§19.7 daily limit:** `ModelCallsSince(t)` sums the cumulative
   `model_calls` of rows whose last attempt is at or after `t`. Calls made
   before `t` for an email retried after `t` count again. That is
   conservative (it can stop early, never late).
9. **§3 layout:** `EmailIndex.Ai.cs` (partial `EmailIndex`: thread and
   `ai_decisions` members). `IndexModels.cs` also holds `MailThreadMeta`,
   `ThreadMessage`, `SentMail`, `DraftCandidate`, `AiDecision`,
