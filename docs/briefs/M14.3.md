# M14.3 App tools: `email_stats` and `query_index`

Base: `dev` at 50d9f03 (M14.2 done) or later. M14.1 (`EmailStats.cs`) and
M14.2 (`IndexQuery.cs`) are merged and their public APIs are fixed; this
task wires them as MCP tools, pins the tool texts, and closes the one
logging gap that would leak SQL/SQLite text into the log file. Other
agents work in parallel on M13.x: touch only the files listed below.

## Goal

Expose the two M14 Core features as MCP tools in `McpTools` (SPEC §11,
§11.11, §11.12): `email_stats` (grouped counts, never mail text) and
`query_index` (one read-only SELECT over the temp views `mail`,
`mail_fts`, `mail_attachments`). Both read the index directly on the
request thread, never through the COM worker, so they work while Outlook
is busy or closed. `mailbox` is empty (own), an address, or `all`
(handled by Core: merged counts for stats, per-mailbox runs with a
leading `mailbox` column for SQL). The tool descriptions, with the
views, limits and four example queries, live as constants in Core so
tests can check them and run every example through `IndexQuery`. Logging
follows §5.1 and §11.12 "Logging and privacy": only counts, the mailbox
key and timings at Debug; never SQL, search text, cell values, column
names or SQLite messages. Because the MCP SDK logs every tool exception
(including `McpException`, whose text can quote SQLite's message) at
Error level, the file logger stops writing `McpException` messages
(§5.1 change below). Tests per §15 "Index statistics and SQL … no SQL
in logs".

## Hard rules that apply here

- Read-only. No writes to any index; the tools only call
  `EmailStats.Run` and `IndexQuery.Run`. No change to the views, the
  authorizer or the connection setup in `IndexQuery.cs`.
- Localhost/token: untouched (`McpHttpHost`, `BearerAuth` not edited).
- Attachment content never enters the index: nothing here reads files.
- No COM: the new methods must not use `worker`, `OutlookStores`,
  `OutlookMail` or `EnsureResolvedAsync`.
- Never log the token, search text, SQL, cell values or SQLite messages.

## Behavior

### `GetEmailStats`

1. `var sw = Stopwatch.StartNew();`
2. `var dto = EmailStats.Run(index.Required(), TimeZoneInfo.Local, new SearchArgs { Query = query, Sender = sender, Recipient = recipient, Subject = subject, DateFrom = date_from, DateTo = date_to, Folder = folder, HasAttachment = has_attachment, AttachmentName = attachment_name, AttachmentExt = attachment_ext, Unread = unread, Mailbox = mailbox }, group_by, top, order, include_cc, cancellationToken);`
   (`Limit`/`Offset` are not set; `EmailStats` ignores them.) Validation
   order, the `all` merge, clamping of `top`, the error texts and the
   §9.3 mailbox errors are all Core's.
3. `log.LogDebug("email_stats: group_by {GroupBy}, mailbox {Mailbox}, {Total} emails, {Groups} groups, {Ms} ms", dto.GroupBy, MailboxLabel(dto.Mailbox), dto.Total, dto.Distinct, sw.ElapsedMilliseconds);`
4. `return dto;`

### `QueryIndex`

1. `var result = IndexQuery.Run(index.Required(), sql, mailbox, max_rows, cancellationToken);`
2. `var key = MailboxIndexes.Normalize(mailbox);` (only after success,
   so it is a configured key or `all`).
3. `log.LogDebug("query_index: {Rows} rows, {Columns} columns, mailbox {Mailbox}, {Ms} ms, truncated {Reason}, {Cells} cells cut", result.RowCount, result.Columns.Count, MailboxLabel(key), result.ElapsedMs, result.TruncatedReason ?? "no", result.TruncatedCells);`
   Column **names** are never logged (an alias or expression text such
   as `'budget' AS x` is user text); only their count.
4. `return result;`

### Threading

Both methods are synchronous, like `search_emails`, and run on the
request thread. They never call `worker.RunAsync` or touch Outlook, so
they work while Outlook is busy, not responding or closed. The SDK's
request `CancellationToken` goes into Core: `IndexQuery`'s progress
handler and `EmailStats`' row loop stop on it. `IndexQuery` bounds the
call at 10 s itself.

### Activity

Nothing to add. `McpHttpHost`'s call-tool filter already shows
`Serving` with the tool name and records the `Tool` event
`email_stats` / `query_index` (or `<name> failed` when the result is an

### Log file: `McpException` messages are not written (§5.1 change)

The MCP SDK (2.4.0, `McpServerImpl.ToolCallError`, `LogLevel.Error`,
category under `ModelContextProtocol`) logs every exception a tool
throws, with the exception object. Error passes the Warning cap for
framework categories, and `RollingFileLoggerProvider.Write` appends
`ex.Message`, so today a `query_index` SQL error (`SQL error: near
"<user text>": syntax error. …`, `no such column: <user text>`, FTS5
syntax errors quoting the MATCH string) and `search_emails` date errors
(which quote the input) end up in `clippy-YYYYMMDD.log`. Fix in
`Write`:

```csharp
if (ex is not null)
{
    sb.Append(Environment.NewLine).Append(ex.GetType().FullName);
    if (ex is not McpException) sb.Append(": ").Append(ex.Message);   // tool errors can quote SQL or search text
    if (ex.StackTrace is { } st) sb.Append(Environment.NewLine).Append(st);
}
```

The formatted message line itself (`"query_index" threw an unhandled
exception.`) stays. Redaction still runs on the whole line. Inner
exceptions are still not written (unchanged). No other logger change.

**`IndexQueryTexts.ToolDescription`**

```text
Runs one read-only SQLite SELECT over the local email index, for questions the other tools can't answer in one call: joins, custom grouping, full-text search with snippets. For plain counts by sender, domain, recipient, folder or time, email_stats is simpler. Works while Outlook is busy or closed; only synced mail is indexed.
Views:
mail(id, doc, mailbox, folder, date, unix_time, sender_name, sender_email, to_addrs, cc_addrs, subject, topic, body, unread, has_attachments, attachment_names): one row per email. id is the id get_message takes. doc joins to mail_fts.doc and mail_attachments.doc. mailbox is '' for the user's own mailbox. folder is a path like 'Inbox' or 'Sent Items'. date is local time as text 'yyyy-MM-ddTHH:mm:ss'; unix_time is UTC seconds. to_addrs and cc_addrs are 'Name <email>; ...'. topic is the conversation topic, body is plain text. unread and has_attachments are 0/1 (has_attachments ignores inline images). attachment_names has one file name per line.
mail_fts(mail_fts, rank, doc, subject, body, sender_name, sender_email, to_addrs, cc_addrs, attachment_names): the FTS5 full-text index. Filter with WHERE mail_fts MATCH '...' (FTS5 syntax: words are ANDed, OR, NOT, "a phrase", prefix*, column:word) and sort with ORDER BY rank (best first). snippet(mail_fts, n, ...) and highlight(mail_fts, n, ...) take a column number: 0 subject, 1 body, 2 sender_name, 3 sender_email, 4 to_addrs, 5 cc_addrs, 6 attachment_names. bm25(mail_fts) also works. Join to mail on doc.
mail_attachments(doc, position, filename, size, is_inline): one row per attachment. Only file names are indexed, never attachment content.
Limits: one read-only SELECT (WITH and VALUES also work), no ? parameters, 10 s, at most 1000 rows (max_rows), long text cut at 2,000 characters. Nothing else in the database can be read; PRAGMA, ATTACH and any write are refused. With mailbox="all" each mailbox is queried separately and the rows are concatenated with a leading mailbox column, so counts and other aggregates are per mailbox; use email_stats for counts merged across mailboxes.
Returns {columns, rows (one array per row), row_count, truncated, truncated_reason, truncated_cells, elapsed_ms}.
Examples:
Top senders last year: <ExampleTopSenders>
Mail per month: <ExampleMailPerMonth>
Full text with snippets: <ExampleFullText>
PDFs by sender: <ExamplePdfsBySender>
```

**`IndexQueryTexts.SqlParameterDescription`**:
`One SQLite SELECT over the views mail, mail_fts and mail_attachments (see the tool description). Write values into the SQL; ? parameters are not supported. On large mailboxes add a LIMIT and a date or folder filter.`

**`IndexQueryTexts.MailboxParameterDescription`**:
`Empty = the user's own mailbox, an SMTP address = that shared mailbox, 'all' = every enabled mailbox, each queried separately (rows get a leading mailbox column).`

**`IndexQueryTexts.MaxRowsParameterDescription`**:
`Maximum rows returned, 1 to 1000.`

**`EmailStats.ToolDescription`** (one line):

```text
Counts emails in the local index, grouped, in one call. Use it for questions like "top 10 people who emailed me last year" (group_by=sender, folder=inbox, date_from one year ago), "how much mail per month" (group_by=month, order=key) or "who do I write to most" (group_by=recipient, folder=sent). Returns counts and names only, never mail text: {group_by, mailbox, total, distinct, truncated, rows: [{key, name, count, first, last}]}. total is the number of matching emails, distinct the number of groups, and truncated is true when there are more groups than top. Keys: sender and recipient are lower-cased email addresses (name is the display name in the newest email); sender_domain and recipient_domain are the part after the @; folder is the folder path; month is yyyy-MM, week yyyy-Www (ISO), weekday Mon to Sun, hour 00 to 23, all in local time. (unknown) means there was no address. recipient counts each To address, plus CC when include_cc is true, once per email. first and last are the dates of the oldest and newest email in the group (local time, ISO with offset). The filters work as in search_emails. With mailbox="all" the counts of every enabled mailbox are added together (an email in two mailboxes counts twice). For joins, snippets or other custom questions use query_index.
```

**`EmailStats.GroupByParameterDescription`**:
`What to group by: sender, sender_domain, recipient, recipient_domain, folder, month, week, weekday or hour.`

**`EmailStats.TopParameterDescription`**:
`Number of groups to return, 1 to 200.`

**`EmailStats.OrderParameterDescription`**:
`count = largest groups first (default); key = by key: chronological for month, week and hour, Mon to Sun for weekday.`

**`EmailStats.IncludeCcParameterDescription`**:
`For recipient and recipient_domain: also count CC addresses.`

**`EmailStats.MailboxParameterDescription`**:
`Empty = the user's own mailbox, an SMTP address = that shared mailbox, 'all' = every enabled mailbox, counted together.`

## Spec changes (proposed; not applied, the caller syncs SPEC.md)

From M14.2's implementation (all in §11.12, low-risk, reversible):

1. **Authorizer READ through a view is column-checked** (tightening;
   CTE-name spoofing). The "view" argument is a *name*, and a user CTE
   or alias can take it (`WITH mail AS (SELECT store_id FROM emails) …`).
   Replace "allowed when the access comes through one of the three
   views" with: a read named `mail`/`mail_fts`/`mail_attachments` itself
   is allowed; inside a view context only the columns the views use are
   allowed (`emails`: `id`, `entry_id`, `folder`, `event_time`,
   `sender_name`, `sender_email`, `to_addrs`, `cc_addrs`, `subject`,
   `conversation_topic`, `body`, `unread`, `has_attachments`,
   `attachment_names`; `attachments`: `email_id`, `position`,
   `filename`, `size`, `is_inline`); top-level reads of `emails` only the
   FTS external-content columns already listed.
2. **No-column reads** (new rule, `IndexQueryAuthorizer.DecideRead`): a
   READ with an empty column (`count(*)`, constant-only select lists, a
   `FROM` whose columns aren't used) reveals at most that rows exist.
   SQLite reports it for CTE names (no schema to tell them apart) and
   for the views' own flattened `FROM main.emails`/`main.attachments`.
   Allowed: `emails`/`attachments` only with database name `main` (the
   views' qualified form); any other table name except `meta`,
   `sync_state`, `ai_decisions`, `dbstat`, `sqlite_*` and `pragma_*`.
   Denied texts stay `table <name>` / `column <table>.<column>`.
3. **`PRAGMA data_version` is allowed for FTS5's own statement**
   (`arg2` null, no view context; `fts5IndexDataVersion`). User-typed
   `PRAGMA` stays refused (keyword check) and `pragma_*` table functions
   are refused by READ.
4. **Lexical tail check**: the text after the first statement may hold
   only whitespace, `;` and comments; it is not prepared again
   (`sqlite3_prepare_v2` returns no statement for an empty `;`, so
   `SELECT 1; ;DROP …` would pass a single tail prepare).
5. **Leading-keyword check before prepare**: `SELECT`/`WITH`/`VALUES`
   pass; `INSERT`, `REPLACE`, `UPDATE`, `DELETE`, `CREATE`, `DROP`,
   `ALTER`, `REINDEX`, `ANALYZE`, `VACUUM` → `writing`; `PRAGMA`,
   `ATTACH`, `DETACH`, `EXPLAIN` → themselves; `BEGIN`, `COMMIT`, `END`,
   `ROLLBACK`, `SAVEPOINT`, `RELEASE` → `transactions`; anything else →
   `statements that don't start with SELECT, WITH or VALUES`. Needed
   because SQLite rejects `DELETE FROM mail` ("cannot modify mail
   because it is a view") before the authorizer is asked.
6. **`SQLITE_LIMIT_LENGTH` 50,000,000** (step 3 of "Connection"), against
   `randomblob`/`zeroblob`/`printf` memory bombs inside the 10 s window;
   and `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION` is set to 0 explicitly.
7. **Texts missing from §11.12**:
   `sql is required: one SELECT over the views mail, mail_fts and mail_attachments.`,
   `sql is longer than 20,000 characters. Shorten the query.`;
   `<mailbox>` in the unavailable text is `your own mailbox` for `""`;
   a trailing `.` of SQLite's message is dropped in `SQL error: …`
   (`unknown error` when empty).
8. **Result rules**: `truncated`/`"max_rows"` only when another row
   really exists, or (with `all`) when mailboxes were left unqueried;
   the size cap is row-granular (a row is added only while the total of
   string cells stays ≤ 1,000,000 characters; numbers, nulls, the
   `mailbox` column and column names don't count); non-finite reals are
   `null`; `truncated_reason` is omitted when not truncated; a file
   without the `emails`/`attachments`/`emails_fts` tables is
   "unavailable" (checked before the views are created). Any error in
   one mailbox fails the whole `all` call.

From this task:

9. **§5.1 Log file**: "plus the exception type, message and stack trace
   when there is one" becomes "… when there is one; for an
   `McpException` (tool errors, which can quote search text, SQL or
   SQLite messages back to the model) the message is left out". Reason:
   the MCP SDK logs every tool exception at Error, which passes the
   framework Warning cap. This also closes an existing leak: invalid
   `date_from`/`date_to` texts from `search_emails` and friends were
   written to the log.
10. **§11.12 / §11.11 logging detail**: the Debug lines are exactly the
    two templates in "Behavior" (counts, the mailbox key, ms,
    truncation; never column names). The tool descriptions are the
    constants `IndexQueryTexts.ToolDescription` and
    `EmailStats.ToolDescription` (this brief has the text).
