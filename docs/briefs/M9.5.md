# M9.5 COM call watchdog + local-first `OutlookStores`

## Goal

A single hung Outlook COM call must never block the worker, the tools or
the sync forever (SPEC §4, §6.1, §6.5, §7, §8, §10). The 2026-11-12 smoke
test hit exactly that: against a cached-mode Outlook with an unreachable
server, the first COM call of the sync never returned, `list_events` hung
for 180 s with no error, and Outlook showed "Not Responding". The likely
trigger was `OutlookStores.List`, which runs a GAL lookup
(`AddressEntry.GetExchangeUser().PrimarySmtpAddress`) for every store on
every `Get()`.

This task does two things:

1. **Watchdog in `ComWorker<TApp>` (Core).** Every attach, probe and work
   item gets a deadline. When a running call misses it, the worker fails
   the item with a new `OutlookNotRespondingException`, **abandons** the
   STA thread (the hung call can't be cancelled), enters a new
   `NotResponding` connection state, and starts a **replacement** STA
   thread. The replacement re-attaches with `IComAttacher.TryAttach` only
   (`GetActiveObject`), so Outlook is never launched. Only a bounded
   number of abandoned threads may be alive at once. While
   `NotResponding`, interactive calls fail at once and background work
   waits. When Outlook answers again (a recovery probe succeeds, or an
   abandoned call finally returns), the worker becomes `Available` and
   background sync resumes. The tray shows the grey `OutlookUnavailable`
   icon with the tooltip "Outlook is not responding" and, after 2
   minutes, a balloon.
2. **Local-first `OutlookStores` (App) + `StoreListCache` (Core).** The
   store list is cached per connection. SMTP addresses come from local
   profile data (`Session.Accounts`) and earlier lookups. The GAL
   owner lookup runs only when a configured shared mailbox can't be
   matched otherwise, as its **own work item with its own timeout**, and
   never inside `List`/`Get`.

## Hard rules that apply here

- **Attach-only.** Replacement threads get Outlook only through the same
  `IComAttacher<TApp>.TryAttach` (`GetActiveObject`). Don't write
  `new Application(`, `new Outlook.Application(`, `Activator.CreateInstance`
  or `CoCreateInstance` anywhere, not even in comments (the M10.1 scan
  matches text).
- **Never send.** No `.Send()` is added. The existing
  `OutlookCalendar.CreateMeeting` `.Send()` stays unchanged. A watchdog
  timeout does not retry anything. The failed item is **not** re-run on
  the new thread, because a write could otherwise happen twice.
- **No token, bodies, subjects or search text in logs or events.**
  Watchdog log lines and the activity event name only the priority and
  the timeout.
- COM objects are apartment-bound. An abandoned thread releases its own
  RCWs **on its own thread** when its call returns. No cache may hold an
  RCW. `StoreListCache` holds strings only.
- No `.Result`/`.Wait()` outside the COM worker threads. `Dispose` may
  `Join` the live thread (shutdown only). It must not join abandoned
  threads.

## Behavior

### A. Lanes and the watchdog (`ComWorker<TApp>`)

**Structure.** Split today's single thread into a private `Lane` class:
one STA thread with its own `Instance`, backoff, next-attempt time,
last-activity time and a `Running` slot `(Item? item, TimeSpan deadline,
bool isAttempt)`. The worker holds the shared queues, `_live` (the lane
that serves the queues, or null), the abandoned-and-still-blocked count,
the state, the hub scope and `ConnectionId`. Every lane thread is created
the same way: `IsBackground = true`, `ConfigureThread` applied (STA in the
App), and the name `ThreadName` plus `#<n>` from the second lane on. The
existing step logic (interactive first, background only with an
instance, scheduled attach with backoff, idle probe, nudge) runs inside
the live lane unchanged, except where noted below.

**Deadlines.** Before a lane calls into COM it sets `Running` under
`_lock`, and it clears `Running` after the call returns. The deadline
depends on the call:

| Call | Deadline |
|---|---|
| Interactive item | its enqueue time + its timeout (`InteractiveTimeout` or the per-call override) |
| Background item | its start time + its timeout (`BackgroundTimeout` or the override) |
| Attach attempt or idle probe | start + `ProbeTimeout` |

**Watchdog.** One `System.Threading.Timer` (period `WatchdogPeriod`) is
started in `Start` and disposed in `Dispose`. On each tick, under `_lock`:

1. Fail every **queued** interactive item whose deadline has passed with
   `OutlookNotRespondingException` (`TrySetException`). This does not
   abandon anything: the lane is busy with something else that is still
   within its own deadline.
2. If the live lane's `Running` deadline has passed, **abandon** it as
   described next.

Release `_lock` before you change state, raise events, log or start a
thread.

**Abandon(lane):**
1. Mark the lane abandoned, set `_live = null`, and increment the
   abandoned count.
2. If it was running an item, fail that item with
   `OutlookNotRespondingException`. If it was an attach attempt that an
   interactive item was waiting on (the fail-fast attempt in §4), fail
   that item the same way.
3. Set the state to `NotResponding` (see State and tray below).
4. Record **one** `ActivityHub` event:
   `Event(ActivityKind.Error, $"Outlook isn't responding: a call took longer than {s} s")`,
   where `s` is the timeout in seconds formatted with `"0.#"` and the
   invariant culture (`30`, `0.3`). Log a Warning with the same text
   plus the priority and the abandoned count.
5. If the abandoned count is below `MaxAbandonedThreads`, start a new
   live lane in **recovering** mode. Otherwise leave `_live` null.

**An abandoned lane, when its call finally returns** (result or
exception): it must not touch the queues, the state or `ConnectionId`.
It discards the result (the item's `TrySet*` is already a no-op), calls
`_attacher.Release(instance)` **on its own thread** if it holds one
(catching everything), decrements the abandoned count, and exits its
loop. Then, if the worker isn't disposed, it signals **"Outlook
answered"**: if there is no live lane, start one in recovering mode with
an immediate attempt; otherwise ask the live lane to attempt at once,
which works like `Nudge`. If the call never returns, the thread stays
blocked until the process exits. It's a background thread, so it
doesn't keep the process alive.

**Recovering mode** (a live lane while the state is `NotResponding`):
- No instance. **Interactive items fail at once** with
  `OutlookNotRespondingException`, with no attach attempt. Background
  items stay queued.
- A recovery attempt is `TryAttach()` followed by `Probe(app)`, both
  under one `ProbeTimeout` deadline. The first attempt runs
  `RecoveryInterval` after the lane starts, or at once after "Outlook
  answered" or `Nudge()`. Later attempts run every `RecoveryInterval`
  (fixed, no doubling).
  - Both succeed: the lane keeps the instance, `ConnectionId++`, the
    state becomes `Available`, and background work drains.
  - `TryAttach` returns null, or either call throws a "gone" error:
    release whatever it got, set the state to `Unavailable`, and continue
    with today's backoff behavior.
  - Any other exception: release whatever it got, log at Debug, and try
    again after `RecoveryInterval`.
  - Deadline missed: the watchdog abandons the lane (and may start
    another, up to the cap).

**`RunAsync` while `NotResponding`.** An interactive call returns
`Task.FromException<T>(new OutlookNotRespondingException())` without
enqueuing. This also covers the case where there is no live lane because
the cap was reached. A background call is enqueued and waits.

**Attach and probe in other states.** These are now guarded too.
- A scheduled attach, the fail-fast attach for an interactive item, or
  the idle probe that misses `ProbeTimeout` gets the same abandon
  treatment.
- Normal (non-recovering) attaches stay `TryAttach` only, as today.
  `ConnectionId++` on each success.
- `Nudge()` now also works in `NotResponding`, where it triggers an
  immediate recovery attempt. It is still a no-op when `Available`.

**State and the tray.** Make `SetState` callable from both the watchdog
and lane threads. Serialize it with a separate state lock that is never
taken while holding `_lock`, so `StateChanged` handlers see transitions
in order.
- `Unavailable`: keeps today's hub scope `Begin(OutlookUnavailable, "")`.
- `NotResponding`: holds `Begin(OutlookUnavailable, OutlookConnection.NotRespondingLabel)`.
- Moving between the two disposes one scope and begins the other.
  `Available` disposes either one.
- The log line stays `"Outlook connection: {State}"`.

**Dispose.**
- Stop the watchdog timer and mark the worker disposed.
- Wake and `Join` the **live** lane (5 s, as today). Don't join
  abandoned lanes.
- `Cleanup` fails pending items with `ObjectDisposedException` and
  releases the live lane's instance on the live lane's thread, as
  today.
- An abandoned lane that returns after `Dispose` only releases its
  instance and exits. It must not throw and must not start a lane.

**What is not done.** There is no retry of a timed-out item, no
`IMessageFilter`, no thread abort or interrupt, and no
`CoDisconnectObject`.

### B. Local-first store list (`OutlookStores`, `StoreListCache`)

**`List(app)`:**
1. If `_cache.TryGet(worker.ConnectionId, out var s)` succeeds, return
   `s`.
2. Otherwise enumerate `session.Stores` as today: type,
   `StoreID`, `DisplayName` and default-store id. Release every COM
   object inside the loop. Also fix the leak from the carry-forward
   notes: put `session.Stores` inside the `try`.
3. Build `accountSmtp`, a `storeId → SMTP` map from `session.Accounts`:
   for each `Account`, take `Account.DeliveryStore.StoreID` →
   `Account.SmtpAddress`. Release the `Account` and its `DeliveryStore`
   inside the loop. A `COMException` that isn't "gone" skips that
   account.
4. Make each candidate with
   `Smtp = accountSmtp.GetValueOrDefault(id)` (null when missing). The
   cache adds known SMTPs from earlier lookups. **Never call
   `GetAddressEntryFromID`, `GetExchangeUser` or `PrimarySmtpAddress`
   here.**
5. Return `_cache.Set(worker.ConnectionId, candidates)`.

**`LookupOwnerSmtp(app, storeId)`** is today's `ReadOwnerSmtp` logic
(`PR_MAILBOX_OWNER_ENTRYID` → `GetAddressEntryFromID` →
`GetExchangeUser().PrimarySmtpAddress`, with the same catch filter) on
`session.GetStoreFromID(storeId)`. A non-"gone" `COMException` from
`GetStoreFromID` gives null. It calls
`_cache.RecordLookup(worker.ConnectionId, storeId, smtp)` and returns
`smtp`. Release every COM object it touches. When it runs on a lane that
was abandoned and its call returns late, it still records the result.
That is fine: the cache holds plain data and the SMTP is keyed by
StoreId.

**`EnsureResolvedAsync(priority, ct, includeUnconfigured)`:**
1. `shared` = the enabled shared mailbox keys from settings, the same
   list `ConfiguredKeys()` gives minus the own `""`.
2. If `shared` is empty and `includeUnconfigured` is false, return. No
   work item runs.
3. Fast path: if `_cache.IsSettled(worker.ConnectionId, shared, includeUnconfigured)`,
   return.
4. Run one work item `app => { List(app); return _cache.PendingLookups(worker.ConnectionId, shared, includeUnconfigured); }`
   at `priority`.
5. For each pending store id, in order: run
   `worker.RunAsync(app => LookupOwnerSmtp(app, id), priority, ct, timeout: LookupTimeout)`.
   - On `OutlookNotRespondingException`: call `_cache.RecordTimeout(id)`
     and rethrow.
   - Other exceptions propagate.
   - After each lookup, stop when
     `_cache.IsSettled(worker.ConnectionId, shared, includeUnconfigured)`.

**`Get(app, mailbox)`** keeps its contract and error texts. It now uses
the cached `List`, so it never does a GAL lookup. If a configured shared
mailbox wasn't matched (because nobody called `EnsureResolvedAsync`, or
the lookup returned null), it throws today's `StoreCatalog.NotAvailable`
text.

**Call sites** call `await stores.EnsureResolvedAsync(priority, ct)`
before their main `RunAsync`:
- `McpTools.ListEvents`, when `mailbox` is not blank.
- `OutlookMeetingCalendar.ResolveAsync`, when `request.Mailbox` is not
  empty.
- `OutlookDraftWriter.CreateAsync`, when `plan.Mailbox` is not empty.
- `OutlookReplyDraftWriter.ReplyAsync`, always (the mailbox may default
  to the original's shared mailbox).
- `McpTools.GetMessage`, before the live `ReadById` only (not for index
  hits).
- `OutlookAttachmentSaver.SaveOneAsync` and `SaveManyAsync`, always.
  These also pass `timeout: OutlookStores.AttachmentTimeout` to their
  `RunAsync`, because saving large attachments is slow but legitimate.
- `OutlookMailSource.OpenMailboxAsync`, at `Background` priority, when
  the key is non-empty.

All interactive call sites use `WorkPriority.Interactive`. Every call is
a no-op without shared mailboxes, so the own-mailbox paths never pay for
it.

**Own mailbox SMTP** comes only from `Accounts`. If it's missing, it
stays `""`. It is never looked up in the GAL. Existing consumers already
handle `""`.

### C. Tray, balloon, index_status, sync resume

- `TrayView`: when the state is `OutlookUnavailable` and
  `progress.Label == OutlookConnection.NotRespondingLabel`, the tooltip
  and status line are `Clippy — Outlook is not responding`. The icon is
  `TrayIconKey.Unavailable` and `ShowStartOutlook` is `false`. With any
  other label, nothing changes. `TrayApp` already shows Start Outlook only
  for `worker.State == Unavailable`, so leave that code alone.
- `BalloonTexts.OutlookNotResponding = "It looks like Outlook isn't responding. I'll keep trying — check Outlook for an open dialog box."`
- `StateBalloonPolicy.Observe`: the episode rules don't change. It is the
  same `OutlookUnavailable` episode, the 2-minute threshold and once per
  episode. When the balloon fires, use `OutlookNotResponding` if
  `progress.Label == NotRespondingLabel`, else `OutlookUnavailable`.
- `McpTools.IndexStatus`: `NotResponding` → `outlook_running = true`.
  Outlook is running. The `state`/`progress` fields already show
  `OutlookUnavailable` / `not responding`.
- `Program`: subscribe to `worker.StateChanged` and track the previous
  state in a local, under a `Lock`, because the handler may run on
  several threads. When it goes from `NotResponding` to `Available`, call
  `sync?.SyncNow()`. This keeps background sync from waiting up to a full
  interval after Outlook recovers. Recovery from `Unavailable` keeps
  today's behavior.

### Edge cases (must hold)

- A call that finishes right at the deadline: whichever side sets or
  clears `Running` under `_lock` first wins. The item completes exactly
  once, and the lane is abandoned only if the watchdog won.
- An item cancelled through `ct` while it runs on a lane that is later
  abandoned stays `Canceled`. The watchdog uses `TrySetException`.
- A background chunk that misses its deadline fails with
  `OutlookNotRespondingException`. Through `OutlookMailSource` that
  becomes `MailSourceUnavailableException`, and the cycle ends quietly
  (§10). The next cycle's items wait in the queue until `Available`.
- `RunChunkedAsync` uses `BackgroundTimeout` per chunk. Its signature
  doesn't change.
- `StateChanged` subscriber exceptions are still swallowed.
- `ConnectionId` never decreases. Reads are `Interlocked.Read`/`Volatile`.

## Tests

All tests are in Core and run on Linux. Use the existing `FakeAttacher`
style, extended with optional `ManualResetEventSlim` gates (`AttachGate`,
`ProbeGate`) that block inside `TryAttach`/`Probe` until set, and a
per-instance record of the attach thread and the release thread. Hang a
work item by having the delegate wait on a gate. Watchdog rig options:
`InteractiveTimeout = BackgroundTimeout = ProbeTimeout = 300 ms`,
`RecoveryInterval = 50 ms`, `WatchdogPeriod = 20 ms`, `MaxAbandonedThreads = 2`.
Always set every gate in `finally`, so no test leaks a blocked thread.
Use polling waits with a 5 s ceiling, never fixed sleeps, for
assertions.

## Spec changes (proposed)

Another architect is editing `SPEC.md` in parallel, so these go in after
merge.

**§4, append to "Details (M5.1)"** (or a new "Details (M9.5): watchdog"
list right after it):

> - **Watchdog.** Every COM call has a deadline: interactive items 30 s
>   from `RunAsync` (queue wait included; a per-call override exists,
>   e.g. 120 s for saving attachments), background items 60 s from their
>   start, attach attempts and probes 20 s. A queued interactive item
>   past its deadline fails without affecting the thread. A *running*
>   call past its deadline can't be cancelled, so the worker fails its
>   item with `OutlookNotRespondingException` (an
>   `OutlookUnavailableException` with the message
>   "Outlook isn't responding. It may be busy, offline or showing a dialog box. Ask the user to check Outlook, then try again. If this call was creating a draft or a meeting, check Outlook for it before retrying."),
>   **abandons** that STA thread, and starts a replacement STA thread.
>   The item is never retried. The connection state becomes
>   `NotResponding`.
> - An abandoned thread does nothing more except, when its call returns,
>   release its own Application object on its own thread and exit. At
>   most 2 abandoned threads may be alive; beyond that no new thread
>   starts until one returns.
> - While `NotResponding`, interactive work fails at once with that
>   message, and background work waits. Every 10 s (or at once when an
>   abandoned call returns, or on `Nudge()`) the live thread tries
>   `GetActiveObject` plus the `Application.Name` probe. Success →
>   `Available`, and a sync cycle starts. No running Outlook or a "gone"
>   error → `Unavailable`. Re-attaching uses `GetActiveObject` only and
>   never starts Outlook.
> - `RPC_S_CALL_FAILED` (`0x800706BE`) also counts as "Outlook is gone".
> - The worker exposes `ConnectionId`, which increments on each
>   successful attach, so callers can cache plain data per connection.
>   Caches never hold COM objects.

**§6.1**, under the table:

> While the worker is `NotResponding` (§4), the tray uses the
> `OutlookUnavailable` icon with the tooltip
> `Clippy — Outlook is not responding` (scope label `not responding`).
> Start Outlook stays hidden. An `Error` event
> `Outlook isn't responding: a call took longer than <n> s` is recorded
> for each abandoned call.

**§6.5**, after the Outlook-unavailable trigger:

>   store id and primary SMTP address. It reads local data only: the
>   store list and `Session.Accounts` (`Account.DeliveryStore` →

>   It is cached per worker connection for at most 10 minutes. The GAL

>   runs only for stores still unmatched when an enabled shared mailbox
>   needs one, each as its own work item with a 10 s timeout, before the
>   tool's or sync's main work item (`EnsureResolvedAsync`). A null
>   result isn't retried on the same connection. A timed-out lookup isn't
>   retried for 30 minutes. The own mailbox's SMTP never needs the GAL.

### Why these are low-risk

All of these choices were decided rather than asked:
- The timeouts and the cap are constants and easy to tune.
- The tray reuses an existing icon and state.
- The new error message tells the model to check Outlook before retrying
  writes. That is the safer default for a draft or invite that completes
  late.
- No hard rule is touched. Nothing is sent, and re-attach is
  `GetActiveObject` only.
