# M19.7 App: reading attachments through Outlook, OneDrive registry, wiring

Base: `dev` with M19.6 merged (`DraftWorkerServices.Attachments`,
`AiSettings.ReadAttachments`, `AiTabTexts.ReadAttachmentsText`,
`DraftAttachmentTexts`). This brief is written against the M19.6 brief
as the contract; if a name there differs in the merged code, follow the
merged code and say so in the hand-back. M17.3 is done
(`PrivateFolder.Ensure`, `OutlookAttachmentLinkSaver`, the start-up
cleanup pattern of `AttachmentLinks.CleanUpAtStart`).

## Goal

Make attachment text real in the running app. The App implements the
M19.4 seam `IAttachmentSource` (`OutlookAttachmentSource`): one COM work
item per attachment reads it through Outlook (`OutlookMail.ReadAttachmentForAi`
in `OutlookMail.Attachments.cs`): cloud attachments are recognised and
never saved, files are saved with `SaveAsFile` into the private folder
`%LOCALAPPDATA%\ClippysRevenge\ai-files\` under a random name, their
bytes are read and the file is deleted in `finally`, and attached emails
are opened with `OpenSharedItem` and closed with `Close(olDiscard)`. The
synced OneDrive scopes come from `OneDriveRegistry` (HKCU, read-only)
through Core `OneDriveScopes.Build`. `Program` cleans `ai-files\` at
start-up and passes `new DraftAttachments(...)` as
`DraftWorkerServices.Attachments`. Settings → AI drafts gets the
*Read attachments and synced shared files for drafts* checkbox. The
§26.11 safety scans are added with planted violations. One small Core
change rides along: `EmailIndex.ThreadAttachments` leaves out rows in
Deleted Items (the coordinator's decision, §26.1).

SPEC refs: §26.9 (COM side and private folder, incl. "Details (M19.7)"),
§26.10 (setting and checkbox), §26.11 (safety rules and scan details),
§26.3 ("Sync data", cloud attachments in COM, Files-On-Demand),
§26.1 (Deleted Items rule), §26.8 (seam, index), §24.2 and §24.6
(private folder, `SaveAsFile` rule), §12 (PathPolicy), §15 (safety
scans), §5.1 (data locations), §8 (GetItem chain).

## Hard rules that apply here

- **Never send, never delete or move mail.** No `.Send(`, `.Move(`,
  `.MoveTo(`, `.Display(`, `.Copy(`, `Delete(` or `PermanentDelete(` on
  any Outlook object. The opened attached item is never saved
  (`.Save(`), only `Close(Outlook.OlInspectorClose.olDiscard)` and
  released. `File.Delete` on Clippy's own temp files is allowed.
- **Never launch Outlook.** Everything runs inside `OutlookWorker`
  work items on the attached instance. No `new Outlook.Application`,
  `Activator.CreateInstance`, `CoCreateInstance`.
- **Attachment content never enters the index.** Bytes and text live only
  in memory for the duration of one read; nothing is written to SQLite,
  settings, logs or Activity. The temp copy exists only between
  `SaveAsFile` and the `finally` that discards it.
- **PathPolicy**: the `ai-files` folder is checked with
  `PathPolicy.Check(folder, [folder], PathMode.Write)` before every save
  (the folder, not the file path, see §26.9); synced files are already
  checked in Core (`SyncedFileReader`, M19.3).
- **No Graph, no network.** No `HttpClient`, `WebRequest`, `WebClient`,
  `Process` in any file of this task. The registry is only read.
- COM objects are released in `finally`, and objects from enumerations
  inside the loop (`Marshal.ReleaseComObject` via the existing
  `Release` helper).
- Logs: only constant texts, counts and exception type names. Never a
  path, file name, URL, entry id, subject, body or exception message.

/// <summary>The ai-files folder can't be used (Ensure failed, junction/symlink, PathPolicy refused).
/// Message is constant and never holds the path.</summary>
public sealed class AiFolderUnusableException : IOException
{
    public const string DefaultMessage = "Clippy's private folder for attachment text can't be used.";
    public AiFolderUnusableException();
    public AiFolderUnusableException(Exception? inner);
}

/// <summary>Temp copies of Outlook attachments for AI drafts (SPEC 26.9). Thread-safe (one lock).
/// Logs only constant texts, counts and exception type names.</summary>
public sealed class AiFiles
{
    /// <exception cref="ArgumentNullException">options, Folder or EnsurePrivateFolder null.</exception>
    /// <exception cref="ArgumentException">Folder not fully qualified.</exception>
    public AiFiles(AiFilesOptions options);

    /// <summary>The folder, Path.GetFullPath'd, without a trailing separator.</summary>
    public string Folder { get; }

    /// <summary>Retries pending deletes, ensures the folder, refuses a link, PathPolicy-checks the folder,
    /// returns Folder + NewFileName(item). Does not create the file.</summary>
    /// <exception cref="AiFolderUnusableException">any of the folder steps failed (inner = the cause).</exception>
    public string PrepareTempPath(bool item);

    /// retried at the next PrepareTempPath; one Warning with the exception type.</summary>

    /// <exception cref="ArgumentException">path not directly in Folder or name not IsTempFileName (programming error).</exception>
    public void Discard(string path);

    /// <summary>App start: ensure the folder, then delete every temp-named file directly in it. Never throws.</summary>
    public void CleanUpAtStart();

    /// <summary>Test hook: failed deletes waiting for a retry.</summary>
    internal int PendingRetries { get; }
}

## Behavior

### A. `AiFiles`

1. Ctor: `Folder = Path.TrimEndingDirectorySeparator(Path.GetFullPath(options.Folder))`
   after the `IsPathFullyQualified` check.
2. `PrepareTempPath(item)`, all under the lock:
   1. Retry every remembered path (`Files.DeleteFile`); success removes
      it from the set; failure keeps it (no extra Warning on retries).
   2. `EnsurePrivateFolder(Folder)`; any exception except
      `OperationCanceledException` → `AiFolderUnusableException(inner)`.
   3. `Files.IsLink(Folder)` true → `AiFolderUnusableException()`;
      `IOException`/`UnauthorizedAccessException` from it → wrapped.
   4. `PathPolicy.Check(Folder, [Folder], PathMode.Write)`;
      `PathNotAllowedException`/`IOException`/`UnauthorizedAccessException`
      → wrapped.
   5. Return `Path.Combine(checked, AiFilePaths.NewFileName(item))`.
   This is the same sequence as `AttachmentLinks.PrepareTempPath`
   (M17); don't change that class.
3. `Discard(path)`: validate (`Path.GetDirectoryName(Path.GetFullPath(path))`
   equals `Folder`, `OrdinalIgnoreCase`, and the name passes
   `IsTempFileName`; else `ArgumentException("path must be an AI temp file.")`
   with no path in the message). Then `Files.DeleteFile(path)`; on
   `IOException`/`UnauthorizedAccessException` add it to the retry set
   and log Warning
   `Could not delete an AI temp file ({Type}); retrying before the next save.`
4. `CleanUpAtStart()` (copy the `AttachmentLinks.CleanUpAtStart` shape,
   with these texts; never throws):
   - Ensure fails → Warning `AI file folder not usable at start-up ({Type}); cleanup skipped.` and return.
   - `IsLink` true (or throws) → Warning `AI file folder is a junction or symbolic link; cleanup skipped.` and return.
   - Delete every file directly in the folder whose name passes
     `IsTempFileName` (through the same delete-with-retry path as
     `Discard`). Other files and subfolders are left alone.
   - Enumeration failure → Warning `AI file cleanup failed ({Type}).`
   - When at least one file was deleted: Debug `AI file folder cleaned ({Count} files).`
5. No log call takes the folder, a path or a file name.

### B. `AiAttachmentCom`

As the signatures say. `IsCloud(7, 1)`: true; `IsCloud(7L, 1)`: true;
`IsCloud(null, 4)`: true; `IsCloud("7", 1)`: false. `CloudUrl` checks
`longFileName` first. `Item` never trims the subject or body text
itself (only the From parts are trimmed for the blank check and the
format).

### C. `ReadAttachmentForAi` (worker thread)

```
validate arguments
ResolvedMailItem<Outlook.MailItem> r;
try { r = Resolve(app, entryId); } catch (ItemNotFoundException) { return null; }
var item = r.Item;
Outlook.Attachments? atts = null; Outlook.Attachment? att = null; Outlook.PropertyAccessor? pa = null;
try
{
    var live = ReadAttachments(item);                         // existing helper, releases its own objects
    var m = AttachmentSelection.MatchLive(live, wanted);
    if (m is null) return new AiAttachmentRead.NotOnEmail();
    atts = item.Attachments;
    att = atts[m.Position];
    var type = (int)att.Type;
    pa = ComSafe.Try(() => att.PropertyAccessor);
    var method = pa is null ? null : ComSafe.Try(() => pa.GetProperty(AiAttachmentCom.PrAttachMethod));
    if (AiAttachmentCom.IsCloud(method, type))
        return new AiAttachmentRead.Cloud(
            AiAttachmentCom.CloudUrl(pa is null ? null : ComSafe.Try(() => pa.GetProperty(AiAttachmentCom.PrAttachLongFileName)),
                                     pa is null ? null : ComSafe.Try(() => pa.GetProperty(AiAttachmentCom.PrAttachLongPathName))),
            ComSafe.Try(() => att.DisplayName) ?? m.FileName);   // nothing saved
    var size = ComSafe.Try<long?>(() => (long)att.Size);
    if (size is { } s && s > maxBytes) return new AiAttachmentRead.TooLarge(s);   // nothing saved
    return type switch
    {
        AiAttachmentCom.OlByValue => ReadFileForAi(att, maxBytes, files),
        AiAttachmentCom.OlEmbeddedItem => ReadItemForAi(app, att, maxBytes, files),
        _ => new AiAttachmentRead.Failed("UnsupportedAttachmentType"),
    };
}
catch (Exception ex) when ((ex is COMException or IOException or UnauthorizedAccessException)
                           && !ComErrors.IsOutlookGone(ex))
{
    return new AiAttachmentRead.Failed(ex.GetType().Name);    // AiFolderUnusableException is an IOException
}
finally { Release(pa); Release(att); Release(atts); Release(item); }
```

- `mailbox` is validated (not null) and otherwise unused: the §8 chain
  locates the item through the index, as `OutlookAiMailbox.GetFacts`
  does. Don't add a store lookup.
- `ReadFileForAi`:
  ```
  var path = files.PrepareTempPath(item: false);
  try
  {
      att.SaveAsFile(path);
      var len = new FileInfo(path).Length;
      if (len > maxBytes) return new AiAttachmentRead.TooLarge(len);
      return new AiAttachmentRead.File(File.ReadAllBytes(path));
  }
  finally { files.Discard(path); }
  ```
- `ReadItemForAi`:
  ```
  var path = files.PrepareTempPath(item: true);
  Outlook.NameSpace? ns = null; object? opened = null;
  try
  {
      att.SaveAsFile(path);
      var len = new FileInfo(path).Length;
      if (len > maxBytes) return new AiAttachmentRead.TooLarge(len);
      ns = app.Session;
      opened = ns.OpenSharedItem(path);
      if (opened is not Outlook.MailItem mi) return new AiAttachmentRead.Failed("NotAMailItem");
      try
      {
          subject = ComSafe.Try(() => mi.Subject); name = ComSafe.Try(() => mi.SenderName);
          address = ComSafe.Try(() => mi.SenderEmailAddress);      // raw, no Exchange resolution
          sent = OutlookDates.FromLocal(ComSafe.Try(() => mi.SentOn), TimeZoneInfo.Local);
          body = ComSafe.Try(() => mi.Body);
          names = up to MaxItemAttachmentNames names: loop mi.Attachments 1..min(Count, 50), each
                  InlineAttachments.FileNameFor(FileName, DisplayName, Index), release each in the loop,
                  release the collection in finally
          return AiAttachmentCom.Item(subject, name, address, sent, body, names);
      }
      finally { ComSafe.Try(() => { mi.Close(Outlook.OlInspectorClose.olDiscard); return 0; }); }
  }
  finally { Release(opened); Release(ns); files.Discard(path); }
  ```
  Order matters: close, then release, then discard (Outlook holds the
  `.msg` open until then; a failed delete is retried before the next
  save and at the next start). `ComSafe.Try` on `SentOn` gives
  `default(DateTime)`, which `FromLocal` maps to null.
- The item is never saved, displayed, sent, moved or copied. No
  property is assigned on any Outlook object in these methods.
- No log calls in `OutlookMail.Attachments.cs`.
- A worker timeout leaves the work item running on its thread; its own
  `finally` still discards the file. No abandon token is needed (unlike
  `SaveAttachmentForLink`, nothing outlives the work item).

### D. `OutlookAttachmentSource`

- `ReadAsync`: `ArgumentNullException` for `mailbox`, `entryId`,
  `wanted`; then
  `await stores.EnsureResolvedAsync(priority, ct)` and

### `AiFilesTests` (Core)

Setup: `_dir` = new temp folder; `Folder = Path.Combine(_dir, "ai-files")`;
`EnsurePrivateFolder = d => { ensureCalls++; Directory.CreateDirectory(d); }`;
a test `ILinkFileSystem` that wraps the real one with switches
(`IsLinkResult`, `DeleteThrowsTimes`, `EnumerateThrows`).

1. `AiFilePaths.Default(<fully qualified temp>)`.`Folder` ==
   `Path.Combine(x, "ClippysRevenge", "ai-files")`; `Default("")`,
   `Default("rel\\x")` → `ArgumentException`.
2. `NewFileName(false)` matches `^[0-9a-f]{32}\.bin$`, `NewFileName(true)`
   matches `^[0-9a-f]{32}\.msg$`; 1,000 calls give 1,000 distinct names.
3. `IsTempFileName`: true for 32 hex + `.bin` and + `.msg`; false for
   upper-case hex, `.BIN`, `.tmp`, 31 or 33 hex, `x.bin`, `""`, null.
4. `PrepareTempPath(false)`: `ensureCalls == 1`, the folder exists, the
   returned path's directory equals `Folder`, the name passes
   `IsTempFileName` and ends `.bin`, and no file exists at it.
   `PrepareTempPath(true)` ends `.msg`.
5. Ensure throws `IOException("C:\\secret\\" + M)`:
