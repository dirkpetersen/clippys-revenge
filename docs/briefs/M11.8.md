# M11.8 Tray and Settings UI for AI drafts

Base: `dev` with M11.1–M11.7 merged, plus the `StyleGuideSource` wiring
in `Program.cs` (776dc84). This task is the UI over APIs that already
exist:
- `DraftWorker`: `DraftSelectedAsync`, `ReportStatus`,
  `NotifySettingsChanged`, `ModelCallsToday`.
- `DraftModelSwitch.CheckAsync` and `ClaudeCliModel.InvalidateStatus`.
- `SettingsStore`: `SaveApiKey` and `LoadApiKey`.
- `StyleSkill`: `GetStatus`, `RegenerateAsync`, `Files.ReadSkillText`
  and `Files.Paths`.
- `IAiMailbox.ShowDraftsAsync`.

Core gets the presenters, texts and two small services so the decisions
can be tested on Linux. The WinForms code stays thin.

## Goal

Give the user the AI drafting controls (SPEC §19.10, §6.2, §6.3, §6.5,
§19.2, §19.6, §19.7 manual path, §1.10).

**Tray: the "AI drafts" submenu.**
- *Draft replies automatically* toggles `Enabled`. Consent comes first.
  When the backend isn't ready, Settings opens on the AI drafts tab
  instead.
- *Draft a reply to the selected email* runs the manual path (consent
  first).
- *Show Drafts in Outlook* is hidden while Outlook isn't running.
- *AI drafts settings…* opens the tab.

**Consent dialog.** The exact §19.10 text, with **Turn on** and
**Cancel** (the default, also on Esc).

**Balloon.** A click on the "I drafted <n> replies" balloon shows the
Drafts folder.

**Settings → AI drafts tab:**
- enable checkbox;
- backend radios, status line and **Check**;
- API key box with **Save key** and **Remove key**;
- Claude Code path, model, effort, daily limit, minimum confidence, max
  age, *Only when I'm in To or CC*;
- the two sender lists;
- per-mailbox opt-in;
- writing style status, *Update weekly*, **View**, **Regenerate**,
  **Open in editor**;
- the "Today:" line and the manual link.

`SettingsEditor` gets the M11.1 carry-overs:
- `Rebase` adopts AI changes made from the tray.
- An apply never clears or changes `ConsentedAtUtc`.
- `AiDrafting.*` errors map to the new tab.

## Hard rules that apply here

- **No sign-in, no credentials (§1.10, §19.5).**
  - Nothing here offers a claude.ai sign-in, opens a sign-in page, runs
    `claude` with any argument, or reads any Claude credential.
  - When Claude Code isn't signed in, the UI shows the §19.3 status text,
    which tells the user to run `claude` in a terminal and sign in
    there, plus `AiTabTexts.SignInHint`. That is all.
  - Status checks only go through `IDraftModel.CheckAsync` (M11.4/M11.5).
- **The API key is never shown or logged.**
  - The key box is masked. It starts empty and is cleared after every
    Save, so it never shows a saved key.
  - The UI knows only "a key is saved" or "no key is saved".
  - Only `Program` calls `store.LoadApiKey()`, inside the `HasApiKey`
    delegate, which returns a `bool`. No code in `Tray/` sees the key.
  - Save and Remove use `Program`'s single `SettingsStore`, so
    `CachedApiKey` (log redaction) stays current.
  - No logging or status text contains the key. `SaveApiKey`'s
    `ArgumentException` messages never include it.
- **Never send, never launch.**
  - *Show Drafts* is `IAiMailbox.ShowDraftsAsync`, which sets
    `CurrentFolder` and calls `Activate()` (M11.7). It never calls
    `.Display()` and never starts Outlook.
  - The manual path is `DraftWorker.DraftSelectedAsync`. No new COM code
    is added in this task.
- **Process starts.** `TrayApp.cs` keeps exactly one `Process.Start`,
  now in `TrayApp.ShellOpen(string target)`. It hands the shell a path
  or URL, with no arguments and no command line. *Open in editor*, *Open
  log/data folder* and the manual link all go through it (§F, §T12).
- **UI thread.** The window and the tray never run a model call, a
  status check, SQLite, DPAPI or COM on the UI thread (§19.10). They
  `await` work that runs on the pool or on the COM worker.

## Behavior

### A. Core presenters

**A.1 `AiDraftsMenu.Build(live, available, outlookUnavailable, busy)`**:
- `AutoChecked = live.Enabled && live.HasConsent`
- `AutoEnabled = available && !busy`
- `DraftSelectedEnabled = available && !outlookUnavailable`
- `ShowDraftsVisible = !outlookUnavailable` (§19.10 "hidden while Outlook isn't running")
- `ShowDraftsEnabled = available`

*AI drafts settings…* isn't in the model. It is enabled whenever the
tray can open Settings.

**A.2 `AiToggle.Next(live)`**:
- `live.Enabled` → `TurnOff`. This includes the invalid state
  `Enabled` without consent.
- Else `!live.HasConsent` → `AskConsent`.
- Else → `CheckBackend`.

`AfterCheck(status)`: `status.Ready` → `TurnOn`, otherwise
`OpenSettings`.

**A.3 `AiTabFields.For(field)`**: strip the `AiDrafting.` prefix
(Ordinal). Take the name up to the first `[`, then use `Enum.TryParse`
with `ignoreCase: false` against the `AiTabField` names. `None` itself
never matches, and neither does a field without the prefix. So
`AiDrafting.TimeoutSeconds`, `AiDrafting.ConsentedAtUtc` and `Port` give
`None`.

**A.4 `AiDraftingToggler`**. Every mutation follows this pattern:

```csharp
settings.Gate.Wait();
try
{
    var next = settings.Clone();
    edit(next.AiDrafting);      // RecordConsent(now) / SetEnabled(enabled, now)
    save(next);                 // throws → live unchanged
    settings.AiDrafting = next.AiDrafting;
}
finally { settings.Gate.Release(); }
changed();                      // outside the gate
```

`now = time.GetUtcNow()`. `changed()` exceptions propagate to the
caller; the tray catches them, see §C.

**A.5 `AiStatusChecker.CheckAsync(refresh, ct)`**: as in the signature.
The log line is `"AI drafts: status check failed ({Type})."`. It never
logs the status text, which may contain the auth method. That text is
safe to show, but it isn't needed in the log.

**A.6 `AiOwner.ResolveAsync`**: as in the signature. Program uses it for
both of these, so there is one owner rule:
- the `StyleGuideSource` owner (`WorkPriority.Background`);
- Settings → Regenerate (`WorkPriority.Interactive`).

### B. Texts (copy exactly)

**B.1 Consent.** As in `AiConsent` (SPEC §19.10 verbatim).

**B.2 `Today(calls, cap, drafts)`**:
- `Today(3, 30, 1)` → `Today: 3 of 30 Claude calls, 1 draft`
- `Today(0, 30, 0)` → `Today: 0 of 30 Claude calls, 0 drafts`
- `Today(1200, 500, 2)` → `Today: 1,200 of 500 Claude calls, 2 drafts`

Only `drafts == 1` is singular (Spec changes #6). The cap is the
**live** `DailyCap`, the one the worker enforces.

**B.3 `PendingCheckNote(draft, live)`**: `CheckNote` when
`draft.Backend != live.Backend`, or `draft.Model != live.Model`
(Ordinal), or the trimmed `ClaudeCliPath`s differ (OrdinalIgnoreCase).
Otherwise `""`.

**B.4 Key and file texts.** As in the constants.

**B.5 `StyleResult(r)`**:

| `r` | Text |
|---|---|
| `Updated(n, _)` | `Writing style updated from <n> sent emails.` (N0) |
| `TooFewEmails(n)` | `Only <n> sent emails found. Clippy needs 20.` (the 20 is `StyleCorpus.MinSamples`) |
| `Failed(reason)` | `Writing style not updated: <reason>.` |
| `NoConsent` | `AiDraftingSettings.ConsentRequiredMessage` |
| `Busy` | `Your writing style is already being updated.` |
| `Edited`, `NotDue` | `Your writing style was kept.` |

**B.6 `ErrorText(e, draft)`**:
- When `e.Field` matches `^AiDrafting\.(ExcludeSenders|IncludeOnlySenders)\[(\d+)\]$`,
  `draft` isn't null and the index is in range, the text is
  `"<entry>": <message>`. `<entry>` is the list entry, trimmed, with
  control characters removed, and cut with `TrayText.Truncate(…, 60)`.
- Otherwise it is `e.Message` unchanged. The entry is user-typed, not
  mail data.

### C. Tray (`TrayApp`)

**Menu.** Add `_ai = new ToolStripMenuItem(AiMenuTexts.Submenu)` right
after `_shared`, in the same group as §6.2. Its drop-down holds:
- `_aiAuto` (`CheckOnClick = false`);
- `_aiDraftSelected`;
- `_aiShowDrafts`;
- a separator;
- `_aiSettings` → `ShowSettings(SettingsTab.AiDrafts)`. It is enabled
  when `CreateSettingsForm` is not null.

In the existing `_menu.Opening` handler and in `_ai.DropDownOpening`,
apply `AiDraftsMenu.Build(_s.GetSettings().AiDrafting, _s.Ai is not null,
_s.IsOutlookUnavailable(), _aiBusy == 1)` to `Checked`, `Enabled` and
`Visible`.

**Draft replies automatically** (`async void`, UI thread). Guard it
with `Interlocked.Exchange(ref _aiBusy, 1)`. A click while busy does
nothing.

```text
step = AiToggle.Next(live.AiDrafting)
TurnOff     → Toggler.SetEnabled(false); done
AskConsent  → if (!AiConsentDialog.Ask(null)) done; Toggler.RecordConsent(); fall through
CheckBackend→ status = await Checker.CheckAsync(refresh: false, CancellationToken.None)
              AfterCheck(status) == OpenSettings → ShowSettings(SettingsTab.AiDrafts); done (Enabled stays false)
              TurnOn → Toggler.SetEnabled(true)
```

- Wrap the whole flow in `try/catch` for `IOException`,
  `UnauthorizedAccessException` and `InvalidOperationException`. Each →
  `PostUserFeedback(AiMenuTexts.ToggleFailed(ex.Message))`.
- `finally` resets `_aiBusy`.
- Consent recorded in the dialog stays recorded even when the backend
  isn't ready (§19.2: it is never cleared).

**Draft a reply to the selected email** (`async void`):
1. If `!live.AiDrafting.HasConsent`: ask with `AiConsentDialog.Ask(null)`.
   Cancel → done. Turn on → `Toggler.RecordConsent()`. Its IO errors
   are handled as in the toggle.
2. `r = await Ai.DraftSelected(CancellationToken.None)`, then
   `_s.Balloons.PostUserFeedback(r.Message)`.
   - `DraftSelectedAsync` never throws except cancellation. Any other
     exception → `PostUserFeedback(DraftTexts.ManualFailed("something went wrong (" + ex.GetType().Name + ")"))`.
   - No busy guard: two clicks queue (M11.7 §C.8).

**Show Drafts in Outlook**, and a click on a `ShowDrafts` balloon:
`ok = await Ai.ShowDrafts(CancellationToken.None)`. When it's false,
call `PostUserFeedback(BalloonTexts.NoOutlookWindow)`. Exceptions are
handled the same way (type name only).

**Balloon click**:
- `OnBalloon` stores `_lastBalloonAction = b.Action` before
  `ShowBalloonTip`.
- `_notify.BalloonTipClicked` → if `_lastBalloonAction ==
  BalloonAction.ShowDrafts` and `_s.Ai` isn't null, run Show Drafts.
- `BalloonTipClosed` and `BalloonTipClicked` both reset it to `None`.

A user-feedback balloon replaces a pending action, because it has
`Action None`. A click on the toast after it moved to the Action Center
doesn't raise the event. That's accepted.

**`ShellOpen`** (the one `Process.Start` in the file):

```csharp
/// <summary>Hands a folder, a file or an https URL to the Windows shell (Explorer, the user's default editor or
/// browser). Never a command line, never arguments. The one Process.Start in TrayApp.</summary>
internal static void ShellOpen(string target)
{
    Process.Start(new ProcessStartInfo(target) { UseShellExecute = true })?.Dispose();
}

private static void OpenFolder(string path)
{
    Directory.CreateDirectory(path);
    ShellOpen(path);
}
```

`ShellOpen` throws whatever `Process.Start` throws (`Win32Exception`,
`InvalidOperationException`). Callers catch.

### F. `Process.Start` allow-list (asked in the task)

These scans exist today:
- `ProcessStart_OnlyInOutlookLauncher_AndLauncherUsesNoCom` allows
  `Process.Start` only in `OutlookLauncher.cs`, `TrayApp.cs` and
  `ClaudeCli.cs`.
- The same test asserts **exactly one** `Process.Start` in `TrayApp.cs`,
  matched by the regex
  `void\s+OpenFolder\s*\(string path\)\s*\{[^}]*Process\.Start\(new ProcessStartInfo\(path\)`.
- `ClaudeCli_StartsProcessesSafely` allows `UseShellExecute = true` only
  in `TrayApp.cs` and `OutlookLauncher.cs`.

*Open in editor* through `UseShellExecute` is a second shell open, so:
- It must **not** be written in `SettingsForm.cs`. That file isn't on
  the allow-list.
- It must **not** be a second `Process.Start` in `TrayApp.cs`.

The design above meets both: one `ShellOpen` in `TrayApp.cs`, which
`OpenFolder`, the manual link and *Open in editor* all call, the last
two through the `AiSettingsServices.ShellOpen` delegate. The allow-list
of files doesn't change. Only the pinned regex changes (§T12 #1).
`ClaudeCli*` keeps `UseShellExecute = false`, and the
`UseShellExecute = true` rule still holds.

If a later task needs a shell open outside `TrayApp.cs`, route it
through `TrayApp.ShellOpen`. Don't add a file to the allow-list.

`UseShellExecute` on a file path calls `ShellExecuteEx` with the path as
`lpFile` and no parameters. No command line is parsed and `cmd.exe`
isn't involved. Only these targets are ever passed:
- the fixed `StylePaths.UserSkillFile` (after `StyleEditorTarget`
  checks it);
- its folder;
- the log and data folders;
- the constant `ManualUrl`.

None comes from a tool, the model or mail, so `PathPolicy` doesn't
apply (§19.6 "fixed app paths").
