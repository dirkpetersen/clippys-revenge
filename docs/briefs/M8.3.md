# M8.3 `InviteConfirmForm` + confirmation queue + `AwaitingConfirmation` state

## Goal

Build the user-confirmation step that sits between "recipients resolved"
and "meeting created" in `send_meeting_invite` Send mode (SPEC §6.6,
§11.9, §6.1, §7, §12 `InviteGate`). Core gets: a view model that turns an
invite into the exact texts the dialog shows (`InviteConfirmView`), the
"outside your organization" rule (`InviteAttendees.IsExternal`), and a
FIFO queue (`InviteConfirmQueue`) that shows one dialog at a time, owns
the timeout, holds an `ActivityState.AwaitingConfirmation` scope on
`ActivityHub` while a dialog is open, and returns
`(Choice?, TimedOut)`. M8.4 passes that straight into
`InviteGate.Decide`. The App gets the WinForms `InviteConfirmForm` and a
thin `InviteConfirmPresenter` that implements the Core presenter interface
on the UI thread. **Nothing in this task touches COM, creates a meeting,
or sends anything.** The COM worker is never involved: the queue only
awaits the UI (§6.6 last bullet).

    public const string DialogFailedMessage =
        "The confirmation dialog could not be shown, so the invite was not created. Ask the user to check the Clippy's Revenge tray icon, then try again.";

    public string Heading { get; }            // InviteConfirmTexts.Heading

    /// <summary>
    /// Shows one dialog and completes when it has closed: with the button the user
    /// clicked, or null when it closed any other way. When <paramref name="dismiss"/> is
    /// signalled the presenter must close the dialog and then complete (any value).
    /// Must never complete before the window is closed (or was never shown).
    /// </summary>
    Task<InviteChoice?> ShowAsync(InviteConfirmView view, DateTimeOffset deadline, CancellationToken dismiss);

    /// Queues the dialog, waits for its turn, shows it, and returns the user's answer.
    /// </summary>
    /// <exception cref="ArgumentNullException">view is null.</exception>
    /// <exception cref="ArgumentOutOfRangeException">timeout &lt;= TimeSpan.Zero.</exception>
    /// <exception cref="OperationCanceledException">ct was cancelled (before or while queued or shown).</exception>

    public void Dispose();

## Behavior

### `InviteAttendees.IsExternal(email, isExchangeEntry, organizerSmtp)`

M8.4 computes `InviteAttendee.External` with this helper from the COM
facts it has after resolving (`isExchangeEntry` = the resolved
`AddressEntry.AddressEntryUserType` is an Exchange user, distribution list,
remote user, public folder or agent; the organizer SMTP is the own or
shared mailbox's primary SMTP). Rule, in order:

1. `isExchangeEntry` → `false` (internal).
2. `email` or `organizerSmtp` null/blank, or either lacks exactly one `@`
   with text after it → `true`.
3. Let `d` = domain of `email`, `o` = domain of `organizerSmtp` (text after
   `@`, trimmed, ordinal-ignore-case). `d == o` or `d` ends with `"." + o`
   → `false`. Otherwise `true`.

Never throws. Unknown is external: the highlight errs toward warning.

### `InviteConfirmView.Create`

- Validates as listed under Public API. Throws before formatting anything.
- `OrganizerLine` = `"From: " + Organizer.Trim()`, plus `" (shared mailbox)"`
  when `OrganizerIsShared`.
- `Subject` = `Subject.Trim()`, or `NoSubject` when that is empty.
- `WhenShort`: call `SlotFormatter.Format(1, Start, End, timeZoneLabel,
  workStartHour, workEndHour)` and strip the leading `"1. "`. If
  `SlotFormatter` throws `ArgumentException` because the slot spans days
  (not `ArgumentOutOfRangeException`, which propagates), `WhenShort` is
  `null`. Do not re-implement the same-day rule; catch it. (Order matters:
  `ArgumentOutOfRangeException` derives from `ArgumentException`, so catch
  it first and rethrow.)
- `WhenFull`, `InvariantCulture`, en dash `–` with spaces:
  - Same calendar date: `"dddd, MMMM d, yyyy, h:mm tt"` for start, then
    `" – "`, then `"h:mm tt"` for end.
    `Tuesday, October 15, 2024, 1:00 PM – 3:00 PM`
  - Different dates (including ending at midnight next day): both in the
    full form. `Tuesday, October 15, 2024, 10:00 PM – Wednesday, October 16, 2024, 1:00 AM`
  - If `timeZoneLabel` is non-blank, append `" " + label.Trim()`.
- `LocationLine` = `"Location: " + Location.Trim()`, or `"Location: (none)"`
  when null/blank. `TeamsLine` = `"Teams meeting: yes"` / `"Teams meeting: no"`.
- `Recipients`: one line per attendee, in input order. Text is
  `Recipients.Format([new Recipient(Name, Email)])` (reuse the existing
  helper: bare email when the name is empty), plus `ExternalSuffix` when
  `External`. `RecipientsHeader` = `"To (<n>):"`, n = count, invariant.
- `ExternalSummary`: `null` for 0 external; `"1 recipient is outside your organization."`;
  `"<n> recipients are outside your organization."` for n ≥ 2.
- `Body`: null/whitespace → `NoBody`. Otherwise normalize `\r\n`, lone `\r`
  and lone `\n` to `\r\n` (for a WinForms TextBox). Do not trim, escape or
  truncate: the user must see exactly what will be sent (§6.6).

### `InviteConfirmTexts.Countdown(remaining)`

`s = max(0, ceil(remaining.TotalSeconds))`, then
`"Saved as draft in {s/60}:{s%60:00} unless you choose."` (invariant).
120 s → `Saved as draft in 2:00 unless you choose.`

### `InviteConfirmQueue`

- Strict FIFO by call order of `ConfirmAsync`. Exactly one presenter
  `ShowAsync` is outstanding at any time. Implement with a lock-protected
  `LinkedList`/`Queue` of entries each holding a
  `TaskCompletionSource<InviteConfirmOutcome>` created with
  `TaskCreationOptions.RunContinuationsAsynchronously`. Not `SemaphoreSlim`
  (not FIFO-guaranteed).
- `ConfirmAsync` argument checks throw synchronously (not in the task). If
  disposed → faulted task with `McpException(ShutdownMessage)`. If `ct` is
  already cancelled → cancelled task; nothing is queued, `Pending` unchanged.
- **The timeout starts when the dialog is shown**, not when it is queued.
  `deadline = time.GetUtcNow() + timeout` taken immediately before
  `ShowAsync`; the presenter gets that deadline. A one-shot
  `time.CreateTimer` due at `timeout` fires the timeout.
- Immediately before `ShowAsync`: `hub.Begin(ActivityState.AwaitingConfirmation, "")`.
  The scope is disposed when the presenter task has completed (dialog
  closed), in a `finally`, on every path.
- Resolution of the shown entry — the first of these wins (guard with a
  single "resolved" flag under the lock):
  1. **Presenter completes** with `c` (no dismiss signalled yet):
     outcome `(c, TimedOut: time.GetUtcNow() >= deadline)`. A click
     reported at or after the deadline counts as timed out even if the
     timer callback hasn't run yet; `InviteGate` then yields
     `SaveDraft(timeout)` for Send/SaveDraft and `Cancel` for Cancel.
  2. **Timer fires**: signal `dismiss`, await the presenter task, ignore its
     value, outcome `(null, true)`.
  3. **`ct` cancelled while shown**: signal `dismiss`, await the presenter,
     then complete the entry as cancelled (`OperationCanceledException`
     carrying `ct`).
  4. **Presenter throws** (or its task faults) at any point before 1–3:
     outcome is a fault with `McpException(DialogFailedMessage)` (inner =
     original). Log nothing here (Core has no logger); the tool records it.
- `ct` cancelled while **queued**: remove the entry, cancel its task, never
  show it. Use `ct.Register`; dispose registrations when the entry finishes.
- The next entry is shown only after the current presenter task has
  completed (the window is gone) **and** the hub scope is disposed.
  Never two dialogs, even after a timeout or cancellation.
- `Pending` = queued entries + 1 if one is shown. Decrements when an entry's
  task is completed.
- `Dispose()`: set disposed; complete every queued entry with
  `McpException(ShutdownMessage)`; signal `dismiss` for the shown entry and
  complete it with the same exception (don't wait for the presenter;
  `Dispose` is synchronous and may be called on the UI thread). Dispose the
  timer and hub scope. Second call no-op.
- The queue never records `ActivityHub.Event`s and never posts balloons:
  the `Invite` event and the sent/timeout notification are M8.4's (§11.9).
- Thread-agnostic: no `SynchronizationContext` capture
  (`ConfigureAwait(false)` everywhere), no `.Result`/`.Wait()`.

### `InviteConfirmForm` (App)

- Topmost without stealing focus: override `ShowWithoutActivation => true`
  and add `WS_EX_TOPMOST` in `CreateParams`. **Do not set `TopMost = true`**
  (that activates the window). No owner, `ShowInTaskbar = true` so the
  user can find it, `FormBorderStyle.FixedDialog`, no minimize/maximize,
  `StartPosition = Manual` at the bottom-right of the primary screen's
  working area (near the tray).
- Layout top to bottom, all text from the view: `Heading`, `OrganizerLine`,
  `Subject` (bold), `WhenShort` (if not null), `WhenFull`, `LocationLine`,
  `TeamsLine`, `RecipientsHeader`, a recipients `ListView` (Details, one
  column, read-only) where external rows have bold font, a light amber
  back colour and the `ExternalSuffix` text (not colour alone),
  `ExternalSummary` (if not null) in bold, the `Body` in a read-only,
  multiline, vertically scrolling `TextBox` (`WordWrap = true`), the
  countdown label, then the buttons **Send**, **Save as draft**, **Cancel**.
- `AcceptButton = CancelButton = cancel button`; Cancel gets initial focus
  (`ActiveControl`). Enter and Esc both close as Cancel; Enter never sends.
- A WinForms `Timer` (250 ms) updates the countdown with
  `InviteConfirmTexts.Countdown(deadline - now)`. When remaining ≤ 0 it
  shows `SavingNow` and disables Send and Save as draft. The form never
  closes itself on the timeout: the queue dismisses it.
- Buttons set `Choice` and `Close()`. Closing any other way (title-bar X,
  Alt+F4, dismiss) leaves `Choice` null. Dispose the timer on close.
- No `.Send(` text anywhere in this file (the §15 source scan counts it).

### `InviteConfirmPresenter` (App)

- `ShowAsync` creates a `TaskCompletionSource<InviteChoice?>`
  (`RunContinuationsAsynchronously`) and **`ui.Post`s** (never
  `SynchronizationContext.Send`, which the safety scan would also count):
  if `dismiss` is already cancelled, complete `null` without showing;
  otherwise create the form, hook `FormClosed` → `TrySetResult(form.Choice)`
  then `form.Dispose()`, call `form.Show()`, and register
  `dismiss.Register(() => ui.Post(_ => { if (!form.IsDisposed) form.Close(); }, null))`.
  Dispose the registration in `FormClosed`.
- Exceptions while building or showing the form → `TrySetException`.

### `Program.cs`

After `var tray = new TrayApp(...)` (the UI `SynchronizationContext` now
exists): `var inviteQueue = new InviteConfirmQueue(new InviteConfirmPresenter(SynchronizationContext.Current!), hub);`
add `.AddSingleton(inviteQueue)` to `ConfigureServices`, and call
`inviteQueue.Dispose()` right after `Application.Run(tray)` returns, before
the host is disposed. No other wiring; no tool uses it yet.

## Cross-task dependencies

- **M5.1 (OutlookWorker)**: none. The queue deliberately never runs on the
  worker (§6.6). Assumed only that M8.4 resolves recipients via
  `RunAsync(..., Priority.Interactive, ct)` *before* calling
  `ConfirmAsync`, and creates the meeting in a second `RunAsync` after.
- **M5.2 (OutlookStores)**: none directly. M8.4 needs the organizer's
  primary SMTP (own or shared, §8) for `IsExternal`.
- **M8.4 (`send_meeting_invite`)**, assumed usage, Send mode only:
  ```csharp
  var view = InviteConfirmView.Create(req, TimeZoneLabels.Resolve(s.TimeZoneLabel, TimeZoneInfo.Local, start),
                                      s.WorkStartHour, s.WorkEndHour);
  var o = await queue.ConfirmAsync(view, TimeSpan.FromSeconds(s.InviteConfirmTimeoutSeconds), ct);
  var decision = InviteGate.Decide(s.MeetingInviteMode, o.Choice, o.TimedOut);
  ```
  M8.4 must build `InviteAttendee.External` with `InviteAttendees.IsExternal`
  and must not define its own external rule. It reads `MeetingInviteMode`
  once, before calling `InviteGate.RequiresConfirmation`, and passes that
  same value to `Decide`. M8.4 owns the `Invite` event and balloons.
- **M9.x**: nothing; the form is complete here.

## Spec changes (proposed)

Append to SPEC §6.6 (after "Invite requests are queued, and only one
dialog is shown at a time."):

> - The countdown for each invite starts when its dialog is shown, not
>   when it is queued. A click at or after the deadline counts as a
>   timeout. If the tool call is cancelled, its dialog is closed (or never
>   shown) and nothing is created. On shutdown, pending invites fail with
>   "Clippy's Revenge is shutting down, so the invite was not created. Try
>   again after it restarts."
