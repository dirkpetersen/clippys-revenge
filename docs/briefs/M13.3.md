# M13.3 Model contract: `meeting` in the reply schema, `DraftReply.Meeting`, prompt rules, settings

Base: `dev` (M12 done). No dependencies. Runs beside M13.1 (meeting-time
primitives) and M13.5 (style skill meeting section). **M13.5 edits the
same file `DraftModel.cs`** (`StyleSchema`): this task touches only
`ReplySchema`, `DraftReply` and the new `MeetingAsk` there, so the two
merge cleanly. Don't touch `StyleSchema` or its test.

## Goal

Pin the model side of meeting times in AI drafts (SPEC §19.7 "Reply
JSON" and "Drafting prompt", §19.2, §21.1, §21.4 heading, §21.6, §21.9
`DraftReply.Parse`). The reply schema gets the optional `meeting` object;
`DraftReply.Parse` reads it tolerantly into `DraftReply.Meeting`
(`MeetingAsk`, null when no meeting was asked) and never lets it make a
reply invalid; `DraftPrompt.SystemPrompt` gets the meeting rules (exact
text below), added only when the caller says `MeetingTimes` is on; and
`AiDraftingSettings` gets `MeetingTimes` (default `true`) and
`MeetingTimeOptions` (default `5`, 1–10) with validation and JSON. No
free/busy, no insertion, no `DraftWorker` change: that is M13.4.

## Hard rules that apply here

- **The model gets no tools and never sees times.** This task only adds
  schema fields and prompt text that ask the model to *say* a meeting
  was asked for and to leave `[[meeting_times]]`. Nothing here reads a
  calendar.
- **Never send / never delete.** Untouched; no COM code in this task.
- **Never touch Claude credentials.** No change to either backend.
- `reason` is still validated for type only and never stored, logged or
  shown. The same goes for every `meeting` field: `MeetingAsk` is never
  logged (it can quote a heading the model wrote from mail text).

### A. `DraftModel.ReplySchema` (exact, compact, one line)

### B. `DraftReply` and `MeetingAsk` (`DraftModel.cs`)

```csharp
/// <summary>The validated, used part of a reply. `reason` is validated for type and then dropped (SPEC 19.7).
/// Meeting: null when no meeting was asked (SPEC 19.7, 21.6).</summary>
public sealed record DraftReply(bool NeedsReply, double Confidence, bool? ReplyAll, string? BodyHtml,
    MeetingAsk? Meeting = null)
{
    public static DraftReply? Parse(JsonElement output);   // unchanged contract: null when invalid, never throws
}

/// <summary>What the model said about a meeting (SPEC 19.7, 21.6). Only built when meeting.requested is true.</summary>
/// <param name="DurationMinutes">An integer in 15–480, else null (the caller uses DefaultDurationMinutes).</param>
/// <param name="EarliestDate">Exactly yyyy-MM-dd and a real date, else null.</param>
/// <param name="LatestDate">Same rule as EarliestDate. Not compared with EarliestDate here (M13.4 does the range).</param>
/// <param name="OutsideHoursHeading">The model's string as sent (not cleaned), or null when absent / not a string.
/// Cleaning and the fallback to the default heading are SPEC 21.4's rule, applied where the heading is used (M13.1/M13.4).</param>
public sealed record MeetingAsk(int? DurationMinutes, DateOnly? EarliestDate, DateOnly? LatestDate, string? OutsideHoursHeading)
{
    public const int DefaultDurationMinutes = 60;
    public const int MinDurationMinutes = 15;
    public const int MaxDurationMinutes = 480;

    /// <summary>The "meeting" property value. Null when it isn't an object or requested isn't JSON true.
    /// Never throws (any exception gives null).</summary>
    public static MeetingAsk? Parse(JsonElement meeting);
}
```

`DraftReply`'s new parameter is optional, so existing
`new DraftReply(true, 0.8, true, "<p>Hi</p>")` calls (tests,
`DraftWorker`) still compile and mean `Meeting = null`.

## Behavior

### `DraftReply.Parse`

1. All existing checks run first and unchanged (types, `confidence`,
   `body_html` length, `reason` type, `needs_reply` with blank body).
   Their result decides validity alone.
2. Only after the reply is known valid: when `output` has a `meeting`
   property, `Meeting = MeetingAsk.Parse(that value)`; otherwise null.
   `meeting` never makes the reply invalid, whatever it holds
   (`"meeting": 5`, `[]`, `null`, `{}`, broken inner types).
3. `Meeting` is parsed regardless of `needs_reply` (the worker ignores it
   when no draft is made).

### `MeetingAsk.Parse(JsonElement meeting)`

- Not `JsonValueKind.Object` (incl. `Null`, `Undefined`/default) → null.
- `requested` missing or not JSON `true` (`false`, `"true"`, `1`,
  `null`) → null ("no meeting asked", SPEC §19.7).
- `duration_minutes`: kept when it is a JSON number for which
  `TryGetInt32` succeeds and the value is in 15–480 inclusive; anything
  else (missing, `null`, `14`, `481`, `30.5`, `30.0`, `1e2`, `"30"`,
  `-60`) → `DurationMinutes = null`. (`30.0` and `1e2` aren't integer
  tokens; `TryGetInt32` rejects them, which is the intended reading of
  "not an integer".)
- `earliest_date`, `latest_date` (each on its own): kept when it is a
  JSON string matching `^[0-9]{4}-[0-9]{2}-[0-9]{2}\z` (ordinal, no
  trimming) **and** `DateOnly.TryParseExact(s, "yyyy-MM-dd",
  CultureInfo.InvariantCulture, DateTimeStyles.None, out d)` succeeds.
  Otherwise null: `"2026-2-03"`, `" 2026-11-20"`, `"2026-11-20 "`,
  `"2026-02-30"`, `"20.11.2026"`, `"2026-11-20T00:00"`, `"٢٠٢٦-١١-٢٠"`
  (Arabic-Indic digits), a number, `null`.
- `outside_hours_heading`: a JSON string → that string as is (may be
  empty or long; no cleaning here); anything else → null.
- Unknown properties in `meeting` are ignored.
- Any exception inside → null (the outer reply still parses).

### `DraftPrompt.SystemPrompt`

- `meetingTimes = false` (default): output byte-for-byte identical to
  today's output for the same arguments.
- `meetingTimes = true`: `SystemTemplate` (filled) + `"\n\n"` +
  `MeetingNote` with `{name}` replaced by the same cleaned name used in
  the template (`the user` when blank), then, as before, the manual note
  (when `manual`) and the `<writing_style>` block. So the order is
  template, meeting note, manual note, style.
- The caller passes `AiDrafting.MeetingTimes`. **In this task nobody
  passes `true` yet**: `DraftWorker.BuildRequest` keeps calling the
  4-argument form. M13.4 passes `ai.MeetingTimes` in the same change
  that fills the placeholder, so no release asks the model for
  `[[meeting_times]]` without Clippy filling it.

### `AiDraftingSettings.Validate`

- Appended after the `ClaudeCliPath` checks (the SPEC §19.2 table order;
  `MeetingTimes` is a bool and has no check):
  `MeetingTimeOptions < 1 || > 10` → `SettingsError("AiDrafting.MeetingTimeOptions", "Must be between 1 and 10.")`.
- `FillDefaults` needs no change (no reference types added).
- JSON: plain properties, serialized as `"MeetingTimes": true` and
  `"MeetingTimeOptions": 5` by the existing `Settings.JsonOptions`;
  `Clone`/`CopyFrom` copy them through JSON as they do the other fields.
- `AiTabField` / `AiTabFields` are not changed here (M13.6 adds the
  controls and their error mapping). Until then an error on
  `AiDrafting.MeetingTimeOptions` maps to `AiTabField.None`, which the
  form already handles.

## Spec changes

None. Decisions within the spec, recorded here only:

- `MeetingAsk.OutsideHoursHeading` carries the model's raw string; the
  §21.4 cleaning/default rule is applied where the heading is used
  (M13.1's `MeetingOffers`, called from M13.4), so the rule exists once.
- "Not an integer" for `duration_minutes` means `JsonElement.TryGetInt32`
  fails (so `30.0` → 60).
- "Exactly `yyyy-MM-dd`" means ASCII digits in that shape and a real
  calendar date; no trimming.
- `MeetingTimeOptions` message `Must be between 1 and 10.` follows the
  other range messages of §19.2 (M11.1 table A style).
- The meeting note is appended as its own block after the template
  (before the manual note), not merged into the template's lists, so
  the prompt with `MeetingTimes` off stays byte-identical.
