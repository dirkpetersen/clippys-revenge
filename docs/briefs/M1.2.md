# M1.2 `FtsQuery` + tests

## Goal

Add `FtsQuery`, the pure Core helper that turns the free text a model passes
as `search_emails.query` (§11.1) into a safe SQLite FTS5 `MATCH` expression
(§9.2, last bullet; §3 layout `FtsQuery.cs`; §15 test row `FtsQuery`). Input
like `budget-2026`, `C++` or `O'Example` must never cause an FTS syntax error.
Tokens are ANDed, a trailing `*` is a prefix match, and an `OR` between tokens
becomes an FTS `OR`. The schema it targets (`emails_fts`, tokenizer
`unicode61 remove_diacritics 2`) is in §9.1. `EmailIndex` (M2) consumes it.
Nothing else is built here.

## Cross-task dependencies

None. `FtsQuery` uses only the BCL. The tests also use `Microsoft.Data.Sqlite`,
which Core already references (M0.1) and the test project gets transitively.
The tests don't use `EmailIndex` or any M2 code.

## Public API

```csharp
namespace ClippysRevenge.Core;

/// <summary>Builds a safe SQLite FTS5 MATCH expression from user/model free text (SPEC §9.2).</summary>
public static class FtsQuery
{
    /// <summary>
    /// Returns the MATCH expression, or null when the input has nothing searchable
    /// (null, empty, whitespace, or only punctuation/operators). Never throws.
    /// </summary>
    public static string? Build(string? userText);
}
```

- Never throws, for any input (including null, control characters, lone
  surrogates, very long strings).
- The result is meant to be **bound as a parameter** (`emails_fts MATCH @q`),
  never concatenated into SQL. Say so in the XML doc.
- `null` result means "no full-text filter". The caller (M2) must then omit
  the `MATCH` clause entirely. Put that in the XML doc too.
- Private helpers are fine (for example a `Quote(string)` that wraps in `"`
  and doubles any inner `"`). Don't add other public members.

## Behavior

Process the input in four steps.

**1. Scan into raw items**, left to right:
- Separators: `char.IsWhiteSpace(c) || char.IsControl(c)`.
- `"` begins a **phrase** only if another `"` occurs later in the string.
  The phrase is the text between the two quotes, and the scan resumes after
  the closing quote. A `"` also ends any bare token in progress, so `ab"cd ef"`
  gives bare `ab`, then phrase `cd ef`.
- A `"` with no later `"` (unbalanced) is treated as a separator.
- Any other run of characters is a **bare token**.

**2. Classify each item:**
- A bare token that equals `OR` (ordinal, **uppercase only**) is an OR
  marker. Lowercase `or`/`Or` is an ordinary search term. A quoted `"OR"` is
  always a phrase, never an operator.
- A bare token that ends in one or more `*` is a **prefix term**. Strip all
  trailing `*`. A `*` anywhere else stays in the text (the tokenizer
  ignores it): `*budg` → `"*budg"`, `bud*get` → `"bud*get"`.
- A `*` right after a closing phrase quote is not special. It's scanned as
  its own bare token `*`, which step 3 drops.
- Other bare tokens and all phrases are **plain terms**. Phrase text is trimmed
  but otherwise kept as it is.
- Other FTS5 keywords (`AND`, `NOT`, `NEAR`) and syntax characters (`-`, `+`,
  `^`, `:`, `(`, `)`, `{`, `}`) get no special handling. They end up
  inside quotes as literal text.

**3. Drop junk terms:** remove any term (after stripping `*`) that contains no
`char.IsLetterOrDigit` character, e.g. `-`, `+`, `&`, `*`, `""`, `" - "`.
Such terms would produce an FTS5 phrase with zero tokens under `unicode61`,
and an empty phrase in an AND chain makes the whole query match nothing.
This happens **before** OR handling, so `a OR - b` behaves like `a OR b`.

**4. Group and render:**
- Walk the remaining sequence of terms and OR markers. An OR marker joins
  the term before it and the term after it into one OR group. A leading
  OR, a trailing OR, or repeated ORs (`OR OR`) are ignored. Each term not
  joined by an OR is its own group.
- Render a term as `"` + text with every `"` doubled + `"`, and append `*`
  for a prefix term (no space): `"budg"*`.
- Render a group of one term as just that term. A group of two or more is
  rendered as `(` + terms joined by ` OR ` + `)`.
- Join groups with ` AND ` (explicit AND, single spaces).
- If there are no groups, return `null`.

Groups are always parenthesized, so the precedence is "OR binds tighter
than AND" (web-search style): `a b OR c` means a AND (b OR c). FTS5's own
precedence (OR lowest) never comes into play.

Reference outputs (C# string contents, shown without the outer C# quotes):

| Input | Output |
|---|---|
| `budget` | `"budget"` |
| `budget review` | `"budget" AND "review"` |
| `budget-2026` | `"budget-2026"` |
| `C++` | `"C++"` |
| `O'Example` | `"O'Example"` |
| `budg*` | `"budg"*` |
| `budg**` | `"budg"*` |
| `a OR b` | `("a" OR "b")` |
| `x a OR b OR c y` | `"x" AND ("a" OR "b" OR "c") AND "y"` |

| `say "hi` | `"say" AND "hi"` |
| `NOT secret` | `"NOT" AND "secret"` |

## Spec changes (proposed)

Replace the `FtsQuery.Build` bullet at the end of §9.2 with:

> - `FtsQuery.Build(string? userText)` → `string?`: quotes every token, so
>   input like `budget-2026`, `C++` or `O'Example` never causes an FTS syntax
>   error. It ANDs the tokens, keeps a trailing `*` as a prefix match, and
>   turns `OR` between tokens into an FTS `OR`. Details: only uppercase `OR`
>   is an operator, and OR binds tighter than AND (`a b OR c` → `"a" AND ("b" OR "c")`).
>   A balanced `"…"` is kept as one phrase, and an unbalanced `"` is a separator.
>   `AND`, `NOT`, `NEAR`, `-`, `:` and the like are literal text. Tokens
>   with no letter or digit are dropped. It returns `null` when nothing
>   searchable remains, and the caller then omits the `MATCH` clause. The
>   result is always bound as a parameter. It never throws.
